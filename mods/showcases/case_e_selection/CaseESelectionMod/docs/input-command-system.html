输入与指令系统

面向第一次接触的新读者。读完你会理解：一次按键、一次触控、一个 bot 的决策，怎么一步步变成游戏里实际发生的事。

0. 这套系统解决什么问题

同一个按键在不同情况下做不同的事：

  • FPS 里 w 是前进，RTS 里鼠标框选是选中，MOBA 里 q 是放技能。
  • 同一个「左键」，在 FPS 是射击，在 RTS 是框选，在 MOBA 是让英雄走过去。
  • 同一个技能，键鼠操作和触屏操作「怎么瞄准目标」完全不同。

这些差异不是「键位不同」，而是「这个输入此刻被理解成什么、最终做成了什么」不同。本系统把这件事分清楚：从一次输入到游戏效果，中间经过哪些层，每层各管什么。

1. 先立住两个底层

在讲任何概念之前，先定两件已经确定、不用再讨论的事：

1.1 现成的基建：App / Machine / Seat / EntityRep

这套系统长在一个已经分层的骨架里，我们直接用它，不重新设计：

  • Machine：一台实机/虚拟机。
  • App：一个进程宿主（UE / Raylib）。
  • Seat：某台机器上，一个 App 进程接的玩家席位。
  • EntityRep（representative entity）：一切 player / team / 单位都物化为实体。一个玩家 = 一个实体。别的 manager 只是它的投影，数据本尊都落在这个实体上。

这一层是现成的，本系统不发明它。它只是「玩家是谁、坐在哪个席位、在哪个世界实体上」的底座。

1.2 唯一要设计的执行载体：graph

graph 是一个函数——一段游戏作者写的可调用逻辑。它是唯一的执行载体：所有「行为」（筛选、算方向、切上下文、组意图、交互形态）都是 graph 执行的。

⚠️ 这点很重要：本系统没有 graph 之外的固定执行器（没有"某个 system 替 graph 做决定"）。一切行为都归于 graph。其他概念（上下文、偏好、操作对象）都是喂给 graph 的声明 / 数据，不是自己会动的东西。

2. 三个概念：input、context、audience view

这套系统里最容易被搞混的是三样东西。先立住：它们是三个独立的东西。

2.1 input — 是谁的输入

「这部分输入来自哪个玩家/哪个席位」。玩家1 的按键、玩家2 的摇杆、bot 的决策——各是各的 input。

2.2 context — 交互状态（挂实体）

「这个玩家此刻在什么交互状态」（战斗 / 施法瞄准 / 菜单 / 选宝物）。它挂在实体上（模拟侧），观战能读，决定此刻哪些语义动作成立。

⚠️ 区分两层：InteractionContext（交互状态，挂实体）是"玩家在干嘛"——这是世界实体状态，观战能读。而"此刻这个键 = 什么意思"的键 → 语义表是本机投影（把交互状态 + scheme 翻译成本机按键语义），不进实体、不进存档。两者别混（详见 §3.3.1 与 §8）。

2.3 audience view — 以谁为视角

「现在以哪个玩家为观众」。观战切到玩家2，就是 audience 切成玩家2。这决定你看到谁的画面、谁的 UI 对你可见。

2.4 三者关系

概念上三个独立。观战切到玩家2，input / context / audience view 可以一起切成玩家2——但它们是三个独立的东西，只是切换时常常联动。

一个例子立刻分清楚：玩家2 在剧情对话里选三个宝物。 - 对话剧情（Model）：对话进行到哪、有哪些宝物 —— 和下面都无关。 - 对话 UI（View）：把宝物选项画出来 —— 和下面都无关。 - interaction context：此刻哪些键 = 选宝物（用键鼠还是手柄，对应的是完全不同的键和语义）—— 它只管「键的语义」，不碰剧情、不碰 UI。 三者分离（MVC）：对话可以是对面玩家2 在操作，但"选宝物"的语义不变；UI 可以是花里胡哨的轮盘 / hover，最终都落到同一个语义。

3. ControlScheme 与 BindingOverride：设备映射怎么定

这是「键 ↔ 语义」那层的关键，单独讲清楚。

3.1 ControlScheme = 设备交互范式

ControlScheme（控制方案）是一套「设备交互范式」：定义「用什么设备、移动/视角/瞄准这些基本交互怎么实现、提供基础绑定」。它不只是键位——不同 scheme 的移动方式可能完全不同（WASD 离散键 / 左摇杆连续轴 / 点地面，见 §3.3）。

例如两种真正不同的方案：

  • 方案 A：键鼠（WASD 离散键移动 + 鼠标视角）。
  • 方案 B：手柄（左摇杆连续轴移动 + 右摇杆视角）。

判据：scheme 变的是"交互范式"（用什么设备、移动/视角怎么实现），不是某一条绑定的键位。 单条语义换键（比如把 1 技能从左键改成空格）不是新 scheme，是 BindingOverride（见 §3.2）。

3.2 BindingOverride = 覆盖某个绑定，不改方案

玩家想自己改键——比如把 1 技能从左键改成空格——这不是新建 scheme，而是在某一个 scheme 下，覆盖某一个绑定。BindingOverride（玩家偏好）挂在玩家身上，只覆盖单个 binding，不改方案本体。

这里"绑定"指"一个物理键 / 设备 → 一个语义动作"的对应关系。方案（scheme）里有一张绑定表，玩家改键就是改其中某一条，不是重做整张表。

3.3 分层结构：基础（ControlScheme + InteractionContext）+ 覆盖（BindingOverride）+ 偏好（InteractionPref）

最终生效的「键 → 语义」表，是分层的——不是四个并列的东西：

[基础] ControlScheme ⊕ InteractionContext → 基础"键→语义"表 / 基础交互方式
   ↑ 覆盖：BindingOverride（必然基于某个 ControlScheme，覆盖它的单个绑定）
   ↑ 偏好：InteractionPref（必然基于某个 InteractionContext，偏好它的交互怎么完成）

两个"必然基于"（结构性）： - BindingOverride 必然基于一个 ControlScheme——它是"改某个键"，前提是已经有一张 scheme 的基础绑定表（"左键=BoxSelect"）。没有 scheme 就没有可覆盖的绑定，它引用它覆盖的那个 scheme。 - InteractionPref 必然基于一个 InteractionContext——它是"这个交互怎么完成"，前提是当前在某个 context（战斗/瞄准）。没有 context 就没有"这个交互"，它引用它作用的那个 context。

用 LOL PC 版举例，一次把四个概念全展示出来：

① ControlScheme（设备交互范式，基础）——不只键位，是整套交互范式 - 方案 A：WASD 移动 + 左键放 1 技能。 - 方案 B：右键移动 + Q 放 1 技能。 - 注意：不同 scheme 的移动方式可能完全不同——键鼠是 WASD 离散键移动，手柄是左摇杆连续轴移动，触屏是虚拟摇杆/点地面移动。"移动"的实现方式（离散键/连续轴/点地面）是结构性的，不是改键。所以 scheme 是一套设备交互范式（用什么设备、基本交互怎么实现、提供基础绑定），不只键位。

② InteractionContext（交互状态，基础，挂实体）——此刻在什么交互状态 - 战斗 / 施法瞄准 / 菜单 / 选宝物——挂实体（模拟侧），观战能读。 - 它决定此刻哪些语义动作成立（能否框选/施法）。

③ BindingOverride（覆盖层，必然基于某个 ControlScheme）——改单个键 - 玩家把 1 技能从左键改成空格——这是 BindingOverride：覆盖它基于的那个 scheme 下的某一个 binding。 - 它只改单键，不动 scheme 的交互范式（移动还是 WASD，不会因为改键变成摇杆）。

④ InteractionPref（偏好层，必然基于某个 InteractionContext）——这个交互怎么完成 - 1 技能智能施法（悬停目标直接放）还是不智能（进瞄准态）。 - 智能施法带不带指示器（按下出指示器、移动瞄准、松开放；还是直接放）——都可配置。 - 它挂在 ability 语义 slot 上，不是挂在具体技能上：语义 slot 是"attack"、"skill1"这种语义键（映射到具体技能）。同一个语义 slot（如 attack），不管落到陆战队还是坦克，都走这个 slot 的偏好。 - 支持两层覆盖 + 一个优先级规则： - per player：玩家级默认（这个玩家全局喜欢智能施法）。 - per ability template：某个具体技能模板覆盖（这个技能必须二次确认）。 - 优先级（总序闭合，把"实例"拆成两个明确角色）：实例(带锁) > per ability template > per player > 实例(默认)。实例默认垫底，但实例带锁定标记时压过一切。

每个概念管什么：ControlScheme 管"用什么设备、移动怎么实现"（基础），InteractionContext 管"此刻什么状态"（基础），BindingOverride 管"改单个键"（覆盖 scheme），InteractionPref 管"这个交互（挂语义 slot）怎么完成"（偏好 context）。LOL 例子：A/B 是 scheme 差异、改键是 BindingOverride（覆盖 scheme）、瞄准态是 InteractionContext 差异、智能/带不带指示器是 InteractionPref 差异（偏好 context，per player 默认 + per ability template 覆盖）。

3.3.1 预设 vs 运行时：InteractionContextDefinition 与 InteractionContextInstance

InteractionContext 要分"预设（定义）"和"运行时（实例）"两层，否则解释不了热插拔 scheme 时数据为什么持久。

  • InteractionContextDefinition（预设/配置，永久）：声明"这个 context 有哪些绑定、启用哪些 trigger"。存在配置里，不随 runtime 变。
  • InteractionContextInstance（运行时/实例，可变）：记录"此刻实体处于哪个 context"（战斗/瞄准/菜单）。存在实体上，随交互变。

两者关系：实例引用定义——runtime 状态说"我在战斗"→ 读"战斗"的定义（配置）→ 结合当前 scheme → 解析出实际绑定。

热插拔 scheme（突然插手柄）时数据持久的依据：插手柄只换 ControlScheme（设备映射），InteractionContextDefinition（配置）和 InteractionContextInstance（状态）都不动——还是"战斗"状态、还是"战斗"的定义，只是 scheme 换了，重新解析出摇杆绑定。如果预设和运行时混在一起（把配置当状态），插手柄就会改掉/重置 context，数据就不持久了。所以预设（Definition）和运行时（Instance）必须分离。

3.4 热切换

像键鼠游戏突然插上手柄：scheme 从键鼠切到手柄，同一场景对应的"键 → 语义"表就跟着变（鼠标点击 → ABX 按键）。但交互状态（选宝物这个场景）不变——你还是在那选宝物，只是换了一种操作方式，视图（panel）也随 scheme 换。这正是 §3.3.1 的 Definition / Instance 分离：热插拔只换 scheme（设备交互范式），context 的定义和实例都不动，数据才持久。

3.5 三个概念怎么分工（含一个易漏的点）

到这儿，scheme、InteractionPref、context 三件事的关系值得立清楚，因为 InteractionPref 会和 context 纠缠：

概念 决定什么 放哪
scheme 设备交互范式：用什么设备、移动怎么实现、基础绑定 方案侧（设备）
InteractionPref 挂在 ability 语义 slot 上：触发后怎么完成（智能施法/二次确认/蓄力） 语义 slot 上，per player + per ability template 覆盖（随存档）
context 此刻哪些语义成立 交互状态（实体）⊕ scheme

重点：InteractionPref 不只是"怎么完成"——它会决定进哪个 context。 举个例子：

  • 同一个 Q 键触发 1 技能（scheme 决定）。
  • 智能施法（InteractionPref = 智能）：不用进瞄准 context，直接放。
  • 不智能施法（InteractionPref = 不智能）：进入瞄准 context（叠加，不替换移动），瞄一下再放。

所以 InteractionPref 在 scheme 和 context 之间是个"楔子"：它自己不是 scheme、不是 context，但它能牵出 context（选"不智能"→ 进瞄准 context）。这个概念之前是缺口，这里明确它——InteractionPref 独立（不并入 scheme），且它会决定要不要进某个 context。

4. 核心链路：从一次输入到一次「语义动作」

这是全篇最重要的一条线。一次输入，无论是玩家按键，还是 bot 决策，最终都收敛到一个「语义动作」。

设备物理输入（键 / 摇杆 / 触控 / bot 决策）
      │
      ▼
① 语义动作 Action  ← 所有形态在这里收敛

语义动作（Action）：一个「可被理解的事」。选宝物、移动、放技能、框选。它不绑定任何键——它是这个词本身。

为什么所有输入都收敛到它： - 玩家按键 → 按 scheme 解释成某个语义动作。 - 玩家点触屏面板按钮 → 引擎把「点面板」映射成对应语义动作。 - bot 模拟玩家 → 直接注入「选宝物」这个语义动作，不需要真的模拟按键。

所以：设备物理输入是玩家才有、可以跳过的；语义动作 是玩家和 bot 的共同入口。

花里胡哨的交互形态（轮盘 / hover / 画圈）不影响这件事——它们只是表现层的花活，最终都「给出一个语义动作」就结束了。

但注意：「共同入口」不等于「所有设备同一套动作」。 是否为同一套动作，取决于语义动作本身相不相同，而不是设备是什么：

  • WASD 和摇杆 —— 语义动作相同（都是「移动到一个方向」）。你按 WASD 还是推摇杆，语义都是 moveIn(direction)，一套动作。
  • 右键点屏幕移动 —— 这是「移动到某个世界点」，语义动作不同，是 moveTo(point)，另一套动作。
  • 选宝物（键鼠指点 vs 手柄按键）—— 一个是 pointAt(pos)、一个是 pressKey(A)，不同套。

所以「是否一套 action」，判据是语义动作相不相同，不是设备。上面的例子要分清两层：「移动」这个动作，WASD 和摇杆语义相同（都是"往一个方向位移"）；「选宝物」这个交互，键鼠和手柄语义不同（键鼠是"点位置"、手柄是"按键"）——这两个是不同的事，不是"有时设备相同语义、有时不同"。

4.1 action 定义层的 processor：处理"单击 / 长按 / 框选"

同一个物理左键，怎么区分"单击（点选）"和"按下→拖动→抬起（框选）"？ 这是 action 定义层的 processor（时间序列处理器）的职责，不属于 context 的职责——照 Unity Input System 的 Interactions / UE Enhanced Input 的 Triggers 结构：

  • Interactions / Triggers（时间序列）：决定"怎么算触发"——Tap（单击，按下同位置抬起）、Hold（长按）、Drag（拖动，按下→移动→抬起）、MultiTap（连按）。
  • Processors / Modifiers（数值）：处理输入值——Deadzone、Normalize、Scale、Invert。

同一个物理左键，配不同的 Interaction，就是不同的 action：

// 同一个 <Mouse>/leftButton，配不同 Interaction → 不同 action
{ "actionId": "TapSelect",    "path": "<Mouse>/leftButton", "interaction": "Tap" }         // 单击 → 点选
{ "actionId": "BoxSelect",    "path": "<Mouse>/leftButton", "interaction": "Drag" }       // 拖动 → 框选

注意：Drag 隐含"按下"——拖动必然要先按住，所以不写 Hold+Drag（那只是一种 Interaction：Drag）。同理 Tap 隐含"按下后同位置抬起"。

所以"单击 vs 框选"在 action 定义层就分开了——单击是 TapSelect（点选），按住拖动是 BoxSelect（框选）。这是两个不同的 action，各自有语义，不是 context 去判断"这次是单击还是拖拽"。零长度框（同帧按下+抬起）也由 Interaction 的阈值/判定处理（Tap 就是"没拖动"的框选 → 点选）。

这属于 action 定义层的配置（绑定 + Interaction/Processor），和 scheme（物理→action 映射）、context（哪些 action 启用）分层明确：action 定义层管"怎么从物理输入识别出这个 action"，不掺 context。

5. 语义动作之后：它停在 context，还是走向意图

先定义两个词，后面会一直用到： - 意图（intent）：玩家想干的那件事，带语义 + 目标 + 参数。例如「命令选中的单位移动到那里」。 - 指令（order）：意图落地成具体动作。例如「移动到那里」落到步兵是走过去、落到坦克是先转向再开炮。

意图回答"想干什么"，指令回答"具体怎么做"。意图不携带具体技能——那个到指令才解析。

语义动作产生后，有两个去向：

语义动作（选宝物 / 放技能 / 移动 / 框选）
      │
      ├─ 去向A：一切非下令消费 —— 不出意图、不下指令
      │    ├─ 例：剧情对话选选项、菜单选项、UI 交互（喂给 UI/剧情逻辑）
      │    └─ 例：框选写选中集合（写世界状态：往"选中集合"这个实体表里写入选中的单位，但不设令）
      │    ————— 到这里就结束。A 支的核心是"语义动作有了，但不往意图/指令走"。
      │
      └─ 去向B：继续走到「施法 / 下令」管线
           ————— 只有「往世界下令 / 放技能」时才走这条。

关键：A 支不是"对话/UI"这么窄，而是「一切非下令消费」——包括对话、菜单、UI 交互（喂给界面/剧情），也包括框选写选中集合（改世界状态但不生成意图、不下指令）。B 支才是「往世界下令 / 放技能」。

所以 command intent / ability order 不是"每次输入都必经"的通用环节，它们只属于「往世界下令 / 放技能」那一支。

6. 施法 / 下令支线：command intent 和 ability order

当语义动作要往世界下令时，往下走：

6.1 command intent（施法意图）

它是什么：玩家想干的那件事，带语义 + 目标 + 参数。例如「命令选中的单位移动到那里」。

它有几个组成部分： - 语义：做什么（移动 / 放技能 / 攻击）。 - 目标：作用在谁 / 哪个位置。 - 偏好（InteractionPref）：怎么完成——智能施法（直接放）、二次确认、蓄力。

InteractionPref 有个容易漏的点：它不只是"怎么完成"，还会决定要不要进某个 context。智能施法不用进瞄准 context 直接放；不智能施法则进入瞄准 context（叠加，不替换移动），瞄一下再放。所以 InteractionPref 会牵出 context——这是它和 scheme/context 的关系（见 §3.5）。

它和具体能力的关系：意图不携带具体技能。同一个「攻击」意图，落到陆战队员是普攻、落到坦克是坦克炮——具体是什么，是下一步才解析的。

6.2 ability order（指令）

它是什么：意图落地的具体动作。对每个目标实体，按它的技能槽 / 装备 / 状态，解析成具体指令。

为什么分两步：同一个意图落到一群实体上，可能有好几种分配方式。例如「框选一群单位同时放技能」，可以一个个放、可以挑最近的放、可以一群同时放。差别全在"领域规则怎么解释这次意图"。

6.3 瞄准怎么算：无状态 helper 节点（aimsource）

「怎么瞄准」这件事，抽象不出一个通用结构——不管双摇杆、WASD 左键、还是右键移动 + q 技能瞄准，都要从「rep entity 的位置 + 这个 context 下的 action payload（动作携带的参数数据）」算出来，而每种方式算出来的东西不一样：

  • 双摇杆 → 方向向量
  • WASD 左键 → 地面点，再转方向
  • 右键移动 + q 技能 → 另一套方向

所以 aimsource 不是意图里的一个字段，也不是一个有状态的系统——它是一组无状态的 utility helper 节点（纯函数），被 graph 调用。graph 在做瞄准相关的花哨逻辑时，调用这些 helper 节点，算出方向 / 点 / 目标。

graph（花哨交互，从 rep entity 拿输入）
  ├─ 调用：aimsource helper 节点（无状态纯函数）
  │    ├─ ScreenPointToGround（屏幕点 → 地面点）
  │    ├─ StickToDirection   （摇杆 → 方向向量）
  │    └─ PointToDirection   （地面点 + 主体位置 → 方向）
  └─ 产出：语义动作 / 意图（携带算好的结果）

统一的不是"怎么算"，而是"算完归一成什么"。 而「归一成什么」是按动词族各自枚举的，不是所有意图都归成同一种形状：

  • 移动族：可能是 moveDirection(矢量方向)，也可能是 moveToPoint(世界点)——看这个游戏怎么定义移动。
  • 攻击族：可能是 attackTarget(目标实体)，也可能是 attackAtPoint(位置)，也可能是 attackDirection(dir vec)——看这个技能要什么。

所以不是"统一只有两种结果"，而是"每个动词族，把不同输入方式收敛到该族的少数几个统一结果"。 上面列的那两组只是示例，具体每个动词族有多少种、哪些种，由游戏自己定义。算的过程不统一（各自 helper 节点），算完归一到本族的统一结果。

7. graph：一切行为都在这里

graph 是函数，是唯一执行载体。所有行为都写进 graph。它从唯一入口拿数据，最后统一提交。

7.1 唯一上下文入口：rep entity

graph 要访问任何"关于这个玩家"的上下文，都必须从「这个玩家的 rep entity」出发。 它不直接抓全局、不绕过 rep entity 抓别的实体。

这样 bot 和玩家完全对齐——两者都有自己的 rep entity，graph 都从它拿上下文。

7.2 graph 能承载什么（举例，不是分类）

graph 能承载各种行为——权威分类见 §7.4 的六类。这里举几类常见用途（不是另一份分类）：

  • context 获取：算「这次操作作用在哪些实体上」（操作对象），从 rep entity 出发。
  • 交互形态：轮盘 / hover / 画圈等花哨交互，也可 graph 化——graph 需要什么输入自己拿（从 rep entity），但要遵守"唯一入口 rep entity"。
  • 意图组装：把操作对象 + 状态 + 瞄准源组织成意图。
  • 切换 context：改写 player entity 上的 context 状态。

7.3 graph 不做什么

  • 不自己实现底层几何原语（点 → 方向那种是独立原语，graph 调用它）。
  • 不自己实现底层设备识别数学（套索曲线、点在多边形这种几何判定是独立原语，graph 调用它）。

7.4 graph 在每层的分工：六类 graph

把整条链拆开，每一段各配一类 graph。这样「哪一层要配 graph」就清楚了。

第 1 类 graph 读 ControlScheme（设备映射表，见 §3）做编排，不是替代它——scheme 是声明数据，graph 读它来决定"这个物理事件 = 哪个语义动作"。

两个例子：两种输入在哪个 graph 处分歧

下面看两个典型的输入差异——它们分别在两个不同的 graph 处产生分歧，不是同一个 graph 同时处理：

① WASD 左键 vs 双摇杆 → 是「设备 → 动作」graph 的区别。 这两个在第 1 类不同。WASD 是离散键、双摇杆是连续轴，把设备物理译成"语义动作"的方式不同（一个逐键、一个积分）。所以"设备→动作"这个 graph，WASD 版本和双摇杆版本内容不同。这也是 ControlScheme 的不同方案（WASD 一套、双摇杆另一套）。

② WASD 左键 vs 右键 Q 技能 → 是「动作 → 意图」graph 的区别。 这两个在第 3 类不同。WASD 左键是「移动/射击」→ 一个意图；右键 Q 技能是「Q 技能瞄准」→ 另一个意图。所以"动作→意图"这个 graph，两者的规则不同。

关键：这两个差异不同层、不同 graph。所以「同样是鼠标左键」，在"设备→动作"是"离散按键"、在"动作→意图"是"移动/射击"——分别由两个不同的 graph 处理。

7.5 graph 两种形态：trigger graph vs func graph（照蓝图）

graph 基建有两种结构形态，照蓝图的约定：

trigger graph（Event Graph） func graph（Pure Function）
入口 入口（语义动作直绑 / context 激活/结束 / 游戏事件） 无事件——它是被调用的
执行引脚（exec） 有（白色：决定执行顺序） 无（纯函数没有执行引脚）
数据引脚（data） 有（彩色：传参数） 有（输入 → 输出）
副作用 可以有（切 context、发事件） 无（纯计算）
典型用途 响应事件、编排流程（切 context、提交请求） 纯计算（过滤命中、集合运算）

关键：exec 流（执行流）和 data 流（参数流）是分开的两套——照蓝图： - exec 引脚（白）：决定"执行顺序"——从一个节点执行完沿 exec 引脚到下一个。这是执行流（谁调用谁）。 - data 引脚（彩）：节点之间的数据输入输出。这是参数流（传了什么数据）。 - 两者不混：一个节点既有 exec 入/出（白），也有 data 入/出（彩）。画图时 exec 用白线、data 用彩线，分开画。

trigger graph 有 exec（事件驱动 + 执行顺序 + 可有副作用）；func graph 无 exec（只有 data，纯函数）。一个 trigger graph 图体内可以调用 func graph（算命中、算集合语义），func graph 是纯计算，不打断执行流。

7.6 集合变化发事件：跨功能基建

"某个集合成员变了，我要响应"是跨功能需求（框选的选中集变化、编队变化、组员变化都用），所以它是基建，不是某个玩法专属。

定义：集合的成员 = presenter 的宿主 entity（host entity）。"集合变化" = 某个 host entity 加入 / 离开某个集合。

事件 schema：

CollectionMembershipChanged {
  collectionKey: string,    // 哪个集合（如 "selected"）
  changedEntity: entity,    // 变化的 host entity（presenter 宿主）——通知"这个实体上的 presenter"
  changeKind: added|removed // 加入 / 离开
}

作者体验（简单）：在任意 presenter rule 里订阅任意集合 key 变化，其余（扫描、编译、通知）都是基建自动做：

presenter rule:
  subscribe: { collection: "selected" }   // 订阅 selected 集合
  onChanged:                              // 收到 CollectionMembershipChanged
    added   → 高亮（驱动本 presenter）
    removed → 取消高亮

初始化编译：启动时扫描所有 presenter rule 的订阅声明 → 编译成「集合 key → 订阅它的 rule 列表」索引。运行时某个 host entity 加入/离开集合 → 基建查索引 → 通知订阅该集合的 rule → 驱动该 host entity 上的 presenter。

8. interaction context 的切换：挂在 rep entity，由 graph 执行

interaction context 的状态，挂在 player entity（rep entity）身上。 它是世界上「这个玩家当前处于什么交互状态」的客观事实，谁都能读。

这里要分清两件事： - 交互状态 / 交互上下文（挂实体）：「这个玩家在干嘛」（选宝物 / 战斗 / 菜单）——模拟侧实体状态，观战能读。 - "键 → 语义"表（本机投影）：「qwe 此刻 = 选宝物」——这是本机把交互状态 + scheme 翻译成键位语义的产物，不进实体、不进存档。它是本机投影，不是世界实体状态。

观战要读的是前者（交互状态挂实体）；后者（键语义表）是本机投影。把键语义表当成世界实体状态，会跟"本机 I/O 不进世界实体状态"这条边界打架（本机的东西：设备、键位、控制方案——不该作为世界实体状态被存档/被网络复制）——所以"键 → 语义"表是本机投影，不挂实体。

切换 context = 改写实体身上的这个字段（交互状态），由 graph 执行。

为什么必须挂在实体上（第一性原理）：看观战。你从玩家1切到玩家2，玩家2正在打开一个菜单——你要能拿到玩家2的交互状态。 这意味着玩家2这些状态必须挂在玩家2的实体上，而不是挂在本机 / seat 上。否则你切过去读不到他。能被人读的、可切换视角的，必须是世界实体状态。

8.1 context 获取：主动 / 触发两种

「这次操作对象从哪来」，分两种： - 主动获取：不等输入，定时更新。例：视锥扫敌人、最近目标、光环内友军。 - 触发获取：输入来了再取。例：点选、框选。

获取的计算由 graph 执行（从 rep entity 拿数据、筛选、排序）。

8.2 context 是图状结构：可衍生子 context

context 不是一张扁平的表，而是图——一个 context 可以衍生出子 context，子 context 用完再回到父 context。

最典型的例子是施法瞄准：

[战斗 context]
   │  按 Q 施法（激活"瞄准"）
   ▼
[瞄准 context]（从"战斗"衍生出来的子 context）
   │  瞄准结束 / 取消（停用"瞄准"）
   ▼
[战斗 context]（回到父 context）

这个"衍生 / 返回"由宏观的 trigger 控制——一个 trigger graph 监听"进入施法"事件 → 激活"瞄准"子 context；监听"施法完成 / 取消" → 停用"瞄准"。

所以 context 图 = context 节点 + 激活/停用的边，边由 trigger graph 驱动。 一个 context 下可以有多个子 context 并存（比如瞄准中还能移动——"移动"和"瞄准"两个 context 同时活）。它们是并存的集合，不是单一路径的栈。

8.3 context 生命周期：学 presenter 的 scope 模型

每个 context 不只是"我是谁"，还带状态——指示器、中间参数、画到一半的圈。这些状态跟着 context 的生命周期走。

context 的生命周期直接学 presenter 的 scope 模型（代码里已有一套）：presenter 创建时绑定 scopeId，销毁按 scope 整组清（含递归子）。context 就是一个 scope 容器：

  • 进入 / 激活 context：建一个 scope（scopeId = 这个 context）。context 内创建的 presenter 都挂这个 scope（Create(defId, owner, scopeId)）。
  • 离开 / 停用 context：DestroyScope(scopeId) 整组清——这个 context 下创建的所有 presenter（含递归子）一起销毁。

关键：不需要作者手工 push/pop、不需要记得"退出时清理"。 context 是 scope 容器——激活建 scope，停用自动清 scope。这是结构性生命周期，不是纪律。例子：

进入"瞄准"context → 建 scope（scopeId=瞄准）→ 创建画圈 presenter（挂这个 scope）
  │
  ├─ 施法完成 → 停用"瞄准" → DestroyScope(瞄准scope) → 圈消失（自动）
  └─ 取消施法 → 停用"瞄准" → DestroyScope(瞄准scope) → 圈消失（自动）

为什么必须这样：如果不按 scope 清，画到一半的圈会一直留在画面上（视觉残留）、中间参数会污染下一次操作。scope 容器保证"离开即清理"，不需要作者记得。

祖先关系：子 context 的 scope 挂在父 context 下（scope 嵌套）。停用父 context → 自动清父 scope（含所有子 scope）——父退自动清子，不需要作者逐层 pop。

指示器这类视觉状态用 presenter 基建，生命周期 scope 绑定实体 interaction context

「画到一半的圈」这类视觉状态，不是 graph 自己画的，是用 presenter 基建（呈现系统）创建的。presenter 的生命周期 scope 绑定到实体的 interaction context 上：

  • 创建：进入 context 时，创建一个 presenter 实例，绑定 owner = 该实体的 rep entity + scopeId = 这个 interaction context 的 scope + 锚定方式（实体锚定 / 世界位置锚定）。
  • 销毁：停用 context 时，按 scope 销毁——DestroyScope(scopeId) 把这个 context 下创建的所有 presenter 一起清掉（指示器跟着 context 清理）。
// presenter 的生命周期 scope 绑定实体的 interaction context
presenter "indicator.aim_circle":
  lifecycle: { persistence: "Scoped" }        // scoped 生命周期
  anchor: { kind: "entity", owner: "rep" }    // 绑定到实体（rep），scopeId = interaction context 的 scope
  // 进入瞄准 context → 创建（owner=rep, scopeId=瞄准context）
  // 停用瞄准 context → DestroyScope(瞄准context的scopeId) → 指示器消失（自动）

所以"清理画到一半的圈" = 按 scope 销毁 presenter——不是 graph 手动调"关指示器"，而是销毁这个 context scope 下创建的 presenter。这由 presenter 基建的生命周期 scope 机制提供（Create(defId, owner, scopeId) / DestroyScope(scopeId)），graph 触发进入/停用 context，presenter 跟随 scope 生命周期。

9. 监听与切换：怎么配「切 scheme / 切 context」的 graph

前面讲的是「一次输入怎么变成意图」。这一节讲另一类 graph——监听事件、触发切换的 graph：它不处理输入，只响应某个事件，然后切 scheme 或切 context。

9.1 切换类 graph 是什么

这类 graph 的结构是固定的：监听一个事件 → 执行一个切换。

[切换类 graph]
  监听：某个事件（设备事件 / 游戏事件）
  → 切：换成某个 scheme / context
  → 数据：从 rep entity 拿（唯一入口）

它不产生语义动作、不组意图——它只是"看到某件事发生了，把 scheme 或 context 换一下"。

9.2 两类切换（各举一例）

① 监听设备事件 → 切 scheme（换设备映射）

像键鼠游戏突然插上手柄（设备热插拔）：

[graph: 切画面设备]
  监听：gamepad_connected（手柄接入，设备事件）
  → 切：scheme 从"scheme.pc_wasd" 换成 "scheme.pad_twin"
  → 视图（panel）也随之换成手柄版

这里切换的是 scheme（设备映射表）。它让"同一场景"从键鼠操作变成手柄操作。

② 监听游戏事件 → 切 context（换交互状态）

像游戏逻辑触发"进入战斗" / "打开菜单" / "进入施法瞄准"：

[graph: 进入施法瞄准]
  监听：ability_aim_enter（游戏事件：玩家进入施法瞄准）
  → 切：context 状态 从"战斗" 换成"施法瞄准"（改写 rep entity 上的交互状态）
  → 之后"施法瞄准"场景下的键语义，由交互状态 ⊕ scheme 组合出来

这里切换的是 context（交互状态）——改写实体上的"玩家在干嘛"。它决定后续走哪套语义绑定。

9.3 配置它们：trigger graph 的 entry（挂事件 + 图体内做切换）

切换类 graph 本质也是 trigger graph——它挂在某个事件上，事件来了才跑。所以配置用 trigger graph 的标准形态（Event 字段挂事件，切换动作写在图体内）：

trigger_graph "graph.switch_scheme_on_gamepad":
  entry {
    event: "GamepadConnected"        // 监听哪个事件（设备事件 / 游戏事件）——字段是 Event
  }
  // 图体：事件来了，执行切换
  body:
    switch_scheme("scheme.pad_twin")   // 切 scheme（设备交互范式）
    // 或 switch_context(...)          // 切 interaction context（交互状态）
    // 数据入口：从 rep entity 拿（唯一入口，见 §7.1）

字段含义： - event：挂载监听的事件。分两种来源——设备事件（插拔手柄、切设备）、游戏事件（进入战斗、打开菜单、进入施法瞄准）。这是 trigger graph entry 的监听字段。 - 图体内的切换动作：switch_scheme(...)（换设备交互范式）或 switch_context(...)（改交互状态）。切换动作写在图体里，不是配置字段。 - 数据入口：始终是 rep entity（唯一入口，见 §7.1）。

9.4 一个容易混淆的点：切 scheme vs 切 context

  • 切 scheme：换"设备映射表"（用哪套设备）。它不改变你"在干嘛"（交互状态不变），只是换操作方式。例：插手柄，选宝物从"鼠标点"变"按 A/B/X"。
  • 切 context：改"交互状态"（你在干嘛）。它改变后面走哪套语义。例：从"战斗"进"施法瞄准"。

两者都可能被"切"触发，但切的是不同的东西。设备事件（插手柄）通常切 scheme；游戏事件（进战斗/开菜单）通常切 context。

补充：实际游戏里，一次切换可能同时切两者（比如从"野外探索"切进"战斗"——既换个交互状态 context，也可能换了设备映射 scheme）。它们是两个基础元素（§3.3 的基础组合），切割哪个看触发的是什么事，可以一起切，也可以只切一个。

10. 完整链路（用剧情对话选宝物走一遍）

玩家2（或 bot）在剧情对话里，遇到三选一选宝物
  │
  ├─ input：这个输入属于玩家2
  ├─ 交互状态：此时在"选宝物"（挂实体，模拟侧）
  ├─ scheme：键鼠 or 手柄（决定"选宝物"绑定哪些键）
  ├─ context（正交）：交互状态 ⊕ scheme → 最终"键 → 语义"表
  ├─ audience view：以玩家2为观众（若是观战视角，能看到他正在选宝物的界面）
  │
  ▼
语义动作：选宝物X / 按 A 选宝物1 / 点第2个宝物
  │
  ├─ 去向A（非下令消费）：喂给对话逻辑 → 结束。不出 command intent，不出 ability order。
  │
  └─ 去向B（施法/下令，本例不走）：再往下。

这个例子的关键： - 「选宝物」这个交互状态，配 scheme（键鼠/手柄），得到完全不同的最终 context——键鼠是"指点"（payload 坐标），手柄是"按键"（payload 键值）。这是正交，不是换键。 - 语义动作之后，只走到「非下令消费」就喂给对话逻辑，不生成 command intent、不生成 ability order。 - 如果宝物选项是轮盘 / hover 等花哨交互，也不影响——它 graph 化、从 rep entity 拿输入、最终同样给出「选宝物X」这一个语义动作。

11. 必记

  1. 三个独立的东西：input（谁的）、context（键此刻什么语义）、audience view（以谁为视角）。三者无关，可一起切。
  2. ControlScheme = 设备映射表（WASD+左键放1技能 vs 右键+Q放1技能，是不同方案）；BindingOverride = 覆盖单个绑定，不改方案。
  3. scheme 与 context 正交：最终「键 → 语义」表 = 交互状态（实体）⊕ scheme（设备映射）。正交不是"换键"，而是"action 和 payload 都不同"（键鼠指点 vs 手柄按键）。
  4. 语义动作是 player / bot 的共同入口：设备物理可被跳过。但「是否一套动作」看语义动作相不相同，不看设备——WASD/摇杆是"移动到方向"（一套），右键点屏是"移动到点"、键鼠选宝物是"指点"、手柄选宝物是"按键"（都不同套）。
  5. bot 注入哪一层，取决于要模拟什么：模拟"怎么操作"→ 注入语义动作；模拟"下了什么令"→ 注入意图；模拟"怎么按键"→ 注入设备输入。没有固定层——玩家从设备往上走，bot 从任意层切入。
  6. command intent / ability order 只属于「施法 / 下令」支线（B 支）：A 支是「一切非下令消费」——对话、菜单、UI 交互，以及框选写选中集合（改世界状态但不设令），都不生成意图、不下指令。
  7. graph 是唯一执行载体：一切行为归 graph；graph 从 rep entity（唯一入口）拿数据；提交格式统一。
  8. aimsource 是无状态 helper 节点：瞄准怎么算抽象不出通用结构，各自是纯函数节点，被 graph 调用；统一的是"每个动词族自己的少数结果"，不是所有意图归成一种形状。
  9. 交互状态挂 rep entity（模拟侧，观战能读）；"键 → 语义"表是本机投影（交互状态 ⊕ scheme 组合，不进实体、不进存档）。
  10. 第 1 类 graph 不替代 ControlScheme，而是读它做编排——scheme 保留为设备映射表，成为喂给 graph 的声明数据。
