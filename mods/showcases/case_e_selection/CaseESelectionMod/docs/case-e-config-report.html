05框拖拽中：每帧高亮命中对象（持续过程）

这不是事件——是"正在框选"context 下的持续过程 配置 + 代码

① 进入拖拽中 = 激活一个衍生的 context（不是去监听 action 动作）

按下框开始 → 激活一个衍生的 context："正在框选"（从"战斗"衍生出来，见主文档 §8.2 的 context 图状结构）。
拖拽中的一切（框 presenter、命中、高亮）都挂在"正在框选"这个 context 上——context 活它们活、context 结束它们停。这样不需要去监听 action 动作（框开始/结束），而是跟着 context 走。

①b 框的 presenter 从哪来——观察者模式，自己 rule 监听 context 变化

presenter 不是被 context 创建的——它是观察者：自己配置 rules[]，每个 rule 监听一个事件（kind + key）→ 执行一个命令。
框 presenter 的 rule 监听"正在框选"context 的激活/结束：激活 → 框出现；结束 → 框自动销毁。
生命周期自动跟随 context，不需要"清理 graph"——presenter 的 rule 监听 context 结束就销毁。
配置结构：presenter rules[]（观察者，真实形态）
rules[].event.kindstring监听什么事件（context 激活 / context 结束）
rules[].event.keystring哪个 context（"正在框选"）
rules[].commandobject命令：激活 → 创建/显示框；结束 → 销毁框

② 命中的人从哪来——纯函数 query graph，入参是候选 EntityCollection 的 key

配置一个纯函数 query graph（入参→出参，无副作用，是纯计算）。
入参 = 一个指定的 key：框之前就存在的 entity collection（如"可框选单位"集合）。框选不会框敌人/中立——入参就是候选集合，预先配好 key。
入参进 graph 后再过滤（排除敌人/中立、只留可框选的）→ 得到命中集合。
拖拽中每帧调用它：矩形每帧变 → 命中集每帧算（当前矩形 → 当前命中）。
它是子图，可复用：拖拽中每帧用（算当前命中）、框结束也用（最终结果）。
配置结构：query graph（纯函数）
inputcollection key候选集合（框之前就有的，如"可框选单位"）
filtergraph过滤：排除敌人/中立，只留可框选的
outputentity set命中集合
graph 流图 · 命中 query graph（纯函数，每帧调用，带引脚）

③ 高亮凭什么处理——presenter 行为，graph 只在集合变化时发事件

高亮是一种 presenter 行为——是"具体的 entity 拿到事件 → 传给自己的 presenter"。
graph 不直接操作每个对象的 presenter。graph 只负责：给命中实体发事件——不是每帧发，是集合变化时发（命中集变了才发"你被选中了 / 你出选中了"）。
实体收到事件 → 自己的 presenter 处理高亮（实体自己的 presenter scope）。
拖拽中每帧 vs 集合变化（关键区别）
每帧 调 query graph → 算当前命中集 集合变化时 发"成员变化"事件 实体 presenter 处理高亮

③b 「集合变化发事件」怎么实现——跨功能基建 + 事件 schema

定义：集合的成员 = presenter 的宿主 entity（host entity）。"集合变化" = 某个 host entity 加入 / 离开某个集合。
机制：初始化时扫描编译所有 presenter rule 的订阅声明 → 编译成「集合 key → 订阅它的 rule 列表」索引。运行时某个 host entity 加入/离开集合 → 基建查索引 → 通知订阅该集合的 rule。
作者体验：在任意 presenter rule 里订阅任意集合 key 变化，其余（扫描、编译、通知）都是基建自动做。
事件 schema：CollectionMembershipChanged（集合成员变化）
collectionKeystring哪个集合（如 "selected"）
changedEntityentity变化的 host entity（presenter 宿主）——通知"这个实体上的 presenter"
changeKindenum加入（added）/ 离开（removed）
presenter rule 订阅（作者体验：一行声明）
subscribecollection key订阅哪个集合（如 "selected"）
onChangedrule 响应收到 CollectionMembershipChanged：added → 高亮；removed → 取消高亮

06框结束：透传"命中集合 + 集合语义" → 下游写入

事件：框结束（抬起）→ 先停用"正在框选"context（DestroyScope），再透传 配置图体

框结束第一件事：停用"正在框选"context（scope 容器自动清）

按下框开始时 激活了"正在框选"衍生 context（建 scope）（见 04/05）。抬起框结束时，停用"正在框选"（DestroyScope 自动清 scope 内所有 presenter）——回到父 context（战斗）。
不需要手工 pop：context 是 scope 容器，激活建 scope、停用自动清（学 presenter 的 Create/DestroyScope）。不这样的话，"正在框选"一直挂着，框 presenter / 高亮也不会销毁（它们跟随 context）。
这也呼应 context 生命周期（主文档 §8.3）：离开/取消 → 清理。框结束就是"离开"，所以框、高亮随之清理（presenter 的 rule 监听 context 结束自动销毁）。

框结束做什么——把"命中集合 + 集合语义"作为参数 + 事件 key 透传，下游再写入

不是 graph 图体里直接写集合（硬副作用）。框结束 → graph 算出命中集合（复用 05② 的 query graph 子图）→
把「命中集合 + 集合语义」作为参数 + 事件 key 透传出去 → 下游（写集合的 handler）接收 → 写入。

为什么这样设计——可复用：如果用户切换 scheme，不用框选、用画圈——
命中层换（框=矩形 query → 画圈=圆形 query），但"透传集合 + 事件 → 下游写入"这层完全共享，不做重复配置。

透传出去的参数 + 事件 key

entitySet 最终命中集合 op replace / add / subtract collectionKey "selected" eventKey 事件 key（下游按它接收）
下游 handler 按事件 key 接收 → 写 EntityCollectionStore。
图 A · 上游 graph（graph.box_select 图体）：命中集合 + 集合语义 → 透传事件 key 发出
图 B · 下游 handler（另一个，不是 graph.box_select）：按 eventKey 接收事件 → 写集合
两段是不同的东西：A 是 graph 图体（算命中、透传事件）；B 是下游 handler（按 eventKey 接收、写集合）。中间靠事件 key 连接，不是同一张图。

op 从哪来——shift/ctrl 是语义动作，不是裸输入

graph 读的是语义动作（不是"左 shift 键按下"这个裸输入）：
ModifierAdd（加选语义）→ op = add（∪）
ModifierSubtract（差集语义）→ op = subtract（−）
无修饰 → op = replace（=）
scheme 里绑定：左 shift → ModifierAdd、左 ctrl → ModifierSubtract。graph 读语义动作，不是读裸按键。
