两个评审人对同一方案的 Round 1 结论已经汇总。你们已一致的部分不再讨论：帧序单一化是地基且工作量被低估（FrameRenderer 需长出 water/navmesh pass，BuildPassPlan 未被 RenderFrame 消费，共三份表达）；AssetManager 分层（Core 管描述符/VFS 合同、GPU 状态留 Render、Adapter 注入）；引用计数必须配租约+GPU 延迟销毁；异步加载 worker 只做 CPU 准备、GL 创建在渲染线程；持久 VB 先做 spike；逐实例剔除消费现有 CullState 不造第二 SSOT；截图/回放时序基准是拆分最大破坏面。

## 待裁定的分歧

**D1 优先级顺序。** 两案：
- codex：帧收敛 → 阴影接线+文档+schema（提前）→ 资产 → GPU 驻留+剔除 → 计量阈值 → RHI 等
- pi：内存守卫（计量+阈值）前置到帧收敛之前 → 帧收敛+HostLoop 拆分 → 资产 → GPU → 方向光+阴影
- 拟裁定：①计量+阈值断言（不含 GC 配置）作为前置小包；②帧序单一化+HostLoop 拆分；③"能力接线修复包"：阴影+方向光宿主接线、后处理/水面互斥、schema Sound、负缓存失效、错误策略统一；④资产句柄/租约/异步；⑤持久 VB spike+逐实例剔除；⑥RHI 等继续暂缓。你是否同意？不同意给出你的排序。

**D2 GC 配置。** codex：ServerGC/堆上限不应默认做，先实测 pause/工作集/native 峰值再定。pi：S7 里包含 runtimeconfig ServerGC:true+堆上限并前置。拟裁定：拆成"计量+阈值断言"（前置、无行为风险）与"GC 模式决策"（实测后单独决策，不进本 epic 默认项）。你是否同意？

**D3 同步 fallback 开关。** pi 的 S4 写了"保留同步 fallback 开关"。仓库纪律禁止 fallback/向后兼容分支，且 codex 强调"不能用资源没好就跳过绘制作为隐式 fallback"。拟裁定：不做开关；异步合同里定义显式状态（含"启动期预加载窗口内允许同步"这类一次性、可观察的语义，如果需要的话）。你是否同意？启动期同步预加载是否应该保留为显式合同？

**D4 阴影接线的位置。** codex 把阴影接线排在资产之前（第 2 位），pi 把方向光+阴影排在资产之后。你的最终立场？（本 epic 内都会做，只定先后与理由。）

**D5 GenTextureMipmaps。** codex：不宜随首次加载顺手加，应与上传策略/离线管线一起设计。拟裁定：mipmap 归入"资产上传策略/离线管线"子项，不单独顺手加。你是否同意？

**D6 子 issue 粒度合并。** Round 1 双方各出了 8 与 13 条子 issue。拟合并为 6 个工作流（对映上述排序①-⑤ + 文档对齐），每个工作流开一个子 issue，内含验收要点。你是否同意这个粒度，还是应更细？
