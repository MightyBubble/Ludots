Ludots 科技树作者配置指南

这页给内容作者和玩法设计用：你不需要先理解 Evaluator 或 ECS 内部结构，只要按“我要表达什么玩法”选择 scope，然后补齐几个 JSON，就能把科技、升级、英雄解锁、区域条件挂到实体上。

作者视角 Entity-scoped progression Cookbook cases 不使用 map tag 做 feature 开关
四步上手 树状编辑 选 Scope 解锁模式 常见配方 字段速查 避坑

四步上手

任何科技树 case 都可以拆成四个作者动作：定义作用域、放置作用域实体、写条件、把条件挂到按钮或效果上。

1. 声明 scope在 Progression/scopes.json 里声明作者自己的玩法作用域，例如 city、faction、region。
2. 放 host 和 memberhost 是保存科技状态的实体；member 是会使用这个科技的建筑、英雄或单位。
3. 写 requirement在 Progression/requirements.json 写“按钮何时显示/可用”的条件。
4. 挂 ability/effectAbility 用 showRequirement 或 useRequirement；升级用 CompleteProgression effect。

最小文件清单

文件作者写什么什么时候需要
assets/Progression/scopes.json作者自定义作用域名字，例如 city、faction只要不是本体升级，都建议声明。
assets/Progression/progressions.json科技 id 和默认 scope每个科技都要有。
assets/Progression/requirements.json按钮显示、按钮可用、升级前置条件需要解锁逻辑时写。
assets/Entities/templates.jsonProgressionScopeHost 和 ProgressionScopeBinding需要城池、势力、区域、省份等作用域时写。
assets/GAS/abilities.jsonshowRequirement / useRequirement需要控制按钮可见或可用时写。
assets/GAS/effects.jsonpresetType: CompleteProgression需要点击、事件或脚本完成科技时写。

树状科技树 Authoring

可以让 mod 作者在 authoring 阶段轻松编辑一棵树。推荐做法不是让作者手写所有 runtime JSON，而是新增一个 authoring source：编辑器保存树、compiler 把树展开成现在的 Progression 和 GAS 配置。

基础募兵scope: city
精兵训练requires: 基础募兵
谋士在场可回退状态门槛
作者只编辑一份树：assets/Authoring/Progression/trees.json。这里可以保存节点位置、分组、连线、设计备注、默认 scope、解锁模式和按钮绑定。运行时不直接加载这份文件。
作者在树上做什么compiler 生成什么运行时谁消费
创建一个科技节点assets/Configs/Progression/progressions.json 里的 progression entryProgressionConfigLoader
连一条前置线ProgressionCompleted 或 ProgressionLevelAtLeast requirement 子节点ProgressionRequirementEvaluator
选择“完成后永久解锁”CompleteProgression effectGAS Effect Pipeline
选择“当前条件满足才开放”EntityCount、TagAll 或 GraphValidation requirementAbility 的 showRequirement / useRequirement
把节点绑定到按钮带 showRequirement 或 useRequirement 的 ability 片段，或生成给作者复制/确认的 binding planAbilityExecLoader

推荐的 authoring 源文件

// assets/Authoring/Progression/trees.json
[
  {
    "id": "Tree.Shu.CityMilitary",
    "defaultScope": "city",
    "idPrefix": "Shu.CityMilitary",
    "scopes": [
      { "id": "city" },
      { "id": "region" }
    ],
    "nodes": [
      {
        "id": "basic_drill",
        "title": "基础募兵",
        "position": { "x": 120, "y": 180 },
        "unlock": { "mode": "PermanentProgression", "level": 1 },
        "bindings": [
          { "ability": "Ability.TrainMilitia", "gate": "use" }
        ]
      },
      {
        "id": "elite_training",
        "title": "精兵训练",
        "position": { "x": 380, "y": 180 },
        "parents": ["basic_drill"],
        "unlock": { "mode": "PermanentProgression", "level": 1 },
        "conditions": [
          {
            "kind": "EntityCount",
            "scope": "region",
            "entitySource": "ScopeMembers",
            "count": 1,
            "tags": ["Hero.Strategist"]
          }
        ],
        "bindings": [
          { "ability": "Ability.RaiseElite", "gate": "show" }
        ]
      }
    ]
  }
]

position、title、分组和备注只属于 editor。compiler 校验它们，但不会把布局写进 runtime config。scope 仍然必须是 self、explicit、tree 的 scopes 声明，或 Progression/scopes.json 已声明过的 named scope。

生成结果的边界

生成文件放在 Configs

产物建议写到 assets/Configs/Progression/scopes.json、progressions.json、requirements.json，以及 catalog 已登记的 assets/Configs/GAS/effects.json / abilities.json。现有 ConfigPipeline 会按相同相对路径合并这些文件，不需要 runtime 新 loader。

作者文件和生成文件分开

作者编辑 Authoring；compiler 独占 Configs 下的 generated 文件。不要在保存树时偷偷改作者手写的 assets/GAS/abilities.json。

id 稳定且可预测

例如 Progression.Shu.CityMilitary.basic_drill、Req.Shu.CityMilitary.elite_training.Use、Effect.Shu.CityMilitary.elite_training.Complete。节点重排不改 id。

校验早于运行

compiler 要检查重复 id、环、未知 scope、未知 parent、未知 graph、binding 指向不存在的 ability，以及 PermanentProgression / ReversibleGate 是否混用错误。

作者需要理解的三个开关

树节点设置作者含义编译策略
unlock.mode: PermanentProgression这是真正被研究、奖励或升级写入的科技。生成 progression、前置 requirement、CompleteProgression effect；后续节点用 ProgressionCompleted / ProgressionLevelAtLeast 依赖它。
unlock.mode: ReversibleGate这不是科技状态，只是当前条件。不生成 progression，不生成 completion effect；只生成 requirement，条件消失后 gate 自动关闭。
bindings[].gate决定按钮是隐藏还是禁用。show 编译为 showRequirement；use 编译为 useRequirement。
树是作者体验，不是玩法开关：一个 feature 仍然应该是一个 mod、一个 showcase map。不要通过 map tag 隐式切换不同科技树，也不要让一张万能 showcase map 负责展示所有 feature。

更完整的 schema、CLI、Editor Bridge API 和验收规则见 树状科技树 Authoring Compiler 设计。

先选 Scope

作者最重要的决定不是“科技属于哪个 player”，而是“这个科技状态应该存在哪个实体上”。

不是硬编码：引擎只内置三种解析方式：self、explicit、named scope。city、faction、region、province 都只是作者在 Progression/scopes.json 里注册出来的 named scope，换成 kingdom、armyGroup、tradeRoute 也可以。
玩法需求推荐 scope科技状态放在哪里作者提示
建筑自己升级自己self建筑实体自己给建筑模板加 ProgressionStateBuffer: {}，不需要 hostKey。
一个城池控制城内建筑可造什么兵city城池 scope host城池是 host，兵营是 member，兵营绑定到该城池。
势力全局科技faction势力 scope host势力 host 可以是真实君主/主城，也可以是不可见数据实体。
区域内有某英雄才解锁region区域 scope host英雄和建筑都绑定到同一个 region；英雄 tag 可由模板、effect 或 runtime 授予。
省份、岛屿、战区共享科技province 或任意作者 key该区域的 scope host按玩法语言命名，不要拿 map tag 临时切功能。
升级效果由外部 UI 指定目标explicitTargetContext 指向的实体只有当调用方能明确传入目标 scope host 时使用。
经验法则：能用 named scope 就优先用 named scope。示例里用了 city、faction、region，项目里可以换成自己的领域词。explicit 很强，但作者必须保证 ability/effect 执行时真的带了 TargetContext。

一次性解锁 vs 可回退解锁

科技树里有两种完全不同的“解锁”。一种是研究完成后永久写入科技状态；另一种是当前世界状态满足时临时开放，不满足时自动收回。复杂条件可以调用现有 graph ops，但要先选对这两种模式。

模式作者意图怎么配会不会回退
一次性科技解锁研究完成、剧情授予、任务奖励、一次性升级CompleteProgression effect 写入 scope host；按钮用 ProgressionCompleted 或 ProgressionLevelAtLeast 检查不会。写入后就是该 scope 的科技状态。
可回退状态门槛英雄在场、建筑存活、区域被控制、buff 存在、关系当前满足不要写科技状态；直接把 EntityCount、TagAll 或 GraphValidation 挂到 ability 的 useRequirement/showRequirement会。条件消失后按钮会重新锁定或隐藏。
复杂可回退条件条件跨 tag、attribute、空间查询、关系、blackboard 等多个系统在 GAS/graphs.json 定义 validation graph，再在 requirement 里用 kind: "GraphValidation" 引用会。graph 每次评估都读取当前世界状态。
GraphValidation 可以用现有 graph ops：Progression Requirement 会把 actor 和解析后的 graphTarget 传给 GASGraph 的 validation 执行器。Graph 可以使用现有的 tag、attribute、空间查询、target list 聚合、relationship、blackboard 等 ops 来判断通过/拒绝。
GraphValidation 不负责写科技状态：它是“当前是否满足”的验证条件。需要永久写入“已研究/已升级”时，仍然用 CompleteProgression effect。

一次性解锁：研究完成后永久开放

// GAS/effects.json
[
  {
    "id": "Effect.CompleteCityDrill",
    "tags": ["Effect.Progression"],
    "presetType": "CompleteProgression",
    "lifetime": "Instant",
    "participatesInResponse": false,
    "progression": {
      "id": "Progression.City.Drill",
      "scope": "city",
      "level": 1
    }
  }
]

// Progression/requirements.json
[
  {
    "id": "Req.City.Drill.Done",
    "root": {
      "kind": "ProgressionCompleted",
      "progression": "Progression.City.Drill",
      "scope": "city",
      "entitySource": "ScopeHost"
    }
  }
]

可回退解锁：英雄在场才开放

// Progression/requirements.json
[
  {
    "id": "Req.Region.HasStrategist",
    "root": {
      "kind": "EntityCount",
      "scope": "region",
      "entitySource": "ScopeMembers",
      "count": 1,
      "tags": ["Hero.Strategist"]
    }
  }
]

// GAS/abilities.json
[
  {
    "id": "Ability.RegionStratagem",
    "useRequirement": "Req.Region.HasStrategist",
    "exec": { "clockId": "FixedFrame", "items": [{ "kind": "End", "tick": 0 }] },
    "presentation": { "displayName": "Regional Stratagem", "iconGlyph": "ST" }
  }
]

复杂可回退解锁：交给 graph 判断

// Progression/requirements.json
[
  {
    "id": "Req.Region.AdvancedControl",
    "root": {
      "kind": "GraphValidation",
      "scope": "region",
      "entitySource": "ScopeHost",
      "graph": "Graph.RequireRegionControl"
    }
  }
]

graph 具体节点写在 GAS/graphs.json。在 progression requirement 里，entitySource 决定 graph 的 target：可以是 ScopeHost、Actor、Subject，或者通过 scope 解析出的目标。graph 的 validation 输出通过/拒绝即可。

组合：一次性科技 + 可回退状态

很多 RTS/SLG 规则是“研究过科技，并且当前条件仍然满足”。这种不要把临时条件写进科技状态，用 All 组合即可。

// Progression/requirements.json
[
  {
    "id": "Req.EliteTraining.Use",
    "root": {
      "kind": "All",
      "children": [
        {
          "kind": "ProgressionCompleted",
          "progression": "Progression.City.EliteTraining",
          "scope": "city",
          "entitySource": "ScopeHost"
        },
        {
          "kind": "GraphValidation",
          "scope": "region",
          "entitySource": "ScopeHost",
          "graph": "Graph.RequireStableSupplyLine"
        }
      ]
    }
  }
]

常见配方

Case 1：城池科技解锁兵营训练

目标：长安城完成“练兵”科技后，长安兵营的“训练民兵”按钮可用。

1. 声明 city scope 和科技

// Progression/scopes.json
[
  { "id": "city" }
]

// Progression/progressions.json
[
  { "id": "Progression.City.Drill", "scope": "city" }
]

2. 城池做 host，兵营绑定到城池

// Entities/templates.json
{
  "id": "city_chang_an_scope",
  "components": {
    "Name": { "Value": "Chang An City Scope" },
    "ProgressionScopeHost": { "scope": "city", "hostKey": "chang_an" }
  }
}

{
  "id": "chang_an_barracks",
  "components": {
    "Name": { "Value": "Chang An Barracks" },
    "AbilityStateBuffer": { "abilityIds": ["Ability.TrainMilitia"] },
    "ProgressionScopeBinding": { "scope": "city", "hostKey": "chang_an" }
  }
}

3. 兵营按钮要求 city scope 已完成该科技

// Progression/requirements.json
[
  {
    "id": "Req.City.Drill.Done",
    "root": {
      "kind": "ProgressionCompleted",
      "progression": "Progression.City.Drill",
      "scope": "city",
      "entitySource": "ScopeHost"
    }
  }
]

// GAS/abilities.json
[
  {
    "id": "Ability.TrainMilitia",
    "useRequirement": "Req.City.Drill.Done",
    "exec": { "clockId": "FixedFrame", "items": [{ "kind": "End", "tick": 0 }] },
    "presentation": { "displayName": "Train Militia", "iconGlyph": "MI" }
  }
]

按钮会显示，但科技未完成时不可用。想完全隐藏按钮，把 useRequirement 改成 showRequirement。

Case 6：点击研究按钮完成科技

目标：研究完成时，把科技写到某个 scope host 上。这里演示 effect 片段，按钮或触发器如何发出 effect 由具体 feature 决定。

[
  {
    "id": "Effect.CompleteCityDrill",
    "tags": ["Effect.Progression"],
    "presetType": "CompleteProgression",

]

如果是“满足任意一个条件即可”，把 kind 从 All 改成 Any。如果要反向条件，用 Not 加一个 child。

字段速查

ProgressionScopeHost

写在保存科技状态的实体上。支持单项 { "scope": "...", "hostKey": "..." }，也支持 entries 数组。

ProgressionScopeBinding

写在要使用某个 scope 的实体上。一个建筑可以同时绑定多个作者声明的 named scope，例如 city、faction、region、province。

showRequirement

控制按钮是否出现。失败时玩家看不到该按钮。

useRequirement

控制按钮能否使用。失败时按钮可以显示，但不可用或执行失败。

避坑清单

  • 不要用 map tag 当 feature 开关。一个 feature 一个 mod，一个 showcase 一个 map；map tag 只表达地图分类。
  • 不要再建 player 科技表。科技状态应该落在 entity 上：城池、势力、区域、建筑本体都可以是实体。
  • 不要把示例 scope 当内置概念。city、faction、region、province 都来自配置声明，不是 C# 硬编码枚举。
  • 不要随手用 explicit。只有调用方能提供 TargetContext 时才用 explicit；否则优先使用 named scope。
  • hostKey 要稳定。city:chang_an、faction:shu 这类 key 是配置身份，不要因为显示名变化而改。
  • member 必须绑定到它要读取的 scope。兵营要读 city 科技，就要有 city binding；要读 faction 科技，就再加 faction binding。
  • 科技完成 effect 必须是 Instant。CompleteProgression 要配 lifetime: "Instant"，并显式写 participatesInResponse。
  • 多级升级用 level 或 delta，不要同时写。progression.level 和 progression.delta 互斥。
  • 复杂条件先看是否能组合。能用 All/Any/EntityCount/ProgressionLevelAtLeast 表达就不要上 graph；需要跨 tag、attribute、空间查询、关系或 blackboard 判断时再用 GraphValidation。
  • 一次性解锁和可回退门槛不要混写。研究完成、任务奖励用 CompleteProgression；英雄在场、建筑存活、区域控制这类当前状态用 requirement 或 GraphValidation。
