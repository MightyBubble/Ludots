OpenRA AI 分层架构剖面

这份报告把 OpenRA 的 skirmish AI 拆成从大厅配置到世界变更的完整剖面。 核心结论很锋利：AI 不拥有第二套玩法运行时，它只是正式命令链路的生产者。 经济、扩张、建造、分队和技能都被拆成玩家级模块，最后统一排队为 Order。

Architecture Thesis

OpenRA AI 的真面目：玩家级模块，命令级出口

OpenRA 的 AI 不是全局大脑，也不是统一行为树。它挂在 SystemActors.Player 上， 通过 ModularBot 调度一组 bot module。模块读世界、维护索引、做启发式判断， 但不会直接写 gameplay state。所有动作都要变成 Order，再进入和人类玩家相同的 World.IssueOrder、OrderManager、UnitOrders、 Actor.ResolveOrder 链路。

边界漂亮 AI 的输出是 Order，不是组件修改。同步、回放、校验都围绕命令流。
模块很实战 经济、建筑、生产、采矿、扩张、分队、支援技能各管一块。
策略靠数据调味 Rush、Normal、Turtle、Naval 主要通过 YAML condition 和参数组合出来。

完整命令剖面

如果把 OpenRA AI 想成一条流水线，它最像一个“参谋部”：参谋部只写命令，真正执行命令的是军队既有系统。 这条链路是理解它底层设计的主轴。

十层架构拆解

1大厅与 Bot Profile 层

这一层回答“玩家能选哪种 AI”。IBotInfo 提供 Type 与 Name， RA/CnC/D2k/TS 各自用 YAML 在 Player actor 上声明不同 ModularBot。

架构味道：AI 类型不是 C# 继承树，而是规则数据暴露出的 profile。

OpenRA.Game/Traits/TraitsInterfaces.cs mods/ra/rules/ai.yaml

2PlayerActor 激活层

Runtime Player 构造时读取 session 中的 bot type，只在 host 侧找到匹配的 IBot 并调用 Activate。其他客户端不跑 AI 决策，只接收 host 发出的 order。

架构味道：AI 内部启发式不进入同步模拟，减少 desync 风险。

OpenRA.Game/Player.cs CreateMapPlayers.cs

3ModularBot 调度层

ModularBot 收集 IBotTick、IBotRespondToAttack、 IBotEnabled 等模块接口。它像一个很薄的 bot kernel：tick 模块、缓存 order、分批发 order。

架构味道：调度器轻，策略厚度下沉到模块。

ModularBot.cs

4模块通信层

模块之间不共享一个巨大基类，而是通过小接口互相请求。例如采矿模块请求补矿车，基地建造模块要求暂停单位生产， 扩张模块通知新基地位置。

架构味道：这是轻量端口模型，代价是调用关系需要追源码。

OpenRA.Mods.Common/TraitsInterfaces.cs

5空间认知层

ResourceMapBotModule 把地图切成粗粒度资源区块，缓存资源中心、矿车、矿厂、敌军、敌方建筑、友方单位等信息。 它不像完整 blackboard，但已经承担了 AI 空间记忆的角色。

架构味道：低成本、分帧更新、为经济和扩张服务。

ResourceMapBotModule.cs

6战略经营层

基地建造、生产比例、采矿维护、MCV 部署和扩张评分都在这里。它们不是通用 planner， 而是大量 RTS 老经验：低电先电厂、钱少补矿厂、钱多补产能、建不下就扩张。

架构味道：启发式厚，但边界清楚，最后仍然只发 Order。

BaseBuilderBotModule.cs UnitBuilderBotModule.cs HarvesterBotModule.cs

7战术分队层

SquadManagerBotModule 把新单位归入空军、海军、突击、防御等 squad。每个 squad 用轻状态机处理 idle、attack、 flee，并用局部 fuzzy 判断该打还是撤。

架构味道：战术不是逐单位大脑，而是分队级状态机。

SquadManagerBotModule.cs Squads/Squad.cs AttackOrFleeFuzzy.cs

8技能与响应层

支援技能、维修、断电管理、占领、布雷等小能力都被拆成独立模块。许多模块是事件触发加周期扫描， 避免把所有判断塞进一个巨型 tick。

架构味道：能力型模块按玩法边界分拆，接入同一个 order 出口。

SupportPowerBotModule.cs BuildingRepairBotModule.cs CaptureManagerBotModule.cs

9Order 边界层

这是系统最硬的一层。AI 发出的 StartProduction、PlaceBuilding、 AttackMove、Harvest 等命令，与玩家 UI 命令同构。校验仍由正式订单链路处理。

架构味道：AI 没有暗门，作弊和合法性在 Order 侧统一看。

OpenRA.Game/World.cs UnitOrders.cs ValidateOrder.cs

10玩法执行层

最终改变世界的是 actor trait、activity、production queue、movement、support power 等正式系统。 AI 不复制这些能力，只是调用它们已经暴露出来的命令入口。

架构味道：复用既有 gameplay runtime，避免第二套隐形玩法系统。

OpenRA.Game/Actor.cs IResolveOrder interfaces

模块生态：一组老练的 RTS 小脑

OpenRA 的模块不是追求抽象优雅，而是追求在真实 RTS 对局里“活下来”。它们各自有缓存、延迟、阈值、比例和失败回退。

ResourceMap

维护资源区块、敌军、矿厂、矿车和基地分布，是经济与扩张的空间底图。

BaseBuilder

按电力、经济、产能、防御、海军需求决定建筑队列，并寻找合法放置位置。

UnitBuilder

按配置比例训练单位，支持单位上限、延迟和其他模块的指定生产请求。

Harvester

给 idle 矿车找资源，被攻击时回矿厂，矿车不足时请求补造。

MCV / Expansion

部署基地车、评分新资源点、选择扩张位置，必要时让基地搬家。

SquadManager

组织突击、防御、空军、海军 squad，用状态机和 fuzzy 判断打还是撤。

SupportPower

扫描候选区域，用 consideration 对目标打分，再发支援技能 order。

Repair / PowerDown

维修受损建筑，电力不足时关闭指定建筑，电力恢复后再逐步打开。

Capture / Minelayer

占领高价值目标，或根据冲突位置布雷，体现了能力模块的可插拔性。

配置性格：AI 风格来自组合，不来自子类

RA 的 rush、normal、turtle、naval， CnC 的 cabal、watson、hal9001，都是通过 YAML condition 激活模块和参数。 GrantConditionOnBotOwner 根据 bot type 授予 condition，模块再用 RequiresCondition 决定是否运行。

这意味着 C# 提供能力，YAML 调性格：建筑比例、单位比例、上限、延迟、攻击规模、扩张阈值、技能评分都能由数据层调整。

像调音台，而不是换发动机。 同一个 BaseBuilderBotModule 可以在 rush 里更激进，也可以在 turtle 里更防御。 模块是乐器，condition 和参数是混音台。

性能与回放：它知道 RTS AI 贵在哪里

策略 OpenRA 做法 价值
分帧扫描 ResourceMap 每次更新一个区块，SquadManager 把 pending update 摊到多个 tick。 避免全图扫描集中在同一帧。
索引缓存 ActorIndex 订阅 actor add/remove，常用集合不靠每帧临时搜。 降低查询成本，减少瞬时分配和过滤。
昂贵操作限流 采矿寻路、支援技能扫描、建筑放置都有 cooldown 或局部候选。 把寻路和目标评分从每 tick 暴力计算中拿出来。
Order 限流 ModularBot.MinOrderQuotientPerTick 控制 pending order 派发量。 防止 bot 瞬间刷爆命令链路。
回放分离 Bot 决策不在 replay 中重跑，回放只消费记录过的 order。 AI 内部状态无需成为回放确定性的唯一来源。

调试观察：能看到 AI 在想什么，但还不够结构化

OpenRA 有 AIUtils.BotDebug、Game.Settings.Debug.BotDebug、 RenderDebugState 等直接工具，可以把 squad 类型和目标画到单位上。这种可视化非常适合 RTS： 当一个小队发呆、撤退或乱冲，调试信息能马上告诉你它属于哪个 squad、目标是谁。

但 OpenRA 没有统一的结构化 decision trace。很多判断散落在模块内部的比例、阈值、随机扰动、cooldown 和特殊规则里。 它是很会打仗的工程系统，不是一本干净的 AI 教科书。

给 Ludots 的启发

AI snapshot/query -> AI module / planner produces command intent -> command proposal merge and cap -> formal OrderBuffer / GAS order validation -> existing gameplay systems mutate ECS state

最值得借鉴的不是具体模块代码，而是边界设计：AI 是命令生产者，正式玩法系统才是世界修改者。 如果 Ludots 做 RTS/战略 AI，应把 OpenRA 的经验翻译到自己的 Arch ECS、Mod、ConfigPipeline、SystemGroup 和 Order/GAS 管线里， 不应复制 GPL 代码，也不应让 AI 模块跨越职责直接写玩法组件。
