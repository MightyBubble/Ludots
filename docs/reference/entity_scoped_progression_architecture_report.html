Ludots Entity-Scoped Progression Tree 架构汇报

这套科技树/升级系统已经按“绑定实体而非绑定 player”的方向落地：科技状态存在于 scope host entity 上，建筑、英雄、区域、城池、势力都可以成为 scope host 或 scope member；Requirement 负责声明解锁条件，GAS effect 负责改变科技状态，UI 只消费显式的 show/use 语义。

结论

本 PR 新增的是一个通用的 entity-scoped progression runtime，而不是某个 RTS showcase 的私有逻辑。它可以表达“城池科技”“势力科技”“区域科技”“英雄在场解锁”“建筑本体升级”等不同作用域，且作用域必须由配置显式声明。

给内容作者：如果你要按玩法 case 配城池、势力、区域英雄、省份或建筑本体升级，先看 Entity-Scoped Progression Tree 作者配置指南。
Scope 语义不是硬编码：city、faction、region、province 是 showcase 通过 Progression/scopes.json 声明的 named scope。Core 只内置 self、explicit 和 named scope 解析。
Entity科技状态挂在实体上，不挂 player。
Scope作用域通过 self / explicit / named 解析。
GAS升级落地走 CompleteProgression effect。
UIshowRequirement 隐藏，useRequirement 锁定。
Showcase 原则：科技树 showcase 是独立 mod、独立 map、独立 Raylib preset。map tag 不承担“隐形 feature toggle”，只保留它原本应有的语义分类职责。

DDD 与架构边界

领域语言围绕 Progression、Requirement、ScopeHost、ScopeBinding 四个核心概念展开。Core 提供通用能力，showcase 只负责演示数据和验收路径。

ProgressionDefinition

声明科技 id 和默认 scope。科技本身不是 player 全局表，而是可以落到任何可解析的 scope host entity 上。

ProgressionStateBuffer

scope host 上的定长状态缓存，保存 progression id / level 和 revision。升级改变 revision，供 UI 和 requirement 缓存失效。

ProgressionRequirementDefinition

由节点数组和 child index 数组组成，表达 All / Any / Not / 技术等级 / 实体数量 / tag / graph validation。

ProgressionScopeHost

把实体声明为某个 scope 的宿主，例如 city:chang_an、faction:shu、region:jing、province:guanzhong。

ProgressionScopeBinding

把建筑、英雄或其他实体绑定到 scope host。Requirement 从 actor / subject 反查 named scope。

ProgressionRequirementEvaluator

唯一运行时判断入口，负责解析 scope、读取科技状态、扫描 scope members、执行 tag 和 graph 条件。

运行时数据流

1. ConfigMod 提供 Progression JSON，ConfigPipeline 合并后注册 id 和定义。
2. Spawn实体模板声明 scope host 或 scope binding，地图只摆放实体。
3. BindProgressionScopeBindingSystem 每帧解析 hostKey，把成员绑定到 host entity。
4. EvaluateAbility UI / GAS 执行用 ProgressionRequirementEvaluator 判断条件。
5. ApplyCompleteProgression effect 解析 scope host，并写入 ProgressionStateBuffer。
显式 scope：explicit 用于“玩家当前选中的城池/目标区域/外部上下文”。GAS 通过 EffectContext.TargetContext 传入，缺失时不会猜测。

核心数据模型

模型字段/枚举用途
ProgressionScopeSpecSelf、Explicit、Named(scopeKey)Requirement 和 effect 都用同一种 scope 描述。
ProgressionLevelChangelevel 或 delta支持直接完成、设置等级、增量升级。
ProgressionStateBuffer定长 64 个 progression slot避免运行时动态分配，适合 ECS 热路径。
ProgressionScopeRefBuffer定长 8 个 scope 引用一个实体可同时属于城池、势力、区域、省份等多个 scope。
ProgressionScopeMembershipRevisionRevision成员变化、tag 变化和科技状态变化会推动 UI 缓存失效。

Requirement 节点能力

设计参考 SC2 Mapster requirement 的 show/use 思路，但领域模型改成 Ludots 的 entity scope。Requirement 是数据驱动树，编译后是紧凑数组。

All / Any / Not

组合条件，用 child index 数组连接，不依赖运行时对象树。

ProgressionCompleted

要求某个科技在解析出来的 scope host 上 level 至少为 1。

ProgressionLevelAtLeast

要求指定科技达到给定 level，可表达多级升级链。

EntityCount

扫描 scope members，统计满足 tag 条件的实体数量。

TagAll

检查 actor、subject、scope host 或 scope members 是否具有全部 required tags。

GraphValidation

把复杂条件交给 condition func graph；适合地形、关系、资源等组合判断。

复杂条件建议：简单事实用 tag，科技/等级用 ProgressionStateBuffer，实体数量用 EntityCount；当条件需要跨多个领域聚合时再用 GraphValidation。
GraphValidation 语义：它调用现有 GASGraph validation runtime，读取当前世界状态并返回通过/拒绝。它不写科技状态；一次性研究完成仍由 CompleteProgression effect 写入 scope host。

怎么配置不同 feature

新增一个科技 feature 时，不需要改 map tag，也不需要写私有开关。按以下四步配置数据即可。

1. 声明 scope key

[
  { "id": "city" },
  { "id": "faction" },
  { "id": "region" },
  { "id": "province" }
]

2. 声明科技和默认 scope

[
  { "id": "Progression.Showcase.CityDrill", "scope": "city" },
  { "id": "Progression.Showcase.FactionMandate", "scope": "faction" },
  { "id": "Progression.Showcase.ProvinceLogistics", "scope": "province" }
]

3. 声明 requirement

{
  "id": "Req.Showcase.RegionStrategist.Use",
  "root": {
    "kind": "EntityCount",
    "scope": "region",
    "entitySource": "ScopeMembers",
    "count": 1,
    "tags": ["Hero.Showcase.Strategist"]
  }
}

4. 在 ability 或 effect 上引用

{
  "id": "Ability.Showcase.RegionStrategist",
  "useRequirement": "Req.Showcase.RegionStrategist.Use",
  "presentation": {
    "displayName": "Regional Stratagem",
    "iconGlyph": "ST"
  }
}
{
  "id": "Effect.Showcase.CompleteCityDrill",
  "presetType": "CompleteProgression",
  "progression": {
    "id": "Progression.Showcase.CityDrill",
    "scope": "explicit",
    "level": 1
  }
}
配置城池科技

城池实体声明 ProgressionScopeHost: { "scope": "city", "hostKey": "chang_an" }，兵营声明 ProgressionScopeBinding 绑定到同一个 city host。兵营造兵 requirement 读取 city scope。

配置势力科技

势力可以是一个不可见的 scope host entity，也可以是一个真实主城/君主实体。只要它拥有 ProgressionStateBuffer，全势力科技就能落在那里。

配置英雄解锁

英雄绑定到 region 或 city，并拥有 Hero.Showcase.Strategist 这类 tag。Requirement 用 EntityCount 检查同 scope 内是否有指定英雄。

配置区域/省份科技

声明 region、province 等 scope key，并把建筑、英雄、资源点绑定过去。Ability requirement 按 named scope 自动从 actor / subject 解析 host。

GAS / UI 语义

showRequirement

失败时按钮不出现。适合 SC2 风格“科技未发现前隐藏”的命令，例如势力政令、隐藏单位。

useRequirement

失败时按钮显示但不可用。适合让玩家看到目标，但明确还缺科技或英雄条件。

explicit scope deferred

当 requirement 需要 explicit scope，但 UI 预览阶段没有目标上下文时，状态是 deferred，不会被错误判死。

缓存策略：Command panel revision 会混入科技状态 revision、scope membership revision；包含 GraphValidation 的 requirement 还会混入 engine clock ticks，避免 graph 条件变化后 UI 旧缓存不刷新。

0alloc 与稳定性策略

点位策略
科技状态ProgressionStateBuffer 使用 fixed arrays，最多 64 项，升级不分配。
scope 引用ProgressionScopeRefBuffer 使用 fixed arrays，最多 8 个 scope 绑定。
Requirement 编译JSON 在加载期编译成节点数组和 child index 数组，运行期不构造对象树。
Scope host 收集ProgressionScopeBindingSystem 使用固定 host entry 缓冲，超过上限直接报错暴露配置问题。
UI 缓存失效revision hash 明确混入 scope、entity、tag、membership、progression state 和 graph clock。
