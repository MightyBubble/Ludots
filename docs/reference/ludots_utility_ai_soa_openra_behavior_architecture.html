Ludots 通用 Utility AI SoA 架构方案

目标不是再写一个局部 Bot，而是把现有 Utility / GOAP / HTN 雏形深化成一套通用 AI Module： SoA 热路径、0Alloc 运行、配置驱动 OpenRA 基础单位行为、Order 与 Ability 分离、Decision 与 Execution 分离、评分机制数据驱动、Graph 函数可扩展。

结论 远端与本地已有 AI 骨架，但没有覆盖 Uintel 式完整 AI 基建。应复用现有 AI / Order / GAS / Graph / Team / Spatial 基建，补齐目标过滤、感知、decision-target pair 评分、执行器、姿态、索敌、执行前置条件和 OpenRA 行为包。

1. 直接回答

远端 PR 有没有已经处理类似 Uintel 的 AI 基建？

没有发现一个已经覆盖“完整通用 Utility AI / SoA runtime / decision-target pair / 数据化评分 / OpenRA 基础行为”的远端 PR。 但远端 `origin/main` 和当前本地已经有 AI 骨架：`UtilityGoalSelectorCompiled256`、`GoapAStarPlanner256`、`HtnPlanner256`、`AIPlanExecutionSystem`、`AiConfigLoader`、`AIDemoMod`、`AIInspectorMod`。

现有 AI 基建有没有这块内容？

有一半：已经有 goal 级 utility、256-bit world state、GOAP/HTN plan、plan 到 `OrderQueue` 的提交、10k agent 0Alloc benchmark。 没有另一半：没有通用 target filter、没有 decision-target pair 评分、没有输入归一化与曲线库、没有 OpenRA 式 stance / auto-target / attack-move / guard / disengage / 执行器就绪门控，也没有发现 AI 系统已接进 `GameEngine` 主循环。

推荐方向

不要另起一套平行 AI。应把 `src/Core/Gameplay/AI` 深化成一个深 Module：配置编译为只读数组，运行时用 SoA runtime 和固定 scratch，decision 只产出 intent，execution 只提交 Order，Ability 和 Effect 仍由 GAS 负责。

复用 现有 AI / Order / GAS / Graph / Spatial / Team / Relationship / Navigation2D。
新增 Perception、TargetFilter、Input、Normalization、Consideration、Decision、Executor、Stance、CombatMemory、ActuatorReadiness。
原则 AI 不直接扣血、不生成 Effect、不绕过 Order 校验；所有战斗执行仍走 Order 和 GAS。

3. Uintel 文档拆解

Uintel ECS 文档的关键不是 Unity DOTS 细节，而是清晰的职责链：感知输入、归一化、consideration、decision、decision maker、action task。运行时再拆成决策阶段和执行阶段。

Input读取 agent、target、环境、blackboard，输出 raw input。
Normalization把 raw input 归一到 0..1。
Considerationinput + normalization + response curve。
Decision一组 considerations + target filters + action tasks。
DecisionMaker在 decision-target pair 中选最高分。
State Machine控制当前 decision 切换，处理 momentum。
ActionTaskSequence / Parallel / ParallelComplete 执行。

最值得复刻的思想

Uintel 思路 对 Ludots 的价值 不能照搬的部分
Decision-making 与 execution 分离 可以保证 scoring 是纯读，execution 才提交 Order，符合 Ludots Order/GAS 职责。 不要把 Unity job/executor 类型原样搬进 Ludots。
Decision-target pair 评分 非常适合索敌、守卫、攻击、修理、采集、运输等“动作和目标一起选”的 RTS 行为。 不能只做 goal 级评分，否则无法表达“打谁”。
Target filter 前置裁剪 先用关系、layer、tag、距离、视野、武器资格过滤，避免对全场实体跑评分。 不要用 managed LINQ / 临时 List 做热路径筛选。
Blob + runtime executor 对应 Ludots 的 compiled arrays + SoA runtime：配置只读，执行状态独立。 不照搬 Unity BlobAssetReference / Baker / SubScene。
Blackboard Ludots 已有黑板 buffer，可承载 Order 参数、感知记忆、target cache。 不要新增平行黑板协议；要复用现有 blackboard key registry。
Optimization tricks 决策间隔、跨帧分摊、target filter、并行/分桶、固定内存池都适合 Ludots。 “启用 Burst”这类 Unity 专属项不能照搬。
和 Ludots 规范冲突的一点

Uintel 文档里提到 fallback decision / idle fallback 的设计。在 Ludots 里不应做平台级 fallback。Idle、Hold、ReturnFire 都应是显式配置的 decision 或 order state；配置缺失时 fail-fast，而不是运行时兜底。

4. 当前缺口

现有 Ludots AI 的 Interface 还偏窄：它能“选 goal、做 plan、提交 order”，但还不能表达“对哪个目标、为什么此时切换、怎么持续执行、什么时候脱战、执行器当前是否满足开火/施法前置条件”。

缺口 当前表现 需要补的 Module
目标候选与过滤 Input mapping 有 `AutoTargetPolicy`，GAS TargetResolver 有 fan-out，但没有 AI 通用无副作用 target filter。 AITargetFilterCompiled、AITargetAcquisitionSystem。
decision-target pair Utility 只选 goal，不选目标。 AIDecisionEvaluator、AITargetCandidateSoA、AIDecisionIntent。
输入归一化和曲线 目前是 bool consideration，无法表达距离曲线、血量曲线、威胁分、优先级桶。 AIInputProviderRegistry、AINormalizationCompiled、AIResponseCurveCompiled。
执行持续性 Plan action 提交 Order 后就 advance，缺少 action task 的 running / finished / cancel 语义。 AIExecutionStateSoA、AITaskExecutor。
OpenRA 基础行为 Order blackboard 已有 Attack/Move/Stop/Hold/Patrol key，但缺 attack-move、guard、stance、retaliate、auto-target runtime。 OpenRaBehaviorPack 配置和 executor adapters。
脱战/警戒/索敌 没有通用 target memory、last seen、leash、scan interval、target priority。 AICombatMemory、AIStanceProfile、AIAutoTargetProfile。
执行器就绪门控 攻击、施法、采集、建造、炮台转向都可能有“正在准备但尚不能执行”的 gameplay 状态；目前 AI 没有统一读取这类 readiness 的入口。 ActuatorReadinessInput、AimGate、AbilityPreconditionAdapter；炮台只是一个 adapter 案例。
主循环接入 `AiRuntime` 会加载，但当前搜索未发现 AI systems 注册到 `GameEngine` simulation loop。 AI bootstrap / SystemFactory / SystemGroup 排布。

5. 目标架构

目标是一个深 Module：外部 Interface 是“给 agent 配 AI profile，系统自动产出 Order intent”；内部 Implementation 才包含 perception、filters、inputs、scoring、task executor、OpenRA 行为包。

Authoring Layer
Mod 配置：AI profile、filters、inputs、curves、decisions、tasks、stance、actuator readiness adapters。
Compile Layer
ConfigPipeline 合并后编译为 id、array、range、programId；热路径不保留 string。
Decision Layer
target candidates、raw inputs、normalization、consideration、decision-target pair score。
Execution Layer
Sequence / Parallel task executor，输出 Order intent，不直接触发 Effect。
Gameplay Layer
OrderBufferSystem、AbilityExecSystem、EffectProcessing、ProjectileRuntimeSystem 执行实际 gameplay。
Interface
`AIAgentProfileRef` + `AICompiledRuntime` + `AIOrderIntentQueue`。调用方只知道配置和 Order，不知道内部评分细节。
Seam
Input provider、normalization、curve、target filter、task executor、order adapter、graph score adapter。
Adapter
`OrderTaskAdapter`、`AbilityCastOrderAdapter`、`MoveOrderAdapter`、`GraphConsiderationAdapter`、`RelationshipThreatInputAdapter`。
Depth
一个配置 profile 覆盖 idle auto-target、attack move、guard、patrol、retaliate、execution readiness、ability cast。

Module 切分

Module Interface Implementation 要点
AIConfigCompiler 输入 `ConfigCatalog`，输出 `AICompiledRuntime`。 解析 AI/*.json，注册 ids，编译 flat arrays 和 range tables，校验所有引用。
AIAgentRuntimeSoA 按 agent index 读取/写入状态。 profileId、lastDecisionId、currentTarget、thinkBucket、cooldown、score、executor pc。
AITargetAcquisition 给 decision maker 返回候选目标 span。 spatial query + target filter + target cache + last seen；不产生 gameplay side effect。
AIInputSampling 按 inputId 读取 raw value。 距离、生命、tag、attribute、cooldown、threat、actuator readiness、order state、graph score。
AIUtilityEvaluator 输出 best decision-target pair。 normalization、curve、veto、multiply、weighted sum、priority bucket、momentum、hysteresis。
AIDecisionStateMachine 控制是否切换 current decision。 keep running、min duration、cooldown、interrupt policy、score margin。
AIExecution 把 decision intent 转为 running tasks。 Sequence / Parallel / ParallelComplete；任务只提交 Order intent 或维护 AI runtime state。
AIOrderAdapter 把 task intent 转为 `Order`。 填 Actor、Target、TargetContext、Spatial、Args、SubmitMode，交给 `OrderQueue`。
OpenRaBehaviorPack 一套可选配置 profile。 Move、Stop、Attack、AttackMove、Guard、Patrol、Hold、Stance、AutoTarget；炮台/采集器/建造器等放到对应 actuator adapter。

6. SoA / 0Alloc 运行时

现有 `UtilityGoalSelectorCompiled256` 已经是数组化思路。新系统要把这个思路推到全链路：配置只读数组，运行状态 SoA，scratch 固定容量，Update 内不分配。

核心数据布局

  DecisionMakerRanges[]          // offset + count into DecisionIds
  DecisionIds[]
  DecisionTargetFilterId[]
  DecisionConsiderationRanges[]  // offset + count into Considerations
  DecisionTaskRanges[]           // offset + count into Tasks
  ConsiderationInputId[]
  ConsiderationNormalizationId[]
  ConsiderationCurveId[]
  ConsiderationWeight[]
  ConsiderationFlags[]           // Veto, Targeted, Graph, Invert
  TargetFilterOps[]
  InputDefs[]
  NormalizationDefs[]
  CurveDefs[]
  TaskDefs[]
  OrderAdapterDefs[]
  GraphProgramIds[]
AIAgentRuntimeSoA
  Entity[] Agents
  int[] ProfileId
  int[] DecisionMakerCursor
  int[] CurrentDecisionId
  Entity[] CurrentTarget

0Alloc 规则

  • 配置加载阶段可以用 `List` 和 JSON object；编译完成后热路径只读 arrays / spans。
  • Update 内禁止 LINQ、`new List<>`、闭包、字符串查找、反射、字典枚举。
  • 所有 string id 在 compile 阶段变成 int id；运行时只比较 int / bitset / enum。
  • 目标候选使用固定 `Entity[]` 或 `Span` scratch，容量来自 profile，例如 `maxCandidates=64`。
  • Top target 选择使用单 pass best 或小容量 insertion sort，不做全量排序。
  • Graph score 用 stackalloc registers；AI 侧 Graph adapter 禁止 effect write op，只允许 pure read / math / query / relationship read。
  • 多 agent 分桶：`NextThinkStep` 和 `DecisionMakingFrame1..N` 类似 Uintel 的跨帧分摊，避免所有 agent 同帧评分。
  • 结构变化集中到 CommandBuffer 或 OrderQueue；decision 阶段不 Add/Remove ECS 数据。
  • QueryDescription 静态缓存；空间查询 buffer 由 system 持有并复用。

热路径伪代码

for each agent in think bucket:
  candidates = targetAcquisition.Collect(agent, profile, scratch)
  bestScore = 0
  bestDecision = None
  bestTarget = Null

  for each decisionMaker in profile:
    for each decision in decisionMaker:
      span = FilterTargets(decision.targetFilter, candidates)
      for each target in span or NullTarget:
        score = EvaluateDecision(agent, target, decision)
        score = ApplyMomentumHysteresis(agent, decision, target, score)
        if score > bestScore:
          best = decision-target pair

  stateMachine.TrySwitch(agent, best)
  executor.Tick(agent, currentDecision, currentTarget)

7. 评分与 Graph

Ludots 需要的不是单一乘法公式，而是一套数据驱动 score graph。默认足够快，必要时允许 Graph 函数参与单个 input / consideration / decision score。

评分结构

Target Filter
关系、layer、tag、距离、视野、weapon eligibility、是否可被攻击、是否可被 repair/capture/harvest。
Input
raw value：distanceCm、healthRatio、threat、cooldownElapsed、ammoRatio、readiness01、aimDelta、orderState、blackboard value。
Normalization
linear、inverse、range、threshold、comparison、cooldown、piecewise、graph。
Curve
constant、linear、quadratic、logistic、step、remap table、graph。
Aggregation
veto、multiply、weighted sum、min gate、max bonus、priority bucket、tie nearest。

OpenRA 优先级如何表达

OpenRA 的 `AutoTargetPriority` 先按 priority 选更高优先级，再用距离做 tie-break。Ludots 不应把这写死在 attack move 里，而应作为 target scoring profile： 

{
  "id": "TargetScore.OpenRA.Ground",
  "mode": "PriorityBucketThenDistance",
  "buckets": [
    { "tag": "TargetType.Defense", "relationship": "Hostile", "priority": 60 },
    { "tag": "TargetType.Vehicle", "relationship": "Hostile", "priority": 50 },
    { "tag": "TargetType.Infantry", "relationship": "Hostile", "priority": 40 }
  ],
  "tieBreak": "Nearest"
}

Graph 扩展点

现有 `GraphExecutor.ExecuteScore` 返回 `F[0]`，`ExecuteValidation` 返回 `B[0]`，并使用 stackalloc registers。这正好可以成为 AI scoring 的 Adapter，但需要加一层 `AIGraphRuntimeApi` 或 `AIGraphOpPolicy`。

Graph 用途 允许 禁止
Input score 读 attribute、tag、relationship、blackboard、position、distance、target list。 ApplyEffect、ModifyAttribute、WriteBlackboard、SendEvent。
Target filter 返回 `B[0]` 判断候选是否保留。 创建实体、发 effect、提交 order。
Decision score 返回 `F[0]` 作为最终补正分。 改变 gameplay state。
Task condition 判断 running / finished / cancel。 绕过 `OrderQueue` 直接执行 ability。

8. Order / Ability 映射

AI 的执行层只能表达 intent，不能拥有伤害和技能执行权。真正的 gameplay 变化仍由 Order、Ability、Effect、Projectile 链路完成。

Decision选中 AttackTarget / Move / Guard / Repair。
Execution把 decision 展开成 task。
Order Adapter写 Actor / Target / Spatial / Args。
OrderQueue进入玩家同构订单入口。
OrderBufferSystem打断、排队、黑板写入。
AbilityExec按 ability spec 执行 timeline。
Effect应用伤害、buff、projectile。

Order 和 Ability 的切分

问题 归 Order 归 Ability/GAS
我要去哪里 `moveTo`、`attackMove`、`guardFollow` 写空间目标或跟随目标。 不负责寻路。
我要打谁 `attack` order 写 `Attack.TargetEntity`。 校验 range、cooldown、ammo、actuator readiness、发射 projectile。
我要用哪个技能 `castAbility` order 写 slot/abilityId/target/position。 Ability timeline、effect request、target resolver、cost、block tags。
我要保护谁 `guard` order 写 guarded entity 和 follow range。 保护行为选出的攻击动作仍走 attack/cast ability。
我要停下 `stop` order 清 active/queue 和 AI execution state。 取消能力实例由 existing stop/ability end 系统处理。
当前一个配置契约风险

`mods/AIDemoMod/assets/Configs/AI/goap_actions.json` 中样例写了 `OrderTagId`，但 `AiConfigLoader` 读取的是 `OrderTypeId`。这说明现有 AI demo 只能当雏形，正式方案必须先统一 AI action 到 OrderTypeRegistry 的配置契约，并做 fail-fast 校验。

9. OpenRA 行为配置包

OpenRA 基础行为的核心不是“攻击移动写死”，而是命令薄、行为编排薄、索敌策略数据化、攻击执行交给 attack trait。映射到 Ludots，就是 order 薄、AI task 薄、target/score 数据化、攻击执行交给 Ability/GAS。

用户看到的输入动作 AI/Order 语义 Ludots 配置实现
右键地面 / Move 移动到目标点，不主动扫描攻击。 `Task.SubmitOrder(moveTo)`，写 `Generic.TargetPosition` 或 movement spatial key。
右键敌人 / Attack 锁定目标，必要时跟进，进入攻击距离后 cast attack ability。 `Decision.AttackTarget` + `Task.ChaseUntilInRange` + `Task.CastAbility(PrimaryWeapon)`。
Attack Move 向目的地移动，途中按 auto-target 策略找敌；遇敌暂停移动，攻击结束后继续目的地。 `Task.Composite.AttackMove`: move subtask + scan subtask + interrupt/resume state。
Assault Move 类似 Attack Move，但允许更积极追击。 同一 task，profile 设置 `allowMoveChase=true`、`maxLeashCm` 更大。
Guard 跟随友军或建筑，扫描威胁并攻击，超出 guard range 回到保护目标。 `Decision.GuardProtect` 使用 guarded target、nearby hostile、attacker memory。
Stop 停止当前活动，清理攻击/移动子活动。 `stop` order + `AIExecution.CancelCurrent` + 清 target memory optional。
Hold Position 不主动移动，可按姿态还击或开火。 `AIStanceProfile.HoldPosition` + `allowMove=false` + attack range gate。
Stance 切换 HoldFire / ReturnFire / Defend / AttackAnything。 `AIStanceState` + `SetStance` order 或 tag effect，影响 target filter 和 allowMove。
Patrol 沿 waypoint 往返，途中可按 auto-target 策略接战。 `Task.PatrolMove` + `Decision.AutoAttackWhileMoving`。
Deploy / Repair / Capture / Harvest / Transport 本质是不同 target filter + ability/order task。 作为 OpenRA behavior pack 的可选 decisions，不写入 AI core 特例。

Attack Move task 状态

Moving
维持目的地 order 或 NavGoal；按 scan interval 扫描候选。
Acquire
通过 target filter + priority profile 选择目标；若无目标继续 Moving。
Engage
暂停移动；提交 attack / castAbility order；跟踪 target validity。
Disengage
目标死亡、失效、超出 leash、不可见、无法攻击、攻击 order 完成。
Resume
回到原 attack-move 目的地；如果刚脱战可立即再扫一次，避免空走。

10. 执行器就绪门控

这里不能把“炮台”升格为 AI Core 概念。通用架构只需要表达：某个执行器当前是否 ready、为什么不 ready、预计何时 ready、是否需要先执行准备动作。OpenRA 的炮台只是这个抽象下的一个案例。

抽象 Module Core 语义 炮台案例如何挂接
ActuatorProfile 描述一个可执行能力的准备条件：范围、冷却、资源、弹药、朝向、通道、占用、目标合法性。 TurretProfile 是 weapon actuator 的配置扩展，不属于 AI Core。
ActuatorReadiness 运行时只暴露 ready01、blockReason、etaSteps、requiresPreparation。 炮台 adapter 把 yaw delta、turn speed、facing tolerance 转成 readiness。
AimGate 面向所有需要方向/朝向的执行器：炮台、正面攻击、蓄力技能、采集朝向、施工朝向。 TurretFacingSystem 是 AimGate 的一个 gameplay implementation。
AbilityPrecondition 最终执行门控仍归 Ability/GAS；AI 只能读取 readiness 或提交准备/执行 order。 攻击 ability 在炮台未对准时阻塞、等待或进入准备阶段。
Presentation Adapter 表现读取 gameplay state，不参与 AI 决策合同。 炮管转向和 recoil 从 turret runtime 投影到表现层。
边界结论

AI Core 不认识炮台，只认识执行器 readiness。炮台、正面开火、采集器朝向、建造者占用、施法蓄力都通过 adapter 映射到同一个 readiness 输入。这样业务语义留在能力 Mod / gameplay implementation 里，架构只保留可复用的执行前置条件。

11. SystemGroup 排布

AI 必须在 `OrderBufferSystem` 前产出 order，才能同 tick 进入现有 Order/GAS 链路。感知又应在空间索引更新之后运行，避免用上一帧位置做索敌。

SystemGroup AI 系统 原因
SchemaUpdate `AIConfigReloadApplySystem` 可选 只处理配置版本切换和 runtime swap，不做决策。
InputCollection `AIThinkScheduleSystem`、低成本 blackboard projection 读取输入、cooldown、order state，确定本 tick 哪些 agent 要思考。
PostMovement `AIPerceptionSystem`、`AITargetAcquisitionSystem`、`AIDecisionSystem`、`AIExecutionSystem`、`AIOrderIntentSubmitSystem` 在 `WorldToGridSyncSystem` / `SpatialPartitionUpdateSystem` 后、`OrderBufferSystem` 前运行，使用最新空间索引，并让 order 同 tick 生效。
AbilityActivation 不新增 AI 决策；必要时用 `InsertSystemBeforeRequired<OrderBufferSystem>` 放置 order submit adapter 避免错过 OrderBufferSystem；AI 不应插在 AbilityExec 后面。
EffectProcessing 无 AI 决策 Effect / projectile 已经是执行结果，AI 不在这里反向改决策。
Cleanup `AICombatMemoryCleanupSystem` 清理死亡 target、过期 last-seen、过期 threat cache。

14. 验收标准

这套系统是否成立，不看 demo 演得像不像，看这些测试能否稳定通过。

验收项 必须证明
0Alloc 10k agent 在 fixed iterations 中 `AIPerception + Decision + Execution + OrderSubmit` allocation 小于等于现有 AI benchmark 级别。
OpenRA priority 高 priority target 永远胜过低 priority target；同 priority 下最近者胜出。
Stance HoldFire 不索敌不还击；ReturnFire 只打 recent attacker；Defend 扫描但不追出 leash；AttackAnything 可追击。
AttackMove 移动途中遇敌暂停、攻击 order 完成后恢复原目的地；目标死亡/失效/超 leash 正确脱战。
Guard 跟随保护目标；保护目标附近有 hostile 或 recent attacker 时攻击；离开 guard range 后回位。
Order/GAS 同构 AI 和玩家使用同一 `OrderQueue`、`OrderBufferSystem`、`AbilityExecSystem`；AI 不能直接发 EffectRequest。
Graph score 自定义 Graph 可影响 score；AI Graph policy 拒绝 effect write / attribute write / event op。
Actuator readiness gate 执行器未 ready 时 ability 被阻塞、等待或先准备；ready 后同一 target 能执行；表现读取 gameplay state。
主循环接入 AI systems 在 `SpatialPartitionUpdateSystem` 后、`OrderBufferSystem` 前运行；同 tick order 可被消费。
配置 fail-fast 未知 input、filter、order type、ability id、graph id、blackboard key 均在加载阶段报错。
不该做的实现

不在某个 showcase 里硬写 AttackMove；不让 AI 直接扣血或发 Effect；不新增平行配置加载器；不把 Idle 做成平台 fallback；不把 Unity DOTS/Burst/BlobAssetReference 当成 Ludots 架构；不把炮台、采集器、建造者这类业务名词写进 AI Core。
