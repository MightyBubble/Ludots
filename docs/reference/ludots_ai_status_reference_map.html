Ludots AI 现状、困境与参考地图

这是一个上层总览文档，不再讲单点实现，而是把现状、问题、取舍和所有相关分析文档串成一张图。 目标是让后续任何 AI 架构决策先看到已知事实，再看还没定下来的地方。

当前结论 AI 骨架已存在，缺的是通用化的 target / score / readiness / execution 分层。业务语义要留在 behavior pack 和 adapter 里，别把炮台、采集器、建造者写进 AI Core。

1. 现状快照

这部分已经可以算“总结到位”，但不是最终定论。当前最重要的事实是：Ludots 不是没 AI，而是已有一条骨架链路，缺一个能承载 OpenRA 基础行为和 Uintel 式 decision-target 评分的通用 AI Module。

已经有的 Utility / GOAP / HTN 编译结构、256-bit world state、AI plan 到 OrderQueue、AI demo 配置、benchmark。
还缺的 通用 target filter、input/normalization/curve、decision-target pair、combat memory、stance policy、readiness gate、主循环接入。
不能做的 不能让 AI 直接发 Effect 或扣血，不能把业务名词写进 AI Core，不能用 fallback 代替显式决策。

3. 困境与问题

这些不是实现 bug，而是架构取舍点。它们决定这套 AI 会不会变成一堆局部特化，还是一个能长期复用的深 Module。

AI Core vs 业务能力
核心必须抽象，业务能力要沉到 behavior pack / adapter。炮台、采集器、建造者都不该进 Core。
stance 放哪
stance 是战斗政策状态，不是行为树，也不是 utility 本体；它更像 target filter 的输入和 order/AI state。
Graph 作用边界
Graph 适合做 score / validation / read-only query，不适合当执行总线，更不能绕过 Order/GAS。
Order vs Ability
Order 是 intent，Ability 是执行。AI 只产出 intent，不负责伤害、特效和投射物。
OpenRA 行为包
AttackMove / Guard / Stance / AutoTarget 应该作为行为包提供，不作为 AI Core 特例。
主循环接入
AiRuntime 已能加载，但还没看到它进入主 simulation loop；这意味着“有配置”不等于“有运行”。

4. 取舍方向

这里给的是我目前的判断，不是死规矩。后续如果要改，也应该是改这张表，而不是让单个系统偷偷长歪。

取舍点 建议方向 原因
stance 放在 AI state / target policy / order 语义里 它是交战规则，不是具体执行动作。
炮台 放在 actuator / readiness adapter 里 炮台是一个业务案例，不应变成 AI Core 的通用词表。
utility 负责评分，不负责执行 utility 选谁去做，不替代 task / FSM / Ability。
Graph 用于可自定义 score / condition 图适合扩展规则，不适合接管副作用。
行为包 OpenRA 基础行为做成可配置 pack Move / Guard / AttackMove / Stance 等要能被别的 mod 复用。
fallback 不用平台 fallback，改成显式决策 缺省行为会把问题藏起来，和当前规范冲突。
目前最容易混进去的业务语义

炮台、采集器、建造者、正面攻击、蓄力施法这些词都很具体。它们应该留在业务能力层，AI Core 只保留更通用的词：ActuatorReadiness、AimGate、ExecutionPrecondition、TargetFilter、DecisionIntent。
