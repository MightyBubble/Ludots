Ludots 通用 Utility AI 与 Autocast 仲裁 SSOT 方案

把 Uintel 的 Utility AI 架构思路完整复刻进 Ludots，并把 OpenRA 一整套 stance / 基础 order 作为业务语义行为包实现。核心命题：普通攻击就是一种 autocast 能力；当多个 autocast 争抢共享 GCD / mana / 施法槽时，仲裁器就是 Utility AI 的决策入口。

SSOT 结论 反应式行为(attack-move/hold/stop/autocast/普攻)是机制层，由 policy 数据驱动；Utility AI 坐在其上，只产 Order intent。两者共享 target-acquisition/filter 底座与 Order 词汇表，唯一区别是最终选择函数：优先级排序(机制) vs 加权打分(utility)。

1. 核心命题与三层模型

人们口中的"AI"其实混了三层。把它们分清，attack-move / hold / stop / approach / 自动施法 的归属就一目了然。

层回答的问题谁需要它本方案归属
Intent（意图 / Order）"我被命令做什么"玩家与 AI 都发统一 OrderQueue 入口
Behavior / 机制（执行）"怎么把命令执行出来"谁控制单位都要，纯人操也要OpenRA 行为包 + GAS（policy 数据驱动）
Deliberation（Utility AI）"在多个有价值选项里此刻选哪个"只有"有脑子"的一方需要Utility AI Core（只产 intent）

命题 A：普通攻击就是一种 autocast 能力

不再有"攻击系统"和"技能系统"两套东西。单位会做的一切反应式行为 = 一个带 autocast policy 的 ability。普攻只是其中优先级最低、前置最宽松、会自动重复的候选——"没有更值得做的事时占用动作槽的默认项"。于是 attack-move 的 engage 步骤，本质就是"普攻这个候选赢得了动作槽"。

命题 B：一条可操作的判定规则

判断任何行为该放哪层，问一句："选哪个"能不能写成确定性的全序策略？

能 → 机制 / policy"最高优先级桶取最近"、"最近的敌人"、"血量最低的友军"。放进 behavior pack，用共享 target-acquisition + filter + priority 基建，不需要 utility 评分。
不能 → Utility 决策需要把"远但残血但威胁高、而且大招好了"这类软因素互相权衡。放进 Utility AI Core。
共享底座两者用同一套候选获取 + filter；区别只在最终选择函数：priority-sort vs weighted-score。

逐项归类

行为归属理由
Stop纯机制（Order）清执行状态，没有任何"选择"。
Hold机制（stance 标志）allowMove=false + auto-target 门控，是约束不是判断。
Approach / 追到射程纯机制attack 执行的子状态(chase-until-in-range)，leash 是 policy 数据。
Attack-Move机制状态机 + auto-target policy移动是机制；"途中遇敌打哪个"是确定性 AutoTargetPriority，不是 utility。
单个 / 互不冲突的 autocast机制（反应式触发）各放各的，谁都不挡谁（如被动光环 + 普攻）。
多个 autocast 抢共享 GCD/mana需要仲裁器 → Utility 入口见第 2 节。
不违反 no-fallback

普攻作为"最低优先级显式候选"不是平台兜底，而是配置里显式声明的默认 decision。候选池为空就什么都不放（显式），不是运行时偷偷兜底。Idle / HoldFire / ReturnFire 都是显式配置的 stance / decision，缺配置时 fail-fast。

2. 多能力仲裁 = Utility 决策入口

这是机制层与 Utility AI 边界真正发生迁移的点。一旦多个 autocast 争抢共享资源，就不能再各放各的，必须有人"选"，而"选"就是评分。

场景：法师（加血 + 诅咒 + CC + 普攻，共享 GCD）

四个能力都是 autocast 候选。共享 GCD 意味着这一窗口最多放一个，因此"放哪个、对谁"是一个带约束的选择问题。每个决策窗口收集候选：

candidate(ability, target) 进入池的条件:
  (autocast 开关开) 且 (有合法目标 via 自身 target filter)
  且 (个体 cooldown 就绪) 且 (mana 可负担) 且 (GCD 就绪)
  且 (precondition graph 通过)

同一条流水线，两种仲裁器（只换最终选择函数）

仲裁方式选择函数归属类比
固定优先级 / 简单条件priority list / if-else 链机制（便宜、确定性、好默认）War3 autocast 实际做法
价值 vs 成本加权打分argmax(score)Utility AI真正"有脑子"
 
// 便宜版（机制 / 优先级表）
if   友军 HP<50% 且 heal 就绪   -> cast Heal  on 最低血友军
elif 敌人正在读条 且 CC 就绪      -> cast CC    on 那个敌人
elif 敌对在射程 且 curse 就绪     -> cast Curse on 最高价值敌人
else                            -> 普攻 on auto-target policy 选中目标

// 升级版（utility）：同一候选池，给每个 (ability,target) 打分，argmax
//   heal 分 ~ 友军缺血 × 该友军是否会死
//   CC   分 ~ 打断的是否致命技能
//   curse分 ~ 目标价值
//   普攻 = 基线分
// 换的只是 else-if 链 -> argmax(score)，流水线一字不改

GCD / mana / 冷却不是独立系统，是仲裁器的 veto/gate 输入

约束形状映射到现有 GAS 原语
个体冷却该能力可用性门AbilityCooldown { CooldownValueAttributeId, CooldownTagId }
公共 CD（GCD）互斥 / 单槽：选中者消耗，本窗口其余 GCD 能力全 veto共享 cooldown tag（复用 CooldownTagId + AbilityActivationBlockTags）
mana / 资源预算门：先按可负担过滤候选ability cost + AbilityActivationPrecondition.ValidationGraphId
执行器就绪（朝向/弹药等）readiness 门新增 ActuatorReadiness（见第 5 节），炮台为 adapter 案例
边界要点
  • 多个 autocast 同时生效 ≠ 同时释放：开关都开只是都进候选池；不抢资源的可真并行，抢 GCD/mana 的是互斥候选集，一窗口选一个。
  • 玩家/AI 显式命令优先级最高、抢占 autocast：显式 Order 抢占本窗口仲裁，autocast 只在空闲/自动时填槽（与 War3 一致）。
  • 性能：不要每帧重新仲裁。普攻作为默认赢家由执行层 auto-repeat；仲裁器只在决策间隔或中断事件（目标死、友军掉阈值、大招转好）时重选。对应 think bucket + keepRunning + interrupt policy。
结论

单个 autocast 是机制；多个 autocast 抢共享 GCD/mana 的那一刻，就需要一个仲裁器，而这个仲裁器就是 Utility AI 的 decision-target 评分机缩到"我自己的能力"上。便宜的优先级表与完整 utility 打分是同一条流水线的两个选择函数。

3. Uintel 架构忠实复刻

复刻的是 Uintel 的职责链与数据形状，不是 Unity DOTS 细节。完整链路：感知输入 → 归一化 → consideration → decision → decision maker → state machine → action task；运行时拆成决策阶段与执行阶段。

Input读 agent/target/环境/blackboard，输出 raw input。
Normalizationraw input 归一到 0..1。
Considerationinput + normalization + response curve。
Decisionconsiderations + target filter + action tasks。
DecisionMaker在 decision-target pair 中选最高分（= 仲裁器）。
StateMachine控制 decision 切换，处理 momentum/hysteresis。
ActionTaskSequence / Parallel / ParallelComplete 执行。

Module 切分（Interface / Implementation）

ModuleInterfaceImplementation 要点
AIConfigCompiler输入 ConfigCatalog，输出 AICompiledRuntime解析 AI/*.json，注册 ids，编译 flat arrays / range tables，所有引用 fail-fast。
AIAgentRuntimeSoA按 agent index 读写状态profileId、currentDecisionId、currentTarget、thinkBucket、score、executor pc、combatMemory。
AITargetAcquisition返回候选目标 spanspatial query + target filter + target cache + last-seen，无副作用。
AIInputSampling按 inputId 读 raw value距离、生命、tag、attribute、cooldown、threat、actuator readiness、order state、graph score。
AIUtilityEvaluator输出 best decision-target pairnormalization、curve、veto、multiply、weighted sum、priority bucket、momentum、hysteresis。
AIDecisionStateMachine是否切换 current decisionkeep running、min duration、cooldown、interrupt policy、score margin。

  • 配置加载阶段可用 List/JSON；编译后热路径只读 arrays / spans。
  • Update 内禁止 LINQ / new List / 闭包 / 字符串查找 / 反射；所有 string id 在 compile 阶段变 int。
  • 候选用固定容量 Span<Entity> scratch（maxCandidates 来自 profile）；top 选择用单 pass best 或小容量插入排序。
  • Graph score 用 stackalloc registers；AI 侧 Graph adapter 只允许 pure read / math / query / relationship read，禁 effect/attribute/event write。
  • 多 agent 分桶（NextThinkStep）跨帧分摊；结构变化集中到 CommandBuffer / OrderQueue。
与 Ludots 规范冲突的一点

Uintel 的 fallback decision / idle fallback 不照搬。Idle / Hold / ReturnFire 都是显式配置的 decision 或 order state；配置缺失时 fail-fast，不运行时兜底。Unity Burst / BlobAssetReference / Baker / SubScene 等专属项不照搬。

4. OpenRA Stance / Order 业务包

OpenRA 基础行为的核心：命令薄、行为编排薄、索敌策略数据化、攻击执行交给 attack trait。映射到 Ludots = order 薄、AI task 薄、target/score 数据化、攻击执行交给 Ability/GAS。这些作为可复用 behavior pack mod交付，不写进 AI Core。OpenRA 的关键原则："索敌是单位能力，不是 bot 特权"——人类、AI、脚本单位都复用同一套。

Stop / Scatter停止 / 短距避让复用 StopOrderSystem；Stop 必须清 current target、guard anchor、attackMove runtime、turret aim desire。
Attack / ForceAttack锁定目标，进射程后攻击attack order 写 Attack.TargetEntity；ForceAttack 允许地面/友军强攻。

5. 分层与 SSOT 边界

SSOT 的关键是每个概念只有一个归属层。最容易出错的是把业务名词写进 AI Core。

Authoring Layer（Mod 配置）
AI profile、target filters、inputs、curves、decisions、tasks、stances、actuator readiness adapters、autocast policy。
Compile Layer
ConfigPipeline 合并后编译为 id / array / range / programId；热路径不保留 string；全引用 fail-fast。
Decision Layer（AI Core）
target candidates、raw inputs、normalization、consideration、decision-target pair score、仲裁、state machine。只认通用词。
Execution Layer（AI Core）
Sequence/Parallel task executor，输出 Order intent，不直接触发 Effect。
Gameplay Layer（GAS / 行为包）
OrderBufferSystem、AbilityExecSystem、EffectProcessing、ProjectileRuntime、Turret/Stance/AttackMove runtime 执行实际 gameplay。

什么进 Core、什么进 behavior pack、什么归 GAS

概念归属理由
TargetFilter / DecisionIntent / ActuatorReadiness / AimGate / ExecutionPreconditionAI Core 通用词跨题材可复用，无业务语义。
Stance（HoldFire/ReturnFire/Defend/AttackAnything）behavior pack（OpenRA 包）+ AI state交战政策状态，不是 AI 本体；影响 target filter 与 allowMove。
AttackMove / Guard / Patrol / AutoTarget profilebehavior pack作为可配置行为包，别的 mod 可复用，不作 AI Core 特例。
炮台 / 采集器 / 建造者 / 蓄力施法actuator adapter（gameplay 能力 mod）业务案例。AI Core 只认 readiness，不认炮台。
伤害 / buff / projectile / cost / cooldown / block tagGAS执行权归 GAS，AI 只读 readiness、只提交 Order。

炮台只是 readiness 的一个 adapter 案例

抽象 Module（Core）Core 语义炮台案例如何挂接
ActuatorReadiness只暴露 ready01 / blockReason / etaSteps / requiresPreparationTurretState(yaw/turnSpeed/readyCheck/muzzle) adapter 把 yaw delta 转成 readiness。
AimGate面向所有需要朝向的执行器TurretFacingSystem 是它的一个 gameplay implementation。
AbilityPrecondition最终执行门控归 GAS炮台未对准时攻击 ability 阻塞/等待/进入准备。
不该做的实现

不在某 showcase 里硬写 AttackMove；不让 AI 直接扣血或发 Effect；不新增平行配置加载器；不把 Idle 做成平台 fallback；不把 Unity DOTS/Burst/BlobAssetReference 当 Ludots 架构；不把炮台/采集器/建造者写进 AI Core。

6. SystemGroup 排布

AI 必须在 OrderBufferSystem 前产出 order 才能同 tick 进入现有 Order/GAS 链路；感知必须在空间索引更新之后运行，避免用上一帧位置索敌。

SystemGroupAI 系统原因
SchemaUpdateAIConfigReloadApplySystem（可选）只处理配置版本切换与 runtime swap。
InputCollectionAIThinkScheduleSystem + 低成本 blackboard projection确定本 tick 哪些 agent 思考（think bucket）。
PostMovementAIPerceptionSystem → AITargetAcquisitionSystem → AIDecisionSystem（含 autocast 仲裁）→ AIExecutionSystem → AIOrderIntentSubmitSystem在 SpatialPartitionUpdateSystem 后、OrderBufferSystem 前，用最新索引且让 order 同 tick 生效。
CleanupAICombatMemoryCleanupSystem清死亡 target、过期 last-seen / threat cache。

一个 Epic + 10 个分阶段 sub-issue。每个 sub-issue 对应本文档一节，有明确 Interface 契约和 0Alloc / fail-fast 验收。开发由下属 agent 执行，方案与审计由架构侧负责。

8. 验收标准

系统是否成立不看 demo 演得像不像，看这些测试能否稳定通过。

验收项必须证明
0Alloc10k agent 在 fixed iterations 中 Perception+Decision+Execution+OrderSubmit 分配 ≤ 现有 AI benchmark 级别。
Autocast 仲裁多 autocast 抢共享 GCD 时一窗口只放一个；选中者消耗 GCD/mana 后其余被 veto；优先级表与 utility 打分两种模式都可配。
普攻=能力普攻作为最低优先级候选，无更优候选时 auto-repeat；被更高价值候选抢占时让出动作槽。
显式抢占玩家/AI 显式 order 抢占本窗口 autocast；autocast 只在空闲/自动时填槽。
OpenRA priority高 priority target 永远胜过低 priority；同 priority 下最近者胜。
StanceHoldFire 不索敌不还击；ReturnFire 只打 recent attacker；Defend 扫描但不追出 leash；AttackAnything 可追击。
AttackMove移动途中遇敌暂停、攻击 order 完成后恢复原目的地；目标死亡/失效/超 leash 正确脱战。
Guard跟随保护目标；附近有 hostile/recent attacker 时攻击；离开 guard range 后回位。
Order/GAS 同构AI 与玩家用同一 OrderQueue/OrderBufferSystem/AbilityExecSystem；AI 不能直接发 EffectRequest。
Graph score policy自定义 Graph 可影响 score；AI Graph policy 拒绝 effect/attribute/event write。
Actuator readiness gate执行器未 ready 时 ability 被阻塞/等待/先准备；ready 后同 target 能执行；表现读 gameplay state。
主循环接入AI systems 在 SpatialPartitionUpdateSystem 后、OrderBufferSystem 前运行；同 tick order 可被消费。
配置 fail-fast未知 input/filter/order type/ability id/graph id/blackboard key/cooldown tag 均在加载阶段报错。
