树状科技树 Authoring Compiler 设计

这份设计回答一个作者体验问题：mod 作者能不能像编辑科技树一样拖节点、连前置、选作用域，然后自动得到 Ludots 现在需要的 Progression、Requirement、Ability 和 Effect 配置。答案是可以，但这应该是 authoring 层，不是新的 runtime 科技系统。

Authoring source Deterministic compiler 复用 Progression/GAS/Graph 不进 runtime hot path
结论 作者流程 Schema 编译映射 编辑器 校验 UAT

结论

新增一层 ProgressionAuthoring，让作者编辑树状文件；新增 compiler，把树转成现有 runtime 配置。runtime 不认识“树编辑器”、节点坐标、分组、备注，也不新增 player 科技表。

作者文件
  • assets/Authoring/Progression/trees.json
  • 节点、连线、位置、分组、scope、条件、按钮绑定
  • 只给编辑器和 compiler 读取
Compiler
  • ludots progression compile，拟新增
  • Editor Bridge 调同一个 compiler
  • 校验、排序、生成、写入 report
运行时配置
  • assets/Configs/Progression/scopes.json
  • assets/Configs/Progression/progressions.json
  • assets/Configs/Progression/requirements.json
  • assets/Configs/GAS/effects.json
  • assets/Configs/GAS/abilities.json
  • 仅限 config_catalog.json 已登记的相对路径
为什么产物放 assets/Configs：ConfigPipeline 对同一个相对路径会读取 mod 的 assets/<path> 和 assets/Configs/<path>。所以 generated 文件可以挂到正式合并链路，不需要给 Progression 建平行 loader。

作者流程

1. 新建科技树选择默认 scope，例如 city、faction、self。scope 名字仍然来自配置声明。
2. 拖节点节点有标题、稳定 id、图标、描述、等级和编辑器坐标。
3. 连前置父节点连到子节点，compiler 自动生成 ProgressionCompleted 或 ProgressionLevelAtLeast。
4. 加条件简单条件用 tag/entity count；复杂条件引用现有 graph validation。
5. 生成配置保存时生成 runtime JSON 和 validation report，作者不手改 generated 文件。
作者看到的概念对应运行时概念备注
科技节点ProgressionConfig只有永久科技节点生成 progression。
前置线ProgressionCompleted / ProgressionLevelAtLeast父节点 id 编译为稳定 progression id。
门槛节点EntityCount / TagAll / GraphValidation门槛是当前状态，不写科技状态。
研究完成CompleteProgression effect走 GAS Effect Pipeline，不让 UI 直接写 state。
按钮隐藏/禁用showRequirement / useRequirement与 SC2 Requirement 的 Show/Use 语义对齐。

Authoring Schema

schema 要保持作者友好，但字段必须能确定性落到现有 runtime 配置。UI 可读字段和 runtime 语义字段分开，避免布局泄漏进 runtime。

字段约定

字段归属规则
id作者身份稳定，不随标题和位置变化。用于生成 deterministic id。
displayName、title、description编辑器/UI可以参与生成 presentation，但不参与 runtime 判断。
position、group编辑器布局只保留在 authoring source，不写入 Progression/*.json。
scopes作者声明tree 会用到的 named scope。compiler 可以据此生成 Progression/scopes.json，或校验它们已在手写配置中存在。
defaultScope、scope运行时语义必须是 self、explicit、tree 的 scopes 声明，或已存在的 named scope。
parents前置关系只允许引用同一 tree 内节点；compiler 做环检测。
conditionsRequirement直接映射到现有 requirement node，复杂条件引用 graph id。
bindingsAbility gate只声明绑定意图；是否覆盖已有 ability 必须显式配置。

Compiler 映射

compiler 是薄而确定的转换层。它不引入新领域判断，不在 runtime 热路径分配对象，也不替代 ProgressionRequirementEvaluator。

拟新增命令入口

dotnet run --project src/Tools/Ludots.Tool/Ludots.Tool.csproj -- \
  progression compile \
  --modPath mods/showcases/progression_scope/ProgressionScopeShowcaseMod \
  --input assets/Authoring/Progression/trees.json \
  --out assets/Configs \
  --writeReport

生成文件

输出内容合并方式
Progression/scopes.jsontree 显式声明的 named scopes。项目可选择由 compiler 生成，或要求作者提前声明后只校验。ArrayById
Progression/progressions.jsonPermanentProgression 节点对应的 progression。ArrayById
Progression/requirements.json父节点、conditions、按钮 gate 的组合 requirement。ArrayById
GAS/effects.json研究完成节点对应的 CompleteProgression effect。ArrayById
GAS/abilities.json可选。只在作者显式允许 generated ability overlay 时写。ArrayById
Authoring/Progression/compile_report.json校验结果、生成 id、未绑定项、冲突列表。不进 runtime

稳定 id 策略

Progression:  Progression.<idPrefix>.<nodeId>
Use req:     Req.<idPrefix>.<nodeId>.Use
Show req:    Req.<idPrefix>.<nodeId>.Show
Done req:    Req.<idPrefix>.<nodeId>.Done
Effect:      Effect.<idPrefix>.<nodeId>.Complete
不要偷偷 patch 手写文件：如果 ability 已存在，默认只生成 binding plan 和 report。只有作者在 tree 里显式设置 "emitAbilityOverlay": true，compiler 才写 generated GAS/abilities.json 片段。

PermanentProgression 与 ReversibleGate

模式生成 progression生成 CompleteProgression可作为父节点会回退
PermanentProgression是可选，默认生成是否
ReversibleGate否否可作为 requirement 片段，不作为 progression parent是

Editor 设计

Editor React 负责作者体验，Editor Bridge 负责文件读写和调用 compiler。两者共享 authoring schema，不直接调用 runtime registry。

React 视图

新增 Progression Tree 面板：左侧树列表，中间节点画布，右侧属性 inspector。节点支持拖拽、连线、复制、禁用、搜索和错误定位。

拟新增 Bridge API

GET /api/mods/{modId}/progression/trees 读取 authoring source；PUT 保存；POST /compile 调 compiler 并返回 report。这些是本设计建议新增的 endpoint，不是当前已存在的 Bridge API。

Compiler 共享

CLI 和 Bridge 调同一套 compiler 类型，避免一个命令行版本、一个编辑器版本。

图条件入口

复杂条件只引用 graph id。编辑器可以显示 graph 选择器，但不在科技树面板里重做 graph 编辑器。

清晰职责：React 管交互；Bridge 管 repo/mod 路径和文件；compiler 管 schema 到 runtime JSON；runtime 管合并、registry、evaluation 和 effect apply。

校验规则

校验要在保存和 compile 时给作者明确反馈。错误应该定位到 tree、node、field，而不是等 runtime 启动后抛 registry 异常。

级别规则示例
错误重复 tree id 或 node idTree.Shu.CityMilitary/basic_drill 出现两次。
错误前置环A 需要 B，B 又需要 A。
错误未知 scopescope: city 未在 tree 的 scopes 或 Progression/scopes.json 声明。
错误未知 graphGraph.RequireRegionControl 不存在或未编译。
错误binding 指向未知 abilityAbility.RaiseElite 不在合并后的 ability 配置里。
警告generated id 与手写 id 冲突作者手写了同名 Req.*。
警告ReversibleGate 被当作永久父科技应该改成 conditions，不要生成 progression state。
提示节点没有 binding可能是剧情奖励科技，也可能是漏配按钮。
禁止隐式 scope：compiler 不应该根据 title 猜 city、faction、region。scope 使用点可以继承 tree 默认值，但 named scope 的定义必须来自 tree 的 scopes 或已声明 config。

UAT 与实现顺序

先做可验证的竖切，再做完整编辑体验。第一版不需要万能 showcase，也不需要 map tag 开关。

实现顺序

阶段交付验收
1. Compiler coreDTO、validator、deterministic emitter、unit tests输入 authoring tree，输出三类 Progression JSON 和 GAS effect JSON。
2. CLI新增 progression compile 命令showcase mod 可一键重新生成配置，diff 稳定。
3. Editor Bridge读取、保存、compile API保存后返回 compile report，错误可定位到节点。
4. React 面板树列表、节点画布、属性 inspector、错误定位作者不用手写 requirement 就能配置常见前置。
5. Showcase独立 mod、独立 map城池科技、势力科技、英雄在场 gate、graph validation 各自可验收。

0alloc 口径

authoring compiler 和 editor 可以正常分配，因为它们不在 runtime hot path。0alloc 约束放在 runtime evaluator、scope binding、effect application 这类每帧或高频路径。compiler 产物仍然进入现有 registry 和 compact requirement node 数组。

验收 case

  • 树上连 basic_drill -> elite_training，生成 ProgressionCompleted 前置。
  • 节点条件选择 EntityCount + Hero.Strategist，英雄离开后按钮重新锁定。
  • 节点条件选择 GraphValidation，graph 改判定后无需改科技 runtime。
  • 同一 tree 重排节点位置，生成 runtime JSON 没有无意义 diff。
  • 删除一个节点，compiler 明确报告受影响的 child、ability binding 和 effect。
