# Launcher SSOT and User-First Endgame

This document defines the Ludots launcher endgame contract for `SSOT` and user-first product behavior.
It complements existing startup and mod architecture docs by specifying one authority model across selection, build, runtime bootstrap, and service wiring.

## 1. Product Principle

Ludots keeps one product truth:

- users operate on content intent: mod, dependency, capability, preset, adapter
- the launcher owns implementation details: project graph, assembly layout, bootstrap artifacts, runtime service wiring

No other entrypoint may own a parallel runtime dependency truth.

## 2. Launcher Graph as Current SSOT Step

The current launcher authority step is a graph artifact generated from selector intent.
When bootstrap metadata links to that graph, runtime consumes the ordered launcher plan directly and validates it in-place instead of re-resolving dependencies from `ModPaths`.
This repository does not yet ship a separate lock file, so documentation must not imply that lock semantics already exist.

Required graph payload:

- schema version and graph fingerprint
- selected adapter descriptor id
- root selectors, resolved root mods, ordered dependency closure
- `orderedModIds`
- `plannedMods[].id`
- `plannedMods[].rootPath`
- plan metadata required for bootstrap integrity checks
- runtime bootstrap strategy and paths
- diagnostics and conflict decisions used for the plan

Evidence paths for current launcher planning model:

- `src/Tools/Ludots.Launcher.Backend/LauncherModels.cs`
- `src/Tools/Ludots.Launcher.Backend/LauncherService.cs`
- `docs/architecture/startup_entrypoints.md`

Current implementation note:

- runtime currently consumes graph order + root paths + plan metadata
- graph still carries richer planning information for launcher/build UX
- lock-level assembly/hash freezing remains a future step

Future lock scope:

- freeze manifest hashes and external dependency identities
- freeze shared assembly policy and capability contract versions
- freeze SDK/export inputs required for cross-machine reproduction

## 2.1 User Entry Contract

Default users should only need two product entrypoints:

- visual launcher: `.\scripts\run-mod-launcher.cmd`
- CLI launcher: `.\scripts\run-mod-launcher.cmd cli ...`

For the visual path, the canonical browser document is:

- `http://localhost:5299/launcher/index.html`

Compatibility redirects may exist, but docs and scripts should point at one canonical URL so screenshots, support instructions, and automation all share one truth.

## 3. Configuration Layering Contract

Configuration ownership is split into four layers with non-overlapping responsibilities.

### 3.1 Project Configuration (shared, committed)

- `launcher.config.json`
- `launcher.presets.json`

Contains workspace roots, bindings, adapter defaults, and reusable launch presets.

### 3.2 User Preferences (local, non-authoritative)

- `%AppData%/Ludots/Launcher/preferences.json`
- `%AppData%/Ludots/Launcher/config.overlay.json`

Contains user-local defaults and convenience overlays.
Preferences never change mod resolution truth.

Evidence path:

- `src/Tools/Ludots.Launcher.Backend/LauncherConfigService.cs`

### 3.3 Runtime Bootstrap (generated artifact)

- `launcher.runtime.json` (current runtime bootstrap input)
- launcher graph artifact (current plan authority and evidence file)
- future lock artifact (stronger cross-environment freeze, not implemented yet)

Bootstrap artifacts are generated by launcher execution and are not user-authored source of truth.
Product bootstrap must point to a launcher graph; runtime no longer treats `ModPaths` as a product fallback.

### 3.4 Content Configuration (gameplay semantics)

- `assets/Configs/game.json`
- `<Mod>/assets/game.json`
- `<Mod>/assets/Configs/game.json`

Gameplay configuration remains under `ConfigPipeline` merge semantics and is separate from launch orchestration.

## 4. Adapter Descriptor Contract

Adapters are modeled as descriptors, not only hardcoded app project paths.

An adapter descriptor defines:

- `adapterId`
- host kind (raylib, web, unity, godot, unreal, external-host)
- build pipeline contract
- runtime bootstrap schema
- required shared contract groups
- integration pack entrypoints

This allows external game hosts to onboard incrementally without creating a second truth for gameplay dependency resolution.

## 5. Typed Service Scope Contract

`CoreServiceKeys` remains the stable typed key catalog.
The endgame runtime container is an explicit typed service graph with scopes:

- `EngineScope`
- `SessionScope`
- `MapScope`
- `AdapterScope`

Rules:

- feature and adapter code should consume typed service keys
- string-key context access is compatibility-only and should be retired
- service requirements should be validated at startup/builder time through typed keys, not discovered ad-hoc in runtime loops

Current migration note:

- direct-debug/test APIs may still pass explicit mod paths or transient string payloads
- product startup, adapter bootstrap, and mod initialization should no longer introduce new string-key dependencies

Runtime assembly policy:

- one launch plan maps to one `ModLoadContext`
- dependent mods inside the same plan share one type universe
- cross-mod capability services should not rely on parallel per-mod load contexts

Evidence paths:

- `src/Core/Scripting/CoreServiceKeys.cs`
- `src/Core/Scripting/ServiceKey.cs`
- `src/Core/Scripting/ScriptContext.cs`
- `src/Core/Engine/GameEngine.cs`
- `src/Core/Modding/ModLoader.cs`
- `src/Core/Modding/ModLoadContext.cs`

## 6. User Experience Profiles

### 6.1 Players

Players choose presets, adapters, and launch targets.
They should not need to read or edit `csproj`, project references, or bootstrap file internals.

### 6.2 Non-coding creators / AI vibe coding creators

Creators should focus on `mod.json`, content assets, and lightweight source files.
Launcher should generate and maintain dependency/build/runtime artifacts.

### 6.3 Professional creators

Professional users may inspect implementation-level build nodes and project hints.
Those details remain advanced-mode concerns, not default product UX.

## 7. Migration Guardrails

1. Keep launcher as the only product launch contract.
2. Keep runtime bootstrap artifacts generated, not manually curated.
3. Keep gameplay config under `ConfigPipeline`.
4. Keep adapter integration inside descriptor + capability contracts, not cross-coupled project references.
5. Keep typed service keys and move runtime access toward explicit scopes.
6. Do not describe lock behavior as shipped until a distinct lock contract exists in code.
