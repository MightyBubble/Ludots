# 设计决策规则

Ludots 设计宪法的决策规则——动手设计时按这些来。**通用，不绑定具体子系统。**

## 1. 从第一性原理出发

- 用一个最朴素的场景问"这里到底需要什么"，不要从现有代码/现有概念出发。
- 例：问"旁观者切到别人，能拿到他的状态吗"→ 推导出"交互状态必须挂实体（世界实体状态，谁都能读）"。不从"现有代码怎么存"出发，从"最朴素场景必须成立"出发。

## 2. 概念能拆就拆、各归其位

- 如果一个概念混了两个域，拆开，各管各的。
- 判断：这个概念里有没有两个不同的域（状态 vs 投影、获取 vs 结果、身份 vs 视角）被塞进一个词？拆。
- 命名要表达"它产出/代表什么"，不要用一个误导的名字（"获取目标" vs "获取操作对象"）。

## 3. 复用现成基建

- 先看仓库已有什么（graph / presenter / context / collection / registry / pipeline），设计挂靠点。
- **别被现有代码带跑**：复用基建 ≠ 照抄现有代码的结构。定宪法时以设计为准，不因为现有代码有没有就标注"提议/真实字段"。
- 判断：新设计是"挂靠现有基建"还是"另造一套"？后者违反。

## 4. 砍多余的配置

- 问"这个配置能从已有配置推导吗"——能就砍。
- 判断：一个配置文件/字段，是"必要的声明"还是"已有配置的重复"？重复就砍。少一个文件 = 少一个 SSOT。

## 5. 作者体验要简单

- 初始化时扫描编译好配置，作者一行声明（订阅/挂载/启用），其余基建自动做。
- 判断：作者写一个功能要几步？超过"一行声明 + 基建自动做"就太复杂。

## 6. 先跑通一个 case

- 不要一次铺开所有 case。先挑一个做完整全流程（从源头到效果，每步标"层 + 配置 + 数据流"），确认结构对，再复制。
- 判断：设计是"先一个 case 验证"还是"一次全铺"？后者容易结构错了才发现。

## 7. 命名要准、避免暗示误导

- 命名不能暗示错误的语义。
- 判断：这个名字会不会让读者以为"有两种东西"（其实是隐含前提）？会不会让读者误解"它产出什么"？

## 8. 配置结构要真实

- 字段、类型、示例都要真实，不臆想字段名。
- 但**不是照抄现有代码**：定宪法时按设计推字段，不因为现有代码没有就标注"提议"。authoring 形状就是宪法本身。
