# 架构理念

Ludots 设计宪法背后的架构理念，逐条展开。**通用原则，不绑定任何具体子系统。** 每条都可迁移到 GAS、UI、网络、输入等任何子系统。

## 1. SSOT 唯一

- 同一概念只在一个地方定义。配置、文档、代码标识符不许有两套真相。
- **推导优于声明**：如果某信息能从已有配置推导（如"哪些 X 要处理"从"有 Y 监听它"推导），就不要单独一个配置去重复声明。少一个文件 = 少一个 SSOT。
- 判断：一个配置是"必要的声明"还是"可推导的重复"？可推导就砍。

## 2. 禁 fallback / 静默回退

- 读不到、配置缺失、非法引用 → fail-fast，明确报错。不悄悄换一条路、不静默回退到默认。
- 判断：某个缺失场景是"明确失败"还是"悄悄换默认"？后者违反。

## 3. 禁重复造轮子

- 已有基建（graph / presenter / context / collection / registry / pipeline）能承载的，设计挂靠点，不另起平行体系。
- 判断：新设计是"复用现有基建 + 挂靠"还是"另造一套平行机制"？后者违反。

## 4. 分层而非并列

- 一个系统里，**覆盖/偏好必然基于某个基础**——改某个基础配置（覆盖）的前提是有一张基础表；偏好某个状态（偏好）的前提是当前在该状态。它们引用它们作用的基础。
- **不把"原值"和"补丁"并列成同一层**（如并列成"元组/轴"）。覆盖/偏好是"作用在基础之上的修饰层"。
- 判断：某个概念是"基础"还是"作用在基础之上的覆盖/偏好"？如果它必然引用另一个概念才能成立，它是修饰层，不是并列层。

## 5. 结构保证优于纪律

- 该由结构保证的不变量（清理、纯函数、对称性、边界），不能靠"作者记得做"。
- 用结构保证：容器（进入建、退出自动清）、编译期校验（纯函数内不得访问世界状态）、生命周期绑定（子随父）。
- 判断：某个不变量是"结构保证"还是"作者记得"？后者会变成活 bug。

## 6. "机制是代码、内容是配置"

- **机制**（谁做、怎么触发、怎么管理生命周期）是基建代码。
- **内容**（做什么、激活哪个、配什么值）是配置。
- **authoring 形状明确**：作者在哪个配置里写什么，是宪法的一部分，不是代码硬编码、也不是让作者猜。
- 判断：设计里"谁做"和"做什么"分清楚了吗？authoring 形状（作者写什么、写哪）明确吗？

## 7. 最小契约

- 跨边界的契约（事件、接口、消息）只带**最小、必要**的信息，不掺该由接收方自己推导/计算的语义。
- 判断：某个事件/接口带的东西，是"必需的事实"还是"接收方该自己算的"？后者违反。
