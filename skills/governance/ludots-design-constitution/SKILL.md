# Ludots 设计宪法

这份 skill 是 Ludots 的**设计宪法**——定义"给 Ludots 设计新系统、写设计文档"时必须遵守的**通用**原则。它沉淀自 owner 的多轮设计迭代（以输入与指令系统为案例），但**原则本身不绑定任何具体子系统**——GAS、UI、网络、输入，都适用。

**适用**：设计新子系统、写设计文档、迭代配置结构、评审设计是否符合 Ludots 原则。

---

## 0. 先读

1. `references/architecture-principles.md` —— 架构理念（SSOT、禁 fallback、复用基建、分层、结构保证优于纪律、机制是代码/内容是配置）。
2. `references/design-decision-rules.md` —— 设计决策规则（第一性原理、概念切开、砍多余配置、作者体验简单、先跑通一个 case、命名准确）。
3. `references/doc-discipline.md` —— 文档纪律 + 反模式清单（面向新人、真实配置结构、此地无银/壮胆文学/假设上下文）。

> 具体子系统的展开（如输入系统的 bot 等价、exec/data 分离）**不属于宪法主体**——它们是宪法在某子系统的应用示例，放子系统自己的文档，不进 skill。

---

## 1. 设计决策工作流

写任何设计前，按顺序过一遍：

1. **从第一性原理出发**——用一个最朴素的场景问"这里到底需要什么"，不要从现有代码/现有概念出发。
2. **概念能拆就拆、各归其位**——如果一个概念混了两个域（状态 vs 投影、获取 vs 结果），拆开，各管各的。
3. **复用现成基建**——先看仓库已有什么（graph、presenter、context、collection、registry），设计挂靠点，不重复造轮子。
4. **砍多余的配置**——少一个配置文件 = 少一个 SSOT。问"这个配置能从已有配置推导吗"，能就砍。
5. **作者体验要简单**——初始化时扫描编译好，作者一行声明（订阅/挂载/启用），其余基建自动做。
6. **先跑通一个 case**——不要一次铺开，先挑一个做完整全流程，确认结构对，再复制。

## 2. 架构红线（违反即返工）

- **SSOT 唯一**：同一概念只在一个地方定义；配置/文档/代码标识符不许有两套真相。
- **禁 fallback / 静默回退**：读不到就 fail-fast，不悄悄换一条路。
- **禁重复造轮子**：已有基建能承载的，不另起平行体系。
- **分层而非并列**：覆盖/偏好必然基于某个基础（覆盖基于基础配置、偏好基于基础状态），不把"原值"和"补丁"并列成同一层。
- **结构保证优于纪律**：该由结构保证的不变量（清理、纯函数、对称性）不能靠"作者记得做"——用结构（容器、编译期校验）保证。
- **"机制是代码、内容是配置"**：谁做（机制）是基建代码，做什么（内容）是配置。authoring 形状明确，不是代码硬编码。

## 3. 文档纪律

- **面向新人、说人话、不假设背景**——读者不需要参与过讨论就能读懂。
- **术语首现定义**——每个术语第一次出现给一句白话。
- **配置结构要真实**——字段、类型、示例；不臆想字段名。
- **一个用例一份文档**——用例文档聚焦一个场景，做完整链路。
- 反模式清单见 `references/doc-discipline.md`。

## 4. 评审时的自检

设计写完/评审前，问：
1. 有没有概念混了两个域没拆开？
2. 有没有多余的配置/文件（能从已有配置推导的）？
3. 有没有"靠作者记得"的不变量（应该是结构保证的）？
4. 覆盖/偏好是不是挂在了它"必然基于"的基础上？
5. 有没有把玩法语义塞进不该塞的地方（事件 payload、通用配置）？
6. 文档有没有此地无银、壮胆文学、假设上下文的表述？
7. **是不是把某个具体子系统的经验当成了通用原则？**（应该是"案例在子系统文档，原则进宪法"）

## 5. 输出

按任务类型：
- 设计文档 → 遵循 `references/doc-discipline.md`。
- 配置结构 → 真实字段 + 示例 + 明确"机制是代码、内容是配置"。
- 评审 → 按第 4 节自检清单给意见。
