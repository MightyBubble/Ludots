# 用户可读 showcase 设计法

## 定位：showcase 是产品，不是验收夹具

能力演示的失败模式几乎从不是"没做"，而是做成了**验收夹具**：单一固定场景、零交互、
关键数字只存在于测试断言里、资产断链。夹具回答"它能跑吗"；showcase 要让**没读过你代码
的用户在 60 秒内看懂这个能力解决什么问题，并产生"我也想用"的冲动**——它回答"它为什么值得"。

接到需求后，按下面八步顺序推导，每步的产出写进设计文档对应小节。

## 防复制条款（先读）

文末的完整示例（视野迷雾）只演示方法，**它的具体内容一个字都不许搬**：惊喜时刻、消融形式、
HUD 指标（如"威胁采样值"）、颜色方案、旋钮条目都必须从**当前能力自己的动态轴**重新推导。
判断方法：把设计文档里的每个元素问一遍"这是这个领域固有的，还是从别的领域借来的"——
HUD 数值必须是该能力的真实状态量（背包是"重量/格位"，寻路是"路径长/重算耗时"，
不是什么能力都显示"威胁采样"）。借来的元素即使碰巧有效，也是错的。

## 第 1 步：定能力形态，找动态轴

先判断需求属于哪类形态。形态决定**动态轴**——这个能力的价值在什么变化中体现：

| 形态 | 典型例子 | 动态轴（世界变 → 什么变） |
|------|----------|---------------------------|
| 空间/场 | navmesh、视野迷雾、影响力场 | 障碍/单位移动 → 路径、场分布实时变化 |
| 决策 AI | 行为树、utility AI、敌人 AI | 玩家行为 → AI 决策及其理由变化 |
| 数据/规则 | 背包、冷却、经济系统 | 状态输入 → 规则判定结果变化 |
| 管线/基础设施 | 配置热载、序列化、网络同步 | 输入扰动 → 管线各阶段产物变化 |

自检一句话：**"如果世界不动，我的 showcase 还有东西可看吗？"** 答"没有"就说明动态轴找错了，回本步重找。

## 第 2 步：一句话说服点 + 消融对照

写下用户会被瞬间说服的那个点。它必须是**用户视角的痛点**，不是实现视角的卖点：
"绕开刚放下的障碍"是对的；"采用了分布式 A*"是错的。
然后把它做成开关：同一场景，关掉该能力 vs 开启该能力，一键切换或并排双开。
消融对照是 showcase 里信息密度最高的元素，缺了它用户看不出"为什么需要这个能力"。

## 第 3 步：设计 60 秒动态主循环

一个持续运转的循环，让动态轴一直可见：
- **谁改变世界**：玩家操作、自动巡演脚本、或随机事件，三选一或组合；
- **用户看到什么随之变化**：视觉反馈延迟必须小于 1 秒，变化要指向能力本身；
- **至少一个惊喜时刻**：制造一个刁难，让能力价值在应对中显形——堵死通路看寻路改道、
  关灯看夜视生效、把背包装满看规则触发。惊喜时刻 = 用户记住这个 showcase 的那 3 秒。

## 第 4 步：解释层——让决策可读

把内部数值和决策过程搬到屏幕上，用户才能"读懂"而非仅仅"看到"：
- **HUD 数值**：当前关键状态量，带量纲（如"路径长度 412cm"、"威胁采样 8.2"）；
- **颜色编码**：连续量用热力色阶梯，离散决策用高亮色；
- **候选可见**：有打分/排序机制时，把 Top-N 候选亮出来；
- **一句话图例**：屏幕角落说明每种颜色/标记的含义。

达标判据：看完演示的用户能回答"**它为什么这么做**"，而不只是"它做了"。

## 第 5 步：列运行时旋钮（不少于 4 个）

每个旋钮 = 一个**运行时**可调参数 + 它回答的用户问题。成表：

| 旋钮 | 范围 | 演示什么（回答用户什么问题） |
|------|------|------------------------------|
| （示例）算法切换 | A* / JPS | 两种算法的路径质量与耗时差 |
| … | … | … |

禁止把"改配置文件重启"的参数当成旋钮。旋钮不够 4 个，通常说明第 1 步的动态轴挖得不够深。

## 第 6 步：结构分层，渐进式引导

- **主演示**：一个综合场景，完整覆盖说服点；
- **子场景**：每个能力子特性一个最小场景，从主演示可进入；
- **首屏引导**：一段文字告诉用户"按什么、看什么、预期什么"。

## 第 7 步：门户资产与同源

为不进演示场的用户（门户读者、评审者）准备资产：
- 截图/录屏/GIF：取**惊喜时刻**的那一帧，不取静态全景；
- 预览页（HTML 等）：必须从真实配置生成，**禁止硬编码第二份数据**；
- 文档：一段说人话的叙述 + 本设计文档。

同源自检："改一份配置，演示和预览页会一起变吗？"——不会，就是埋了漂移债。

## 第 8 步：反向 API 审计

showcase 是 API 完整性的验收器。逐项检查第 3–5 步的每个元素需要什么接口：
运行时切换算法？查询内部打分？路径/场细粒度可视化？把 showcase 需要而现有 API 可能缺的
接口列成清单，逐条标注归属（本次交付 / 后续 issue）。**设计 showcase 就是在给 API 挑毛病**——
这份清单是设计文档的第二产出，价值不亚于演示本身。

## 反模式清单（交稿前逐条自审）

1. 单一固定场景 + 零交互 = 验收夹具；
2. 关键数字只在测试断言里，屏幕上没有 HUD；
3. 预览页硬编码参数，与真实配置漂移；
4. 资产断链（引用不存在的截图/文件）；
5. 无消融对照；
6. 文档只有架构/算法，没有"用户看懂什么"一节；
7. 术语不经解释直接堆给用户。

## 输出纪律

- 首行即文档标题（`# …`），此前禁止任何寒暄、思考标记、元话语（"让我想想"/"以下是"/`<blink>`之类）；
- 直接输出文档本身，不要在文末汇报"我遵循了哪些步骤"之外再解释方法论；
- 遵守任务给的行数上限；自报行数时以实际输出为准，不虚报。

## 输出文档骨架

```markdown
# <能力名> showcase 设计
## 一句话与目标用户      ← 30 字内讲清演示什么，写给没读过代码的人
## 主循环                ← 谁改变世界 / 用户看到什么变 / 惊喜时刻
## 消融对照              ← A/B 场景设计
## 解释层                ← HUD 数值 / 颜色编码 / 图例
## 旋钮清单              ← 表格，≥4 行
## 场景结构              ← 主演示 + 子场景 + 首屏引导
## 门户资产              ← 截图/预览/文档 + 同源方案
## 反向 API 审计         ← 需要但可能缺的接口清单，标注归属
```

## 完整示例：视野迷雾（fog-of-war）

先看**夹具式反例**：固定地图、固定单位、渲染一张已探索区域贴图、无任何交互。
它证明了"迷雾计算正确"，但用户 5 秒就关掉了。

**按八步推导的正例**：

1. **形态**：空间/场。动态轴 = 单位移动与视野遮挡 → 迷雾覆盖实时变化。
2. **说服点**：「同样一面墙，站左边看得见墙后的敌人，站右边看不见」。消融：开关记忆层
   ——关：离开视野立刻忘记敌人；开：留下渐淡的"记忆残影"。一键切换，同场景。
3. **主循环**：玩家 WASD 移动一个侦察单位，迷雾实时揭开/重新合拢（<100ms）；
   **惊喜时刻**：故意把单位撤走，敌人从记忆残影位置推进——用户亲眼看到"刚才那里有东西，
   现在没了，但系统记得"。
4. **解释层**：HUD 显示"当前可见敌人 N / 记忆中 M"；可见=亮色、记忆=半透明蓝、
   未知=黑；图例固定在左下角。
5. **旋钮**：视野半径（100–800cm，"多远能看见"）、视锥角度（30°–360°，"朝向影响视野吗"）、
   记忆衰减速度（"忘得多快"）、遮挡开关（"墙真的挡视线吗"）。
6. **结构**：主演示 = 侦察遭遇战；子场景 = 纯视锥、纯遮挡、记忆衰减三条最小链路；
   首屏："用 WASD 移动，注意墙后与残影"。
7. **资产**：惊喜时刻帧（残影+推进中的敌人）作封面图；预览页直接读 showcase 的视野配置
   JSON 渲染 2D canvas，改配置预览跟着变。
8. **反向审计**：需要"按单元格查询迷雾状态"的只读接口（HUD 用）、"运行时改视野参数并立即
   生效"的接口（旋钮用）、"记忆残影的渲染数据导出"（预览页用）——若引擎当前只有整图渲染
   API，前两条列入本次交付清单。

（本例只演示方法。为其他领域设计时，重新走八步推导，不要套用迷雾的具体内容。）
