# [y5k][A9] 活动生命周期引擎键与呈现投影

## 1. 概述

### 1.1 背景

目标追踪、审计工具和界面都需要知道「一个活动开始了、呈现了、玩家选了、结算了、进档案了」。这些订阅点是**引擎键**，属于运行时对外暴露的接口，不是活动的内容定义。

两件事必须提前防住。一是命名混淆：一旦有人把这些键叫成「子活动」，内容作者就会试图去配置它们，而它们根本不是配置对象。二是自我订阅成环：把「活动已呈现」这个键写进某条定义的 `source_subscription`，活动一呈现就再触发一次自己，一路滚下去。

### 1.2 目的

- 发布并实现五个生命周期引擎键：开始、呈现、选定、结算、历史落档。
- 明确它们与活动定义、与事实来源的区别，并在加载期拒绝把它们当事实来源使用。
- 规定载荷的最小字段集，让订阅方不必回头去猜是哪一个实例。
- 规定呈现投影的方向：界面只读投影实例状态，不反过来把界面状态当真相。

### 1.3 思路

键名稳定、可订阅、可测试，顺序有明确合同。载荷里一定带得上定义 id 和实例 id，选定这个键还要带上选项 id。

本卡**玩家不可见**：玩家只感知弹层与历史，不感知键名。线框图在这里把「玩家所见」和「审计侧所见」上下对照，说明同一件事在两侧分别长什么样，也说明为什么键名绝不能出现在玩法文案里。

## 2. 结构

| 生命周期键 | 什么时候发出 | 典型订阅方 |
|---|---|---|
| 活动开始 | 实例创建，状态进入 `pending` | 审计、目标追踪桥接 |
| 活动呈现 | 实例呈现给玩家，状态进入 `active` | 界面呈现层 |
| 选项选定 | 玩家确认了某个选项，且执行条件复检通过 | 审计 |
| 活动结算 | 结算完成，状态进入 `resolved` | 目标追踪、历史 |
| 历史落档 | 历史记录写入完成 | 档案界面 |

需玩家处理的路径，顺序合同是：开始 → 呈现 → 选定 → 结算 → 历史落档。自动结算路径没有呈现与选定两步，顺序是：开始 → 结算 → 历史落档。

### 2.1 载荷最小字段集

所有键都带定义 id 与实例 id。选项选定这个键额外带选项 id。结算与历史落档复用同一个实例标识，让订阅方能把整条链串起来。

## 3. 详情

### 3.1 命名纪律

文档、注释、界面文案都必须写清：这些是引擎订阅键，不是活动定义，也不是事实来源。任何把它们称作「活动」「子活动」的表述，按合同违规处理。

### 3.2 不得当作事实来源

生命周期键写进 `source_subscription` 会在加载期被拒绝，失败原因指明它是生命周期键而不是事实来源。这条挡的是自我订阅成环，也挡的是「用生命周期键绕过登记目录去改世界」。

### 3.3 呈现投影的方向

投影是单向的：实例 entity 是真相，界面读它。界面**不得**只听键不查实例——只听键会漏掉状态，也会在断线重连、读档之后拿到过期的画面。正确做法是键只作为「该刷新了」的提示，刷新时仍然按实例 id 去查当前状态。

同理，界面不得把自己缓存的选择结果当成已经发生的事实。玩家点了确认，也要等结算键回来才认。

### 3.4 顺序不变量

| 不变量 | 含义 |
|---|---|
| 开始一定最先 | 任何实例都必须先创建再做别的 |
| 呈现与选定成对 | 有选定必有在它之前的呈现 |
| 结算一定在选定之后 | 需玩家处理的路径上，没选过就不该有结算 |
| 历史落档最后 | 落档之后不再有该实例的任何生命周期键 |

### 3.5 锚定 fixture 字段

| 字段名 | 语义 | 单位 | 谁可改 |
|---|---|---|---|
| `lifecycle_fixture.expected_key_sequence_player_path` | 需玩家处理路径上应观察到的生命周期键顺序 | 键名序列 | 验收夹具维护者 |
| `lifecycle_fixture.expected_key_sequence_auto_path` | 自动结算路径上应观察到的生命周期键顺序 | 键名序列 | 验收夹具维护者 |
| `lifecycle_fixture.chosen_option_id` | 夹具中玩家所选的选项 id | id | 验收夹具维护者 |
| `lifecycle_fixture.lifecycle_key_used_as_source` | 负例包里被误当作事实来源的生命周期键 | 键名 | 验收夹具维护者 |

## 4. 场景

> 本卡是运行时接口与投影纪律，**玩家不可见**；失败必须 fail-fast 可见——顺序不对、键被当成事实来源、界面只听键不查实例，都要当场失败并给出原因。

### 4.1 需玩家处理路径的顺序

走完一次玩家选择 → 观察到的生命周期键顺序与夹具字段一致，选定这个键的载荷里带着玩家实际选的选项 id。

### 4.2 自动结算路径的顺序

自动路径走完 → 观察到的顺序里没有呈现与选定两步，与夹具字段一致。

### 4.3 把生命周期键当事实来源

某定义把生命周期键写进 `source_subscription` → 加载失败，原因指明这是生命周期键。

### 4.4 界面只听键不查实例

测试替身让投影层只根据键更新画面、不回查实例 → 守卫检查判定不合格，因为断线重连或读档之后画面会与真相不符。

## 5. 边界

- 不新增任何玩法域的事实来源。
- 不让界面成为状态真相，投影永远是单向只读。
- 禁止用生命周期键绕过登记目录去改世界。
- 禁止在玩法文案里把引擎键称作 Activity。
- 禁止在顺序合同之外插入未声明的生命周期键。

## 6. UAT

```gherkin
Feature: 生命周期键可以订阅，但它不是活动内容
  Scenario: 需玩家处理路径的生命周期顺序完整
    Given fixture "y5k_activity_lifecycle_v1" 已加载
    When 玩家完成一次需要处理的活动并结算
    Then 观察到的生命周期键顺序等于 fixture 字段 lifecycle_fixture.expected_key_sequence_player_path
    And 选项选定键的载荷中，选项 id 等于 fixture 字段 lifecycle_fixture.chosen_option_id
    And 每个键的载荷中都带有定义 id 与实例 id

  Scenario: 自动结算路径没有呈现与选定
    Given fixture "y5k_activity_lifecycle_v1" 中自动结算路径已执行
    When 读取该实例的生命周期键序列
    Then 序列等于 fixture 字段 lifecycle_fixture.expected_key_sequence_auto_path
    And 序列中不包含活动呈现与选项选定

  Scenario: 读档之后界面按实例回查而不是只信键
    Given fixture "y5k_activity_lifecycle_v1" 中存在一个状态为 active 的实例
    When 投影层在没有收到任何生命周期键的情况下重新初始化
    Then 界面仍能按实例 id 查到该实例并正确呈现
    And 呈现内容与实例当前状态一致

  Scenario: 边界——生命周期键不能当作事实来源
    Given 某活动定义的 source_subscription 引用了 fixture 字段 lifecycle_fixture.lifecycle_key_used_as_source 指定的键
    When 加载该定义
    Then 加载失败
    And 失败原因中包含 "lifecycle_key_not_source"
    And 该定义没有以任何降级形式进入 Registry

  Scenario: 边界——投影层只听键不查实例判定不合格
    Given 测试替身让投影层仅依据生命周期键更新画面且不回查实例
    When 运行合同守卫检查
    Then 判定不合格
    And 原因中包含 "projection_must_read_instance"
```
