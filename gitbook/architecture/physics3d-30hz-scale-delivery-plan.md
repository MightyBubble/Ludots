# Physics3D 固定 30Hz 大规模联机实施计划

## 1 概述

### 1.1 目标

本计划把 Physics3D 从当前的基础样例能力推进为 Ludots 的正式 3D 动作物理车道，服务以下同一组产品目标：

- 服务器权威固定 `30Hz`，每个已提交服务器帧只执行一次权威物理步；
- `150` 名真人玩家同时在线；
- `100K` 刚体可注册，`10K` 活跃刚体作为常态，`25K` 活跃刚体作为战斗峰值，`50K` 活跃刚体作为稀疏世界压力门；
- Raycast、Box/Sphere/Capsule Cast、Sweep、Overlap、Sensor/Trigger、接触事件均走正式批量查询与结果通道；
- 支持摩擦、风场、力场、冲量、移动/旋转/传送带/单向平台；
- 支持 Character3D、移动平台速度继承、攀爬、抓边；
- 支持实体轮、Box Wheel、Raycast/Shape Cast Wheel、悬挂；
- 支持 Ragdoll、关节范围、主动姿态与碰撞子组；
- ECS 热路径遵守 SoA、Chunk 迭代、Inline-query、Span、固定容量、稳态 `0GC`；
- 服务器权威快照、同构环境重放、客户端局部预测与校正具备清晰边界；
- 每项能力既有自动化证据，也有新玩家能直接上手、看懂结果的 Showcase。

### 1.2 当前基线

当前分支已具备以下可复用基础：

- `Ludots.Physics3D` 对 BepuPhysics `2.4.0` 的封装；
- Box、Sphere、Capsule 与 Dynamic、Kinematic、Static body；
- Ball Socket、Hinge、Weld，以及九类线性/角度 Servo、Motor、Limit；
- Raycast、三类 Shape Cast、三类 Overlap；Closest/Any、逐请求过滤和无分配批处理正在收口；
- CCD、接触事件、固定容量异常；
- Force、Acceleration、Torque、Linear/Angular Impulse、ImpulseAtPoint 的固定容量 SoA 命令缓冲；
- `CopyActiveBodyIds`、`CopyAwakeBodies`、可观察刚体状态哈希；
- 引擎时钟与 Physics3D 时钟均为 `30Hz`，`MaximumPhysicsStepsPerSourceTick=1`；
- Physics3D Playground 和 `1K/10K/25K/50K` 持续活动刚体预设。

源码证据以 `src/Core/Ludots.Physics3D/`、`mods/capabilities/physics3d/` 和 `mods/showcases/capability_standard/CapabilityStandardPhysics3DShowcaseMod/` 为准。现有 Playground 是十站点玩家入口基线，不代表本计划中的完整网络回滚或大规模混合压力已经交付。

### 1.3 决策真相与治理门

本页是交付路线和验收门，不是新的 ADR。Physics3D 的 issue 计划真相仍由 [#257](https://github.com/MightyBubble/Ludots/issues/257) 及其子单维护，位姿、确定性与服务器权威合同由 [#258](https://github.com/MightyBubble/Ludots/issues/258) 裁决，重放与复制留口由 [#266](https://github.com/MightyBubble/Ludots/issues/266) 裁决。

2026-07-24 已完成 #257 至 #268 的计划口径收口。以下旧口径均已废止，后续实现和验收不得重新引用：

| 主题 | 已废止口径 | 正式口径 | 治理结果 |
| --- | --- | --- | --- |
| 规模 | 气泡内数十至数百 3D 实体 | 10K 活跃常态、25K 峰值、50K 稀疏压力 | #257/#260/#261/#268 已更新 |
| 联机 | 只留 replication 接口，不实现预测/复制 | 服务器权威快照、局部预测校正、重放恢复 | #257/#266 已更新 |
| 线程 | Physics3D World 强制单线程 | 固定分区、固定工作线程数的可重放并行执行 | #258/#260/#268 已更新 |
| 模块 | 角色、车辆和飞机由一个控制器承担 | Character3D、Traversal3D、Vehicle3D 独立归属 | #264 已更新 |
| Showcase | API 菜单与一次性掉落 benchmark | 可交互的切站式 Playground 与持续活动 Scale City | #267 已更新 |

P0 的范围裁决已经完成；性能门仍须以可复现测量逐项关闭。任何后续范围变化必须先更新 #257 层级，再修改 Core 合同。

### 1.4 完成定义

“彻底完成”同时满足以下条件：

1. 六个正式模块边界落地且没有 Showcase 私有旁路；
2. 所有规模档位在声明的参考硬件上通过 P95/P99、内存和 `0GC` 门；
3. 固定帧输入、命令、求解、提交、快照和重放使用同一个 Tick 真相；
4. 角色、平台、车辆、布娃娃和查询可组合运行，而非各自孤立演示；
5. 服务器与客户端对“预测什么、插值什么、谁拥有最终结果”没有灰区；
6. 容量不足、输入缺失、版本不匹配、重放分歧均明确失败，不静默降质；
7. 玩家 Showcase、headless 验收、性能报告、长稳报告和架构守卫全部通过。

### 1.5 市场方案评估与自研难度

截至 2026-07-24，没有一个开源方案能以 Ludots 可直接使用的形态同时交付“C# 公共合同、SoA、稳态全线程 0GC、50K 活跃刚体、150 人输入/AOI/局部预测和完整 3D 回滚”。但“开源 3D 物理都不支持固定帧联机”也不准确：Jolt 已提供确定性与状态保存/恢复，Jitter2 和 Rapier 也提供受条件约束的跨平台确定性。真正的差距在 Ludots 数据布局、托管边界、网络协议、容量门和可验证集成。

| 方案 | 官方能力 | 与 Ludots 目标的差距 | 决策 |
| --- | --- | --- | --- |
| [BepuPhysics v2](https://github.com/bepu/bepuphysics2) | .NET 8、SIMD、多线程、低成本睡眠、批量 Ray/Sweep、丰富约束；当前 Ludots 已使用 2.4.0 | 不提供网络协议和完整公开回滚；跨环境逐位一致不是正式承诺；原生 API 非 Ludots SoA | 继续作为当前唯一生产 Kernel；先完成 K1 批量桥、稳定合并和测量 |
| [Jolt Physics](https://github.com/jrouwe/JoltPhysics) | MIT、C++、多核、Character/Vehicle/Ragdoll/Sensor；官方文档提供同构确定性、可选跨平台确定性及 `SaveState/RestoreState` | C# 绑定是社区层；回调和查询顺序仍需稳定排序；结构创建/销毁和业务状态不在普通状态快照内；需要原生生命周期、内存和 0GC 桥接 | 最强替代候选；只有 K2/完整恢复被 Bepu 证据阻断时，才开隔离迁移基准，不并存生产后端 |
| [Jitter Physics 2](https://github.com/notgiven688/jitterphysics2) | C#、无外部依赖、可选跨平台确定性、约束/软体、低成本 100K 非活动体 | 官方证据没有覆盖 Ludots 的 10K/25K/50K 活跃混合门、SoA 公共合同、全线程 0GC、批量查询和回滚协议 | 保留为 C# 确定性对照基准，不因语言相同直接迁移 |
| [Rapier](https://github.com/dimforge/rapier) | Rust、Apache-2.0、2D/3D、序列化、局部确定性；`enhanced-determinism` 可跨平台 | 官方说明跨平台确定性不能同时启用 SIMD 和 parallel；C# 需要 FFI；不含 150 人权威网络和局部预测 | 与当前大规模并行目标冲突，不作为生产替换 |
| [NVIDIA PhysX](https://github.com/NVIDIA-Omniverse/PhysX) | BSD-3-Clause、成熟 C++ 刚体/车辆/场景查询、CPU/GPU 生态 | 没有面向锁步网络的正式确定性/回滚合同；C# FFI 和原生内存边界成本高 | 适合功能/性能对照，不适合本项目固定帧真相 |
| [Bullet](https://github.com/bulletphysics/bullet3) | zlib、C++、成熟刚体和多物理，支持固定 timestep | 固定 timestep 不等于确定性联机；数据布局、稳定顺序、C# 0GC 和大规模门均需重做 | 不迁移 |
| [ReactPhysics3D](https://github.com/DanielChappuis/reactphysics3d) | zlib、轻量 C++、无 STL 容器、基础刚体/关节/查询 | 官方能力不含多核规模、确定性回滚、车辆/Ragdoll 高级约束和 C# SoA 桥 | 能力覆盖不足 |
| [Unity Physics](https://docs.unity3d.com/Packages/com.unity.physics@1.3/manual/index.html) | DOTS 数据导向、确定性刚体和空间查询 | 绑定 Unity ECS/Burst/包许可与运行时，不是 Ludots 可独立采用的通用开源库 | 仅参考数据布局与作业设计 |
| Photon Quantum | 商业固定点确定性、预测/回滚和网络框架 | 闭源商业运行时，不是可纳入 Ludots 的开源 Physics3D；规模和定制边界受产品约束 | 可作联机产品体验对照，不作为内核依赖 |

Jolt 的确定性有明确条件：修改世界的 API 顺序必须一致；普通多线程宽相查询、监听器回调和 active body 顺序不保证稳定，调用方仍需过滤和排序；`SaveState` 只保存物理更新自己修改的状态，帧间新增/删除 body/constraint 和业务属性必须由上层同步恢复。因此即使迁移 Jolt，Ludots 的稳定命令、网络 ID/generation、输入环、AOI、局部预测和业务快照仍然必须自研。

自研难度按“已有成熟窄相和求解器可复用”与“从零写完整 3D Kernel”分开估算：

| 层级 | 粗略投入 | 主要难点 |
| --- | --- | --- |
| K1 Ludots 数据面 | 2–3 名熟悉 ECS/物理的工程师，约 6–10 人周 | 固定容量 SoA、批量桥、稳定合并、逐线程 0GC、真实混合场景测量 |
| K2 受控源码与完整状态恢复 | 2–3 名工程师，约 12–20 人周 | 上游纳管、内部句柄/缓存快照、约束冲量、流形、island、宽相代理和版本兼容 |
| K3 自研宽相/查询 | 2–4 名工程师，约 4–7 人月，另需长期压测 | 动态/静态/大物体分层、并行更新、稳定候选集、50K 查询和内存局部性 |
| K4 自研 island/求解器 | 3–5 名工程师，约 8–15 人月，另需 6 个月以上稳定期 | 图着色、SIMD 约束批、摩擦/堆叠/车辆/Ragdoll 稳定性、完整恢复和调试工具 |
| 从零固定点跨平台 3D Kernel | 4–6 名专职工程师，约 18–30 人月 | 数学库、碰撞形状、CCD、求解器、查询、工具链、平台一致性和多年边界案例 |

这些是启动门估算，不是排期承诺。当前 true-sparse 50K 的短时物理步百分位与 `0GC` 子门已通过，但完整服务器 Tick、P99、宽相完整性和长稳门仍待补；现有证据不支持为了“自研”直接进入 K3/K4。最划算的路线仍是保留 Bepu 求解器，彻底自研 Ludots 的 SoA 数据面、固定帧协议、玩法模块、网络复制和可验证快照边界。若完整世界恢复成为硬阻塞，先做 Jolt 与 Bepu K2 的同场景隔离基准，再二选一，禁止生产环境保留双后端 fallback。

## 2 结构

### 2.1 模块归属

| 模块 | 唯一职责 | 不得承担 |
| --- | --- | --- |
| `Physics3D` | body/shape/material、宽相/窄相/求解、批量查询、接触策略、Sensor、力与冲量、约束、状态导出 | 玩家输入、攀爬状态机、车辆玩法、网络 transport |
| `Character3D` | 地面支撑、坡度、台阶、跳跃、移动平台相对速度、稳定角色移动 | 抓边题材规则、车辆悬挂、网络复制 |
| `Traversal3D` | 梯子、攀爬、抓边、翻越，消费 Character3D 和查询结果 | 自建碰撞世界或直接调用 Bepu 类型 |
| `Vehicle3D` | 实体轮、Box Wheel、Raycast/Shape Cast Wheel、悬挂、转向、驱动、刹车、轮胎力 | 私有查询系统、私有时间步 |
| `Ragdoll` | 骨骼配方、关节范围、碰撞子组、主动姿态、动画与物理切换 | 角色移动真相、Showcase 特例 |
| `Networking` | Tick 输入环、确认、快照、AOI、基线、预测校正、重放调度 | 直接改 Physics3D 内部状态或拥有第二套 Tick |

跨模块合同必须只暴露 Ludots 类型；Bepu 类型只允许存在于 Physics3D 实现边界。每个可变状态只有一个写者，其他模块通过命令、查询结果或只读快照消费。

### 2.2 固定帧流水线

```text
输入按 Tick 截止并校验
        ↓
提交 Character / Traversal / Vehicle 意图
        ↓
生成平台轨迹与运动学速度
        ↓
执行批量 Cast / Sweep / Overlap
        ↓
形成定容 SoA 物理命令并稳定排序
        ↓
施加力、冲量、马达、伺服与接触策略
        ↓
Physics3D Step(1 / 30s)
        ↓
收集接触、支撑、Sensor 与约束反馈
        ↓
批量同步 Dirty / Awake 状态到 ECS
        ↓
提交 CommittedTick、可观察刚体状态哈希和 AOI 快照
        ↓
客户端插值或局部预测校正
```

必须区分三个 Tick：

- `ExecutingTick`：正在执行，不允许发布；
- `CommittedTick`：该帧全部系统和物理已完成，可以成为权威结果；
- `SnapshotTick`：某客户端收到的权威状态版本。

渲染可以变帧，但只能在相邻两个已提交状态之间插值。暂停时权威 Tick 不前进；单步必须恰好提交一个 `1/30s` Tick。

### 2.3 热路径数据结构

下列缓冲均为预分配、固定容量、按字段连续存储的 SoA：

- `BodyStateSoA`：位置、旋转、线速度、角速度、质量、惯量、shape、material、layer、island、generation、flags；
- `BodyCommandSoA`：创建、销毁、传送、唤醒、睡眠与属性变更；
- `ActuationSoA`：Force、Acceleration、Torque、Impulse、ImpulseAtPoint；
- `QueryRequestSoA` 与 `QueryResultSoA`：形状、起点、方向、距离、过滤、结果范围；
- `ContactEventSoA`：接触对、法线、点、相对速度、阶段和策略结果；
- `ConstraintCommandSoA`：创建、销毁、目标、马达和限位更新；
- `SnapshotSoA`：网络复制和重放需要的状态分区。

每个工作线程写入自己的固定分区，帧末按 `Tick → ProducerId → EntityStableId → Sequence` 合并。禁止热路径 ECS 结构变更、托管集合扩容、跨 Chunk 随机追指针和依赖任务完成先后的合并。

### 2.4 内核演进

自研采用逐层替换，不同时保留两个生产物理后端：

| 层级 | 内容 | 启动条件 | 退出条件 |
| --- | --- | --- | --- |
| K1 | 保留 Bepu 求解器，先完成 Ludots SoA、批量桥、Dirty/Awake 同步和逐阶段计时 | 立即执行 | 10K 混合场景不再被逐体桥接主导 |
| K2 | 将经过审计的 Bepu 源码纳入仓内受控 Kernel，固定版本、补许可证与上游同步规则 | #258 更新且 K1 基线稳定 | 公共 API 无 Bepu 泄漏，源码基线可重复构建 |
| K3 | 自研世界固定网格 + 单元动态 BVH + 静态压缩 BVH + 大物体全局 BVH | 宽相或批量查询在目标场景连续超预算 | 25K 峰值和 50K 稀疏门通过 |
| K4 | 自研稳定 Island 调度、约束图着色、SIMD 求解扩展和完整快照恢复 | 求解/调度经测量确认是主瓶颈，修改 K2 不足 | 混合场景、车辆和布娃娃门全部通过 |

K3/K4 是允许的自研方向，不是预设结论。每次升级必须由逐阶段计时、最小复现场景和回归基线触发；不得为了“纯自研”重写已通过验证的碰撞算法。生产配置只有一个 Kernel，不提供失败后静默切回旧实现的 fallback。

### 2.5 依赖图

```text
P0 issue/ADR 口径与基准合同
 └─ P1 固定 Tick + SoA 命令/查询/状态通道
     ├─ P2 力/接触策略/高级形状/约束/Sensor
     │   ├─ P3 Character3D ─ Traversal3D
     │   ├─ P4 Vehicle3D
     │   └─ P5 Ragdoll
     ├─ P6 Networking 快照/重放/局部预测
     └─ P7 规模内核优化 K2/K3/K4

P3 + P4 + P5 + P6 + P7
 └─ P8 综合 Showcase、150 人混合压力、长稳与收束
```

P3、P4、P5 可以在 P2 合同稳定后并行；它们不得分别复制查询、接触过滤、约束或 Tick 管线。P6 可以先用基础 body 场景打通，但最终验收必须覆盖角色和车辆。P8 不拥有新运行时能力，只负责组合、引导、观察和证据。

| P7 规模内核 | 按 K1→K4 触发，优化宽相、查询、Island、求解、快照 | 100K/10K、25K、50K 三档全部通过 |

每个阶段都采用 red/green/refactor：先写行为或性能失败证据，再补最小正式能力，最后删除重复入口并更新文档。某阶段不能通过门时，保留失败报告并继续定位；不得通过减少实体、隔帧偷算或关闭能力把报告改绿。

### 3.2 查询、Sweep 与 Sensor

统一 Query Contract 必须覆盖：

- Ray、Box、Sphere、Capsule 的 Any/Closest/All；
- Box/Sphere/Capsule Sweep；
- Box/Sphere/Capsule/Convex Overlap；
- layer、body kind、Sensor、IgnoreBody、IgnoreAssembly 过滤；
- 起点重叠、命中点、法线、距离、body、entity、sub-shape；
- All Hits 的稳定顺序和明确容量错误；
- 单请求和批请求共享一套执行器，不维护两套算法；
- 大结果集合不得使用 O(n²) 插入排序。

Sensor/Trigger 是不产生求解冲量但保留重叠生命周期的正式形状语义，不能用普通接触事件伪装。所有结果在 Tick 内有效；跨 Tick 持有必须复制到调用方自己的固定容量状态。

### 3.3 力、摩擦和平台

力学输入统一进入 `ActuationSoA`：

- Force 与 Torque 按本 Tick 的固定时长积分；
- Acceleration 不受质量影响；
- Impulse 与 ImpulseAtPoint 立即改变本 Tick 的速度，作用点冲量同时产生角速度；
- 风场、引力场、爆炸和牵引只负责生成上述正式命令；
- 材料组合、静摩擦/动摩擦扩展、接触面速度和恢复速度由接触策略处理。

移动和旋转平台必须由相邻 Tick 姿态计算真实线速度与角速度。传送带通过接触面速度驱动，单向平台通过条件接触禁用实现；禁止直接改角色速度伪装平台继承，或在接触事件之后补一次位置纠正。

### 3.4 Character3D 与 Traversal3D

Character3D 使用动态胶囊、接触支撑和相对运动约束。每 Tick 的基本路径为：读取移动意图、批量探测、判定支撑、生成约束目标、随物理步求解、输出稳定角色状态。

台阶探测只在前方受阻且满足配置条件时执行“上探、前探、下探”；不能让 150 个角色无条件执行固定数量的 Cast。坡度、台阶高度、皮肤宽度、悬空宽限、跳跃速度和查询容量全部配置化。

Traversal3D 通过查询结果进入明确状态：普通移动、附着、攀爬、抓边、翻越、脱离。抓边必须校验手部净空、顶部可站立面和角色胶囊落点；状态切换通过命令缓冲发生，不在查询循环中增删 ECS 组件。

### 3.5 Vehicle3D

Vehicle3D 提供三种正式实现，共用输入、动力、轮胎材料、查询和调试证据：

- 实体轮/Box Wheel：轮体参与碰撞，悬挂轴、弹簧、限位、轮轴马达和转向约束组合；
- Box2D Wheel Joint 语义：不是单个 Hinge，而是轴向移动约束、弹簧、行程限位、轮轴转动和马达的明确组合；
- Raycast/Shape Cast Wheel：每轮批量查询地面，以接地点和相对速度生成悬挂、纵向和横向力，适合高数量车辆。

相邻轮体、车身和同一装配体需要碰撞子组过滤。轮胎打滑、悬挂压缩、接地点、接触法线和施力方向必须可被 Showcase 读取，但调试表现不能反写仿真。

车辆固定帧事务顺序固定为 `SetInput → PrepareFixedStep → Physics3D Step → ObserveFixedStep`。从准备完成到观察完成之间，输入、车辆注册、车辆移除和销毁均被明确拒绝，避免本帧已经生成的扫描、冲量、马达目标与车辆拓扑分叉。Showcase 的控制系统必须插在正式 `Physics3DSimulationSystem` 之前，观察系统必须位于后续阶段；测试中不得通过清空冲量命令伪造完整物理帧。

### 3.6 Ragdoll

Ragdoll 由数据化骨骼配方生成，不在代码中硬编码人形层级。配方包含 body shape、质量比例、父子连接、Swing/Twist 范围、碰撞子组、主动姿态强度和断裂策略。

动画角色切换为 Ragdoll 时，初始姿态和速度在 Tick 边界一次性移交；恢复时由 Ragdoll 状态生成候选站立姿态，经 Character3D 空间检查通过后再移交。相邻骨骼默认不碰撞，非相邻骨骼按配方决定；任何非有限状态都立即失败并报告 body/constraint/tick。

### 3.7 联机、重放与跨平台边界

正式网络模型为服务器权威：

- 服务器以 `30Hz` 接收、验证并执行带 Tick 的输入；
- 快照频率只能是 `30Hz` 的整数分频，具体档位由配置决定；
- 客户端只预测本地角色或本地驾驶车辆，并保留固定长度输入历史；
- 远端玩家、普通刚体和 Ragdoll 使用权威快照插值；
- 校正从服务器确认 Tick 重放本地输入，不回滚整个 10K 世界；
- AOI 只决定复制集合，不得删除服务器权威实体或改变服务器物理解算；
- 迟到、重复、缺失、越界输入都有显式协议和计数器，不用默认输入静默掩盖；
- 构建、Kernel、配置、SIMD、线程数或场景哈希不兼容时拒绝接管和精确重放。

浮点内核的正式承诺是同构服务器环境、相同构建和相同配置下的可重放性；x64 与 ARM、不同 SIMD 宽度或不同线程配置之间逐位一致不是本计划目标。跨平台客户端通过服务器快照收敛。如果未来业务必须跨架构逐位锁步，应另立固定点 Kernel ADR，不能把量化状态哈希宣传为完整跨平台确定性。

“可观察刚体状态哈希在重建场景后相等”只叫确定性重放检查。只有快照同时覆盖 body、稳定槽/generation、约束累计冲量、接触流形缓存、睡眠 island、宽相代理和命令/输入游标，并能从任意保留 Tick 恢复，才可以称为世界回滚。

## 4 场景

### 4.1 Showcase 产品结构

正式入口继续使用 `CapabilityStandardPhysics3DShowcaseMod`，作为一个可直接操作的 Physics3D Playground，而不是把测试方法列表做成菜单。当前产品形态是十个独立站点：玩家通过面板切站，每次切站明确清理并重建当前场景；角色路线只存在于 Platform Station 与 Traversal Course 内。面板只显示当前站点的目标、操作、关键状态和结果，不宣称存在跨十站连续环形路线。

| Scanner Range | 瞄准并切换 Ray/Box/Sphere/Capsule 扫描，拖动距离和层过滤 | 扫掠体积动画、全部命中顺序、命中点、法线、距离、起点重叠 | 批量 Query |
| Material Hill | 推动相同箱体经过冰、木、橡胶坡道 | 滑行、停止距离和侧向摩擦差异 | Material/Contact |
| Platform Station | 乘电梯、旋转盘、传送带并从下方穿过单向台 | 身体稳定跟随、离开后继承速度、传送带移动、单向通过 | 平台速度/条件接触 |
| Wind Tunnel | 调整稳风、阵风和涡旋，向场中投放轻重物体 | 质量差异、旋转、作用点冲量和力方向 | Actuation/Field |
| Traversal Course | 连续通过坡、台阶、移动平台、梯子、岩壁和抓边点 | 移动不断流，抓边、翻越和落地反馈明确 | Character/Traversal |
| Wheel Lab | 同一底盘切换实体轮、Box Wheel、扫描轮，驶过坑洼、侧坡和跳台 | 悬挂压缩、接地点、打滑方向、驱动和刹车差异 | Vehicle |
| Ragdoll Lab | 推人偶下楼梯、启动摆锤、切换主动姿态 | 关节范围、碰撞子组、倒地和恢复 | Ragdoll |
| Constraint Forge | 操作门、吊桥、滑轨、链条、马达和破坏装置 | 各类约束的运动范围、载荷和失效反馈 | Advanced Constraints |
| Deterministic Rebuild | 运行一段脚本基线，重建同一批创作刚体，再启动逐步核对 | 蓝色基线与金色重建结果沿同一进度比较；一致时通过，差异时停在首个不同步骤 | 同构确定性检查 |
| Scale City | 切换 1K/10K/25K/50K 工作负载和混合玩法档位 | 物体持续循环、碰撞、受风和被发射，不会落地后全部睡死 | Scale Kernel |

### 4.2 Showcase 设计规则

- 每区先提供一个明确目标和即时反馈，再展示指标；不以 API 名单代替玩法。
- Scanner Range 必须显示实际扫描过程和全部结果，不能只画起点、终点和第一命中。
- Deterministic Rebuild 必须把“脚本基线、重建、逐步核对”呈现为清楚的三阶段流程，不能只显示两个哈希数字，也不得称为玩家输入回放或运行中世界回滚。
- Scale City 的工作负载由种子和配置生成；活动体持续循环，休眠率是场景结果，不是偷减负载手段。
- 性能采样和可视化采样分离；允许只绘制有界样本，但权威世界中的声明实体必须全部存在并参与配置的工作负载。
- 玩家调节的数值来自配置范围并经过校验；Showcase 不写 Core 私有字段。
- 每个区都提供复位，复位通过正式命令缓冲在 Tick 边界执行。
- 任何能力未安装、容量不足或配置不合法时，场景明确失败并指明原因，不隐藏按钮、不替换成简化实现。

### 4.3 自动证据

每次正式验收产出：

- 单元与集成测试结果；
- 固定帧 trace 和首个分歧报告；
- 各压力档的逐阶段 P50/P95/P99、内存和所有线程分配；
- 150 人丢包、迟到、重排和校正统计；
- 长稳测试中的 Tick 积压、容量水位、睡眠/唤醒和错误计数；
- Showcase 各区截图或录像及人工 UAT 记录。

## 5 边界

### 5.1 明确非目标

- 不承诺不同 CPU 架构、SIMD 宽度或线程配置间的浮点逐位锁步；
- 不让 150 个客户端各自模拟并回滚整个 10K/25K 物理世界；
- 不用固定点求解器替换浮点内核，除非后续独立 ADR 明确业务需要；
- 不把 50K 密集堆叠定义为常态目标；50K 门是稀疏活动世界，25K 门覆盖爆发碰撞；
- 不在 Physics3D 内实现玩法输入、网络 transport、动画状态机或题材规则；
- 不把 Showcase 画面帧率当服务器 Tick 性能证据。

### 5.2 禁止事项

- 禁止热路径 ECS 结构变更、动态扩容、LINQ、闭包、每帧对象或字符串分配；
- 禁止通过 `GetBodyState/SetBodyVelocity` 逐体跨接口循环驱动 10K 世界；
- 禁止用直接改速度伪装力、冲量、传送带或平台继承；
- 禁止用 Hinge 假装完整 Wheel Joint，用普通接触事件假装 Sensor；
- 禁止 Character、Vehicle、Ragdoll 各自建立查询、碰撞过滤或时间步；
- 禁止容量不足后截断结果、丢弃命令、跳过实体或切换低保真实现；
- 禁止为了通过性能门减少声明实体、隔帧偷算、关闭碰撞或提前睡眠；
- 禁止 Bepu 类型泄漏到 GAS、Showcase、adapter 或业务 Mod；
- 禁止同时保留旧桥接和新 Kernel 作为运行时 fallback；迁移完成即删除旧入口；
- 禁止把可观察刚体状态哈希演示命名为世界回滚。

### 5.3 风险与止损条件

| 风险 | 观察信号 | 处理方式 |
| --- | --- | --- |
| 外层桥接吞噬预算 | body 同步和接口调用高于求解 | 先完成 K1，禁止提前重写求解器 |
| 单棵全局树在稀疏世界退化 | 50K 宽相/查询连续超预算 | 启动 K3 两级空间结构 |
| 实体轮与 Ragdoll 约束爆炸 | solver/constraint sort 成为主耗时 | 分场景剖析，启动 K4 图着色和批次优化 |
| 浮点重放不稳定 | 同构配置出现首帧分歧 | 先锁定任务分区和合并顺序，分歧未清零不得发布 |
| 网络校正过多 | 本地角色频繁大幅回拉 | 检查输入截止、角色合同和量化，不扩大客户端权威 |
| 文档与 issue 冲突 | 实现依赖本页但 issue 未裁决 | 阻断实现，先更新 #257/#258/#266 |

## 6 UAT

以下场景使用玩家可观察的 Cucumber BDD 语言。性能和内存数字由同一次运行的自动证据补充，不把架构内部名称塞进玩家步骤。

```gherkin
# language: zh-CN
功能: 固定30帧的3D物理游乐园
  作为第一次进入 Ludots 物理游乐园的玩家
  我希望操作结果稳定、反馈清楚
  以便我能理解并信任每项物理能力

  场景: 暂停后逐帧观察碰撞
    假如 玩家把两个正在相撞的物体暂停在半空
    当 玩家按下一次单步
    那么 世界只向前推进一个三十分之一秒
    并且 再次按下单步前所有物体都保持不动

  场景: 看懂一次胶囊扫描
    假如 玩家面前三道障碍位于不同距离
    当 玩家启动胶囊扫描
    那么 玩家看到胶囊沿完整路径移动
    并且 三个命中按由近到远显示位置、表面方向和距离
    并且 起点压住障碍时会明确显示起点重叠

  场景: 比较不同表面的摩擦
    假如 三个相同箱子分别位于冰面、木面和橡胶面
    当 玩家用相同力度推动三个箱子
    那么 玩家看到三个箱子的滑行距离明显不同
    并且 重复试验得到相同的先后顺序

  场景: 乘坐移动和旋转平台
    假如 玩家站在一座先平移再旋转的平台边缘
    当 平台完成一整段路线
    那么 玩家稳定地随接触点移动
    并且 玩家离开平台时保留合理的离开速度
    并且 玩家不会周期性弹起、漂移或穿入平台

  场景: 通过传送带和单向平台
    假如 玩家走上传送带并来到单向平台下方
    当 玩家先站在传送带上再向上跳
    那么 传送带按标示方向带动玩家
    并且 玩家能从下方穿过单向平台
    并且 玩家落回平台后会被稳定支撑

  场景: 在风洞比较轻重物体
    假如 玩家把轻球和重箱放进同一阵风
    当 玩家开启风洞并改变风向
    那么 轻球比重箱更快改变运动方向
    并且 玩家看到受力方向与物体旋转随风向同步变化

  场景: 连续完成攀爬路线
    假如 玩家从训练路线起点出发
    当 玩家经过坡道、台阶、移动平台、梯子和岩壁
    那么 玩家能连续走坡、上台阶、攀爬、抓边并翻上平台
    并且 撞墙或落地时不会穿墙、弹飞或卡入地面

  场景大纲: 驾驶不同车轮通过测试路
    假如 玩家把展示车切换为<车轮类型>
    当 玩家驶过减速带、坑洼、侧坡和跳台并完成刹车
    那么 车辆能转向、加速、悬挂回弹并停下
    并且 玩家看到每个轮的悬挂压缩、接地点和打滑方向

    例子:
      | 车轮类型 |
      | 实体轮   |
      | Box Wheel |
      | 扫描轮   |

  场景: 推倒并恢复一个布娃娃
    假如 一个人形站在楼梯顶端
    当 玩家用摆锤将人形推下楼梯并随后启动恢复
    那么 人形按关节范围弯曲并与每级楼梯碰撞
    并且 相邻骨骼不会互相挤压弹飞
    并且 空间足够时人形能从合理姿态重新站起

  场景: 看懂确定性重建核对
    假如 蓝色通道已经完成一段固定脚本基线
    并且 场景已从相同创作配置重新建立金色通道
    当 玩家启动逐步核对
    那么 玩家看到基线、重建和核对三个阶段依次完成
    并且 结果一致时面板明确显示所有步骤通过
    并且 出现差异时核对停在第一个不同的步骤并显示期望值与实际值
    并且 界面明确说明这不是玩家输入回放，也不是运行中世界回滚

  场景: 一百五十名玩家共同活动
    假如 150名玩家已进入包含车辆、人偶、风场和平台的战场
    当 战场以固定30帧连续运行两小时
    那么 每名玩家看到的最终结果都来自完整提交的服务器帧
    并且 本地操作在校正后与服务器结果一致
    并且 服务器没有跳过任何已声明的物体或玩法

  场景大纲: 在大规模城市维持活动世界
    假如 玩家选择<规模>活动物体预设
    当 玩家观察物体持续循环、碰撞、受风和被发射十分钟
    那么 场景保持固定30帧的服务器推进规则
    并且 所有声明物体继续参与其配置的工作负载
    并且 性能面板显示该档位通过对应的百分位预算

    例子:
      | 规模 |
      | 10000 |
      | 25000 |
      | 50000 |

  场景: 容量不足时明确停止
    假如 玩家选择的压力预设超过当前配置容量
    当 场景尝试启动
    那么 玩家看到具体不足的资源、需要容量和当前容量
    并且 场景不会少生成一部分物体后继续运行
```

UAT 完成还必须满足：对应 headless 行为测试全绿、参考硬件性能门全绿、稳态所有线程 `0GC`、两小时长稳无 Tick 积压，以及 Showcase 截图或录像能证明玩家看到的反馈与场景描述一致。
