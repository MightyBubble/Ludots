# 《双人前线》RTS 联机 Showcase 设计与验收

> 上游 Epic：[平台无关服务器权威联机核心：RTS 最小闭环与双人 Showcase #709](https://github.com/MightyBubble/Ludots/issues/709)。#709 是联机实施计划与 Core 职责的单一真相；本文只定义《双人前线》的玩家体验、Showcase 组合边界与正式验收。

## 1. 概述

《双人前线》是一场供新玩家直接上手的双人 RTS 遭遇战。玩家不需要理解连接、帧、快照或数据包，在 3–5 分钟内即可完成一次完整循环：

```text
加入同一对局 -> 采集晶体 -> 生产步兵 -> 移动接敌 -> 交战 -> 摧毁敌方指挥核心 -> 结算
```

Showcase 的正式交付形态必须同时包含：

- 1 个独立权威对局进程；
- 2 个独立客户端进程；
- 2 名真人玩家；
- 1 张左右镜像的小型地图；
- 1 套双方相同的阵营配置；
- 1 种资源，以及指挥核心、采集车、步兵三类玩家对象。

单进程切换 `PlayerId`、分屏控制同一个 World、两个客户端各自运行完整玩法世界，均不构成联机验收。浏览器、桌面窗口或商业引擎只是宿主；Showcase Mod 和 Core 联机语义不得依赖其中任何一种宿主。

本页描述的是目标合同，不代表相关运行时已经存在。当前主线的 RTS 资产能证明资源花费、生产、生成目标和移动等局部能力，但不能证明双人会话、服务器权威、状态复制、迷雾披露、重连或完整对局已经完成。

## 2. 结构

### 2.1 运行结构

```text
客户端甲：本地框选、镜头、指针、命令反馈、画面
                         |
                         | 语义命令 / 该玩家可知的状态
                         v
独立权威对局：会话、席位、命令接纳、唯一玩法世界、胜负
                         ^
                         | 语义命令 / 该玩家可知的状态
                         |
客户端乙：本地框选、镜头、指针、命令反馈、画面
```

权威对局拥有唯一的玩法真相。客户端只发送可校验的移动、攻击、采集和生产命令，不发送本地框选框、悬停对象或宿主输入事件。客户端画面只消费 Core 给出的玩家可见状态，不自行决定资源、伤害、死亡、生成、胜负或重连结果。

### 2.2 职责分配

| 层次 | 拥有内容 | 禁止内容 |
| --- | --- | --- |
| Core | 会话、内容一致性、玩家席位、命令接纳、控制权、网络实体身份、每玩家信息披露、状态增量、重连、恢复与胜负所依赖的权威时间 | Socket、浏览器 API、窗口生命周期、RTS 专有单位名称 |
| 传输适配器 | 跨进程收发、缓冲池、真实连接质量观测、确定性故障注入 | 识别晶矿、步兵、基地或决定玩法结果 |
| 宿主 | 输入与画面接入、房间和连接状态呈现 | 私有玩法世界、私有网络身份、掉线后的本地继续运行 |
| Showcase Mod | 地图、镜像阵营、晶体数值、单位配置、目标、胜负配置与表现 | 自建连接、命令队列、复制、迷雾披露、重连或宿主分支 |

### 2.4 必须补齐的运行时依赖

以下能力在《双人前线》可运行前必须由 #709 的纵向切片补齐或给出正式生产证据，Showcase 不得私自实现：

1. 独立权威进程、双客户端会话、邀请码加入、就绪与内容指纹校验。
2. 每玩家定容命令环、重复/迟到/超前/乱序判断、原子批次接纳和分阶段结果。
3. 独立于 Arch Entity 与 `PresentationStableId` 的网络实体身份，以及 spawn、update、despawn。
4. 已确认基线上的每玩家增量状态、缺基线时的显式重同步和固定容量合同。
5. Knowledge、Visibility 与网络空间范围共同形成的每玩家披露结果；现有全量发布器不能直接进入网络热路径。
6. 30 秒席位保留、当前战局完整同步、命令确认游标与重连后的增量恢复。
7. 可复用的采集循环。当前正式 RTS 验收主要覆盖资源花费、建造和训练，没有证明“采集车往返晶矿并卸货”的生产级闭环。
8. 可复用的 RTS 直接攻击、伤害、死亡和胜负闭环。现有 `RtsDemoMod` 元数据提到战斗，但当前配置和验收不能替代本 Showcase 的双人攻击与摧毁核心证据。
9. 房间、命令阶段、连接状态和结算的宿主无关 UI 投影。
10. 真实跨进程故障注入、迷雾数据泄露检查、稳态零分配和 30 分钟长跑证据。

### 2.5 Showcase 注册要求

实现完成时，`showcase.registry.json` 中必须只有一个《双人前线》正式根条目，并完整填写 `binding`、`preset`、`docsPath`、`acceptanceTest`、`artifactDir`、`screenshot` 和 `status`。只有独立服务器与两个独立客户端的正式验收、截图和产物均存在后，条目才能标记为 `active`。

现有 `rts_demo`、`rts_showcase` 条目没有完整的 binding、preset 与证据字段，三个训练条目也只有部分验收字段；新条目不得复制这种未收口状态。本设计任务不修改注册表、Launcher、Mod、Apps 或任何运行时代码。

## 3. 详情

### 3.1 对局配置

首个版本使用版本化配置 `rts_duel_v1`。下列数值属于场景数据，禁止写成 Core 或宿主代码默认值：

| 项目 | 值 |
| --- | ---: |
| 真人玩家 | 2 |
| 权威对局进程 | 1 |
| 客户端进程 | 2 |
| 开局指挥核心 | 每方 1 座 |
| 开局采集车 | 每方 2 辆 |
| 开局步兵 | 每方 2 名 |
| 开局晶体 | 每方 40 |
| 单次卸货 | 20 晶体 |
| 训练步兵价格 | 60 晶体 |
| 训练步兵时间 | 8 秒 |
| 断线席位保留 | 30 秒 |
| 常规结束目标 | 3–5 分钟 |
| 时间判定点 | 5:00 对应的 CommittedTick |

地图左右镜像，双方到安全晶矿、中央通道和敌方核心的玩法距离一致。地图只提供基础阻挡、己方安全晶矿与中央交战通道，不加入高地、隐身、科技树、建筑摆放或第二种资源。

### 3.2 玩家界面与场上反馈

- 己方、敌方和中立对象使用可区分的颜色与轮廓，不能只依赖颜色表达阵营。
- 选中对象显示稳定尺寸的选择环；框选、镜头和悬停立即响应，且只属于本地交互。
- 采集车载货时显示晶体，只有返回核心并完成卸货后资源数字才增加。
- 指挥核心显示生命、生产队列、当前进度与集结点；资源不足或队列已满时给出明确原因。
- 移动命令使用地面标记，攻击命令使用目标标记；标记样式必须与命令阶段一致。
- 步兵受击显示短促反馈，死亡后从主视图、选择集合和小地图一致消失。
- 主界面只常驻晶体、双方核心生命、比赛时间、当前目标和连接状态，不展示 Tick、快照编号、包数或内部队列。
- 结算只显示胜、负或平局，以及用时、采集量、生产数和损失数，并提供“返回房间”和“再来一局”。

连接状态必须来自真实连接观测和命令确认延迟：

| 状态 | 玩家看到 | 行为 |
| --- | --- | --- |
| 顺畅 | 绿色图标与“顺畅” | 正常显示命令阶段 |
| 指令稍有延迟 | 黄色图标与同名文字 | 命令保留在“发送中”，不让单位假执行 |
| 连接中断 | 红色图标、“正在重连”与剩余席位时间 | 停止提交新玩法命令，尝试恢复同一席位 |

颜色不是唯一信息。玩家悬停连接图标时可以看到近期往返延迟和丢失率，但正常对局不展开技术仪表盘。测试配置写了“180ms、5% 丢失”不能直接驱动黄色图标；图标必须由实际观测触发。

### 3.3 命令五阶段反馈

“五阶段”指五类玩家可观察反馈，不表示每条命令会依次经过五种状态。第五类是任一权威阶段都可能进入的失败终点。

| 阶段 | 触发条件 | 玩家反馈 | 严禁误导 |
| --- | --- | --- | --- |
| 1. 发送中 | 本地语义命令已生成，尚未收到权威结果 | 空心命令标记、“发送中” | 单位不能移动、攻击、扣资源或生成 |
| 2. 服务器已接纳 | 会话、序号、身份、控制域、可见性、载荷和整批容量通过，完整批次进入唯一 `OrderQueue` | 标记变为已接纳样式 | 不能显示“开始执行” |
| 3. 已排队/等待条件 | 实体接单结果为 Queued 或 Pending | 显示“已排队”或具体等待原因 | 不能把全局入队当成实体已行动 |
| 4. 开始执行 | 实体接单结果为 Activated | 实心脉冲与“开始执行”，随后由玩法状态表现动作 | 不能在 Activated 前播放权威动作 |
| 5. 指令未执行 | 任一权威阶段拒绝，或在规定时间内无法取得结果 | 清除待执行标记，显示最终原因 | 禁止静默丢弃、默认成功或先执行再拉回 |

玩法动作完成由资源到账、单位抵达、生产完成、目标死亡等真实玩法结果表达，不再新增“网络已完成”假状态。重复命令必须返回同一结果，不能重复扣资源、重复生成或重复攻击；群体命令容量不足时整批拒绝，不能只让部分单位行动。

### 3.4 基础迷雾与信息披露

- 玩家始终知道自己的对象和已公开的场景目标。
- 敌方对象只有进入己方基础视野后才进入主视图、小地图、选择候选与实时状态。
- 敌方离开视野后，不再更新其实时位置、生命、生产队列或当前命令；已探索地形可以保留，但不能用地形记忆夹带实体实时状态。
- 玩家重连后仍只收到当前允许知道的状态；完整同步不是完整世界泄露。
- 可见性求值失败时拒绝披露，不能返回全世界或空快照假装成功。
- 画面被迷雾遮住只能证明表现正确。正式验收还必须检查发送给该玩家的状态中不存在视野外敌军的实时字段。

首版不加入隐身、侦测、高地、视锥、共享视野或战争迷雾衰减。这些是后续 Mod 能力，不是验证服务器权威的必要条件。

### 3.5 断线与重连

断线后，权威对局继续推进；已接纳的移动、采集和生产继续执行，但服务器不会替离线玩家选择目标、训练单位或发起攻击。离线席位保留 30 秒：

1. 离线玩家看到“正在重连”和剩余时间，不能继续提交新玩法命令。
2. 对手看到“对手暂时离线”，仍可继续对局。
3. 玩家在期限内使用服务端凭据恢复同一席位，而不是创建新玩家。
4. 重连先恢复最新已提交状态、当前可见集合和命令确认位置，再恢复增量。
5. 离线期间完成的采集、生产、移动、伤害和死亡全部保留；已死亡单位不能复活，已确认命令不能执行第二次。
6. 超过 30 秒未恢复时触发离线判负；禁止 AI 接管。
7. 权威进程不可用时双方明确看到对局服务中断并结束该局，客户端不得本地继续。

### 3.6 胜负与重连优先级

比赛计时以权威 CommittedTick 为准。每个已提交逻辑帧按以下优先级结算，排在前面的结果一旦成立，后面的规则不再改写结果：

1. **指挥核心摧毁。** 一方核心被摧毁，另一方立即获胜；同一 CommittedTick 内双方核心都被摧毁则平局。即使某方断线，已经发生的核心摧毁也立即结算。
2. **席位保留超时。** 某方超过 30 秒未恢复，离线方判负；双方在同一 CommittedTick 超时则平局。该规则优先于尚未结算的 5:00 生命判定。
3. **5:00 核心生命。** 只在没有核心被摧毁且没有席位超时时使用。核心剩余生命高者获胜，同值平局。

5:00 的具体处理规则如下：

| 5:00 时状态 | 处理 |
| --- | --- |
| 双方在线 | 立即比较 5:00 CommittedTick 的核心剩余生命并结算 |
| 任一方离线但仍在 30 秒期限内 | 记录 5:00 CommittedTick 的双方核心生命，暂缓该项判定 |
| 暂缓期间任一核心被摧毁 | 立即按“指挥核心摧毁”结算，不再使用 5:00 记录 |
| 离线玩家在期限内重连 | 双方恢复在线后，按记录的 5:00 核心生命结算，不使用重连时的生命替换记录 |
| 离线玩家先达到 30 秒期限 | 按“席位保留超时”结算，不再使用 5:00 记录 |

这组规则保证玩家不会因为画面计时器先后、重连耗时或客户端本地时间得到不同结果。指挥核心在 5:00 同一逻辑帧被摧毁时，摧毁判定优先于生命比较。

## 4. 场景

### 4.1 3–5 分钟新玩家流程

| 时间 | 玩家目标 | 玩家所见 | 被验证能力 |
| --- | --- | --- | --- |
| 0:00–0:20 | 创建或使用邀请码加入，双方就绪 | 房间、双方席位、内容一致状态、3 秒倒计时 | 独立会话、两名真人、内容指纹、无 AI 补位 |
| 0:20–0:55 | 储备 100 晶体 | 镜头落在己方核心；采集车与晶矿被轻量提示；装载、返程、卸货清楚可见 | 所有权、采集 Order、资源权威结果、复制 |
| 0:55–1:30 | 部署 1 名步兵 | 选择核心后看到唯一生产项；资源扣除一次，进度推进，单位在集结点出现 | 生产、网络实体生成、队列阶段、资源去重 |
| 1:30–2:30 | 推进中央通道 | 框选步兵，命令阶段标记出现；进入视野后第一次看见敌军 | 群体移动、五阶段反馈、每玩家披露、远端插值 |
| 2:30–4:30 | 突破并摧毁敌方核心 | 双方继续采集与生产，生命、死亡和核心受击结果一致 | 攻击、伤害、销毁、增量状态、胜负 |
| 最迟 5:00 | 完成结算 | 摧毁核心立即结束；否则按第 3.6 节处理 | 权威时间、离线优先级、双方一致结算 |

新玩家引导只呈现当前目标“储备晶体”“部署步兵”“推进中央”“摧毁核心”，通过对象高亮、上下文指针和可用命令按钮引导，不放置联机架构说明、快捷键清单或技术遥测。

### 4.2 不稳定连接演练

故障注入是同一 Showcase 的验收配置，不是正常首局强制体验。标准演练使用 #709 定义的 180ms 往返延迟、正负 30ms 抖动、5% 丢失和 2% 乱序：

- 玩家本地框选和镜头保持即时响应；
- 玩法命令停留在与真实结果对应的阶段；
- 没有确认时单位不假移动；
- 丢失、重复与乱序不会造成重复扣费、重复生产或重复攻击；
- 连接状态由实际观测变化；
- 双方最终看到同一权威结果。

### 4.3 断线演练

断线演练至少覆盖两个关键时刻：生产进行中，以及 5:00 判定前。玩家重连后必须看到当前战局，而不是断线前画面、重载地图或预制恢复状态。对局进程、两个客户端进程和故障注入器的日志与截图共同组成证据，但正常玩家结算界面不显示这些内部信息。

## 5. 边界

### 5.1 本 Showcase 必须包含

- 邀请制双人房间、就绪、开始、返回房间与再来一局；
- 两名真人、一个独立权威对局、两个独立客户端；
- 一张镜像地图、一个镜像阵营、一个资源、三类玩家对象；
- 采集、生产、移动、攻击、死亡、摧毁核心和 5:00 判定；
- 命令五阶段反馈、真实连接状态、基础迷雾和信息不泄露；
- 30 秒重连、无 AI 接管，以及第 3.6 节的明确胜负优先级；
- 正常网络与不稳定连接两套数据驱动验收配置；
- 固定容量、明确失败、稳态零分配和跨进程证据。

### 5.2 本 Showcase 明确不包含

- 公共匹配、账号、排行榜、聊天、观战、录像浏览、存档局、多人队伍或联盟；
- NAT 穿透、全球中继、主机迁移、跨版本兼容或完整反作弊体系；
- AI 补位、断线 AI 接管或权威进程退出后的客户端本地继续；
- 客户端全世界回滚、军队移动预测或客户端权威玩法模拟；
- 建筑摆放、第二种资源、科技树、英雄技能、隐身、高地与高级迷雾；
- 每 Tick 完整世界 JSON、存档快照冒充网络快照、容量不足时截断实体或返回空世界；
- 使用 Arch Entity、地图 InstanceId 或 `PresentationStableId` 直接作为网络实体身份；
- Showcase 私有的订单、所有权、采集、战斗、可见性、复制、恢复或连接运行时；
- 宿主识别晶矿、采集车、步兵或核心；
- 单进程切换玩家身份、分屏或 loopback 代替三进程正式验收；
- 修改现有 RTS Showcase 来掩盖缺失的通用运行时。

## 6. UAT

以下验收均从玩家所见、所做和所得结果出发。协议层、分配和数据泄露测试为这些玩家场景提供底层证据，但不能替代玩家场景。

三进程自动验收会从两个独立客户端实际执行这条主流程：每方先普通训练一次，再在第一项仍执行时按住队列键追加第二次训练；随后核对第二项先“已排队”再“开始执行”。群体移动不以其中一名单位到达为通过，而是为命令中的每名单位逐一核对唯一身份、起点、终点和最小移动距离。
