# 《双人前线》三进程玩法验收

> 上游 Epic：[平台无关服务器权威联机核心：RTS 最小闭环与双人 Showcase #709](https://github.com/MightyBubble/Ludots/issues/709)。完整玩家体验以[《双人前线》RTS 联机 Showcase 设计与验收](rts-multiplayer-showcase.md)为准。

## 1. 概述

这项验收同时启动一个独立权威对局和两个独立 Raylib 客户端，由两个客户端通过正式玩家输入完成一局最小 RTS 对战。它不再把“窗口打开、进程存活、凭据生成”当成联机玩法通过，而是要求两名玩家依次完成就绪、采集、两次训练、群体移动、交战和摧毁核心，并由三个进程分别写出可核对的终局证据。

Raylib 只是本次承载画面与输入的客户端宿主。会话、命令、接单、资源、单位、可见信息和胜负仍由平台无关的正式运行时负责，本验收不依赖浏览器接口或网页语义。

## 2. 结构

```text
同一次 Launcher 解析结果与内容指纹
  -> 独立权威进程：唯一玩法世界、接单、资源、战斗与胜负
  -> 独立客户端甲：玩家甲输入、己方与可见战场、复制结果
  -> 独立客户端乙：玩家乙输入、己方与可见战场、复制结果
  -> 验收脚本：核对三份证据、正式玩法配置与运行产物
```

三个角色使用同一份 Mod 顺序、计划指纹和玩法配置，各自拥有隔离的启动文件、输出目录和证据文件。客户端只注入玩家实际使用的按键与指针动作；它们不能直接写资源、位置、订单队列或胜负。权威进程保有唯一玩法真相，客户端最终只能从复制状态得到比赛结果。

第二次训练复用 `QueueModifier`、输入订单映射和正式 `OrderQueue`。验收读取现有 `commands[].admissionHistory`，确认这条命令先被实体接纳为“已排队”，等第一项完成后才变成“已激活”，不新增验收专用玩法通道。

## 3. 详情

运行配置由 `scripts/acceptance/rts-multiplayer-frontline-three-process.profile.json` 提供，玩法步骤和超时由 `RtsMultiplayerFrontlineThreeProcessAcceptancePlan.json` 提供。脚本从 Launcher 解析图定位正式 `RtsMultiplayerFrontlineConfig.json`，使用其中的训练价格核对总扣费，并把配置文件哈希写入运行清单。

脚本按以下顺序工作：

1. 检查端口，构建并解析一次 Launcher 计划，为权威进程和两个客户端生成互相隔离的启动产物。
2. 顺序启动三个进程，确认两个客户端取得不同会话身份，并确认三个角色使用相同的会话、内容和计划指纹。
3. 两名玩家从各自客户端按正式输入选择就绪，等待权威比赛进入进行中。
4. 每方选择一辆采集车，连续下达真实采集命令；每次卸货必须严格增加正式运输配置规定的一车资源，直到晶体从 40 增至 120。
5. 每方选择自己的指挥核心，先普通训练一名步兵；第一项仍在执行时按住队列修饰键再次训练。第一条不得出现实体级“已排队”，第二条必须先出现“已排队”，之后才出现“已激活”。
6. 每方最终必须恰好多出两名步兵，资源必须按正式价格两次扣除，即从 120 变为 0。
7. 双方选择步兵向中央推进。胜方至少用两名步兵继续推进并攻击敌方核心；每个参加群体移动的单位都必须有唯一身份、对应起点和终点，并各自达到最小移动距离。
8. 败方攻击进入视野的敌方步兵并造成伤害；胜方在敌方核心进入视野后摧毁它。
9. 权威进程和两个客户端必须报告同一结束时刻、同一胜方和同一核心摧毁结果。任一命令拒绝、运行时故障、错误输出、证据缺失、进程提前退出或数值不符均失败。
10. 结束时只清理本次持有且身份匹配的三个进程；删除原始会话凭据，只在清单中保留其哈希、格式校验和删除结果。

每次运行在 `artifacts/acceptance/rts-multiplayer-frontline-three-process/<UTC 时间>/` 留下解析结果、三组启动产物、输入文件与程序集哈希、三个进程的输出、三份玩法证据和 `run-manifest.json`。只有全部核对完成后，清单状态才会写为 `passed`。

## 4. 场景

在仓库根目录运行：

```powershell
./scripts/acceptance/run-rts-multiplayer-frontline-three-process.ps1
```

端口被占用时，可以为本次运行显式覆盖：

```powershell
./scripts/acceptance/run-rts-multiplayer-frontline-three-process.ps1 `
  -Port 28777 `
  -ConnectionKey "frontline-local-review"
```

验收人员先查看脚本退出码，再打开最新的 `run-manifest.json`。只有清单为 `passed`、三份玩法证据均通过、两份凭据哈希不同且原始凭据已删除、三个运行时标准错误为空、失败字段为空时，才能确认这次最小 RTS 联机玩法通过。

客户端画面仍用于确认新玩家体验是否清楚，包括选择反馈、生产进度、命令提示、战场可读性和结算表现；自动验收负责证明输入确实穿过正式链路并得到一致玩法结果，不能用结构化证据冒充画面质量。

## 5. 边界

- 不使用浏览器、网页接口或浏览器专属联机语义；更换客户端宿主不改变本验收的会话与玩法合同。
- 不用单进程切换玩家身份、进程内回环或两个本地完整世界冒充联机。
- 不直接写订单队列、资源、位置、伤害、死亡或胜负；所有动作从正式玩家输入进入。
- 不把网络层接收命令解释为单位已经执行；排队训练必须提供实体级“已排队 -> 已激活”证据。
- 不以任意一个单位移动代替群体移动；每个被移动命令覆盖的单位都要独立核对。
- 不在证据缺失时读取日志猜测通过，不忽略错误输出，不切换本地模式，不写入伪通过清单。
- 不按进程名或模糊时间范围清理其他任务的进程，只处理本次记录且 PID 与启动时间匹配的进程。
- 本项自动验收覆盖最小完整对局，不替代不稳定网络、断线重连、内容不一致拒绝、人工画面和新玩家可读性验收。

## 6. UAT

```gherkin
# language: zh-CN
功能: 两名玩家从独立客户端完成一局最小 RTS 对战

  场景: 两名玩家准备后进入同一战场
    假如 独立权威对局、客户端甲和客户端乙已经启动
    并且 两名玩家各自进入一个不同席位
    当 两名玩家都选择就绪
    那么 两人进入同一场正在进行的《双人前线》
    并且 每名玩家只能选择和指挥自己的单位
    并且 开局时双方都看不到迷雾外的敌方步兵和指挥核心

  场景: 每名玩家通过连续运输备齐两次训练资源
    假如 每名玩家拥有 40 晶体和一辆可用采集车
    当 玩家选择采集车并连续命令它采集最近的晶矿
    那么 玩家每次只在采集车卸货后看到晶体增加一车数量
    并且 玩家最终恰好拥有 120 晶体
    并且 采集车确实往返了晶矿与指挥核心

  场景: 第二名步兵等待第一名步兵训练完成
    假如 玩家已经选择自己的指挥核心并拥有 120 晶体
    当 玩家先普通训练一名步兵
    并且 第一名仍在训练时按住队列键再次训练
    那么 第一条训练命令直接开始且不会显示“已排队”
    并且 第二条训练命令先显示“已排队”
    并且 第一名完成后第二条训练命令才显示“开始执行”
    并且 玩家最终只新增两名步兵
    并且 晶体按正式价格扣除两次后恰好为 0

  场景: 群体中的每名步兵都完成推进
    假如 玩家已经选择一组自己的步兵
    当 玩家命令这组步兵向中央推进
    那么 命令中的每名步兵都有唯一身份
    并且 每名步兵都从自己的起点移动到对应终点
    并且 每名步兵都达到本场景要求的最小移动距离

  场景: 双方交战并由胜方摧毁敌方核心
    假如 双方步兵已经推进到中央并互相进入视野
    当 败方命令步兵攻击可见的敌方步兵
    并且 胜方命令至少两名步兵继续推进并攻击可见的敌方核心
    那么 败方看到目标步兵生命降低
    并且 胜方最终看到敌方指挥核心被摧毁
    并且 两个客户端都看到同一胜方和同一结束时刻
    并且 权威对局报告相同的核心摧毁结果

  场景: 任一步骤没有正式证据时明确失败
    假如 任一玩家命令被拒绝、任一进程提前退出或运行时报告故障
    或者 资源、单位、移动、伤害、胜负或三端结果任一项不一致
    当 验收汇总本次对局
    那么 本次验收明确显示失败
    并且 不会把进程存活、窗口打开或日志文字解释为玩法通过
    并且 不会静默跳过缺失证据
```
