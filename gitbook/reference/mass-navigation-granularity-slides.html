大世界导航入门

给 0 基础、0 项目上下文的新同学看的 Mass Navigation 概念课。

大世界导航入门

00 / start here

导航，就是游戏帮单位从这里走到那里。

你不需要先懂 ECS、Recast、NavMesh、HPA。先记住玩家看到的一件事：框选单位，点一个地方，单位应该绕开墙、山、建筑和别的单位，最后到达目标。

玩家看见

我点了目标，单位走过去；如果走不过去，游戏告诉我原因，而不是没反应。

设计师关心

哪些地方能走，哪里是路、桥、坡、森林，哪些单位能通过哪些区域。

工程关心

64km 大世界不能每帧全图暴算。要分层、分块、缓存、只更新变化的地方。

这套课件的读法：先看“它解决什么玩家问题”，再看术语名。术语只是给问题贴标签。

01 / player action

一次右键移动，底层通常拆成六步。

从玩家角度只有一个命令；从引擎角度，它会经过点选、粗路线、局部绕障、群体执行、避让、缓存和诊断。

1

把鼠标点变成世界坐标

用户点到地图上的哪里，先要变成 runtime 可计算的位置。

2

远距离先找大方向

几十公里外的目标，先用 Road Graph / Macro Chunk 找一条战略路线。

3

到附近再看细节

建筑、坡道、桥口、墙角这些“最后一公里”交给 NavMesh。

4

大群体共享执行

10k 单位不应该每个人一条完整路线，MassFlow 让一群人共享方向场。

5

局部避让和防重叠

空间 Hash 帮单位快速找到附近的人和障碍，避免 O(n²) 全场互看。

6

缓存和证据

重复查询要快；地图变了要失效；showcase 要能把这些层画出来。

02 / why layers

大世界导航不能只靠一张超级细的网。

64km 世界很大，1m 精度又很细。如果把全世界每个细节都放进一次寻路里，性能会爆；如果全都粗算，单位又会穿墙或卡住。所以要分层。

粗层解决

  • 远距离往哪个方向走。
  • 经过哪条路、桥、关口。
  • 跨哪些大 chunk。
  • 小地图上画整条战略路线。

细层解决

  • 最后几十米怎么绕建筑。
  • 坡度和地形高低能不能走。
  • 单位之间怎么排队。
  • 画了新障碍后怎么局部更新。
越往下越细、越贵、越局部

03 / units

km 是给人看的，cm 才是 Ludots 现在真实计算用的单位。

策划可以说“这是 64km 地图”。工程里，点击点、障碍物、路径缓存、dirty bounds 都应该落到 world cm，避免不同系统各自换算。

说法换算谁在用
64km给人看的地图尺度策划、文档、小地图标注
64,000m渲染或世界观常用表现层可能需要
6,400,000cm当前 runtime 世界宽度导航、障碍、点选、缓存
int cm厘米整数Ludots 当前权威坐标

为什么这很重要

如果障碍物用米，NavMesh 用局部厘米，小地图又用另一套比例，就会出现“我画的障碍和路径没关系”“mesh 像只铺了一小块”的问题。

64km = 64,000m = 6,400,000cm worldMin = -3,200,000cm worldMax = 3,200,000cm

04 / coordinate spaces

初学者最容易晕的点：同一个点，可能在三种空间里。

先别背类名。只记一句：用户操作用世界坐标，bake 文件有自己的局部坐标，画到屏幕上还要变成表现坐标。

World cm

玩家点击、路径起终点、运行时障碍、dirty 区域、path cache 都应该在这里对齐。

真实运行时全世界

Baked local cm

.lhtm / .ntil 文件里的局部 tile 坐标。它不能不换算就直接画到 world。

文件内部局部坐标

Visual space

渲染线、地表高度、UI overlay 用的空间。它负责看起来在哪，不负责改变寻路真相。

表现层通常 cm -> m
给 0 基础用户的排错口诀：如果“画出来的位置”和“寻路算的位置”不一样，先查是不是坐标空间混了。

06 / logic heightmap

LogicHeightmap 是给导航看的“地图底图”。

美术地形负责好看；LogicHeightmap 负责告诉导航：这里高度多少、能不能走、什么区域、有没有坡。它是生成 NavMesh 之前的中间层。

A

美术或地图源

地形、quad grid、视觉高度、静态障碍，先汇总成逻辑语义。

B

LogicHeightmap chunk

当前每块 64 x 64 cells。如果 cell 是 1m，一块就是 64m x 64m。

C

NavMesh bake

Recast 读取这份底图，生成可走多边形和 tile 数据。

业务场景

如果策划说“这片沼泽能走但很慢”，它不应该只是一张贴图颜色。导航数据里要能看到它是一个 high-cost area，寻路才会少走或绕开。

验收时不要只问“有没有 mesh”。还要问：这个 mesh 用的 height、blocked、area、cost 是不是对的。

07 / chunk basics

Chunk 的人话解释：把大地图切成很多小块，方便加载、计算和更新。

“chunk”不是一种东西，而是一类做法。不同系统会按自己的业务切块，所以必须带上前缀说清楚：streaming chunk、nav macro chunk、logic chunk、road chunk。

名字人话解释当前或建议尺寸用在什么场景
Streaming chunk加载工作区64m相机附近、热数据、流送
Nav macro chunk大世界导航索引块250m256 x 256 全世界 nav tile / macro 查询
Logic chunk导航底图块64m.lhtm，64 x 64 cells
Road chunk路网组织块道路/portal 级远距离战略路线、桥、隘口
Flow window战斗执行窗口100mMassFlow、10k 单位局部执行
如果只说“chunk”，但不说是哪一种，新同学一定会误解。验收界面也必须标清楚 overlay 当前画的是哪种 chunk。

07A / config map

你开发 Mod 时，不是“配置 chunk”，而是配置四层密度。

先别管术语。你真正要回答的是：地图有多大、导航切多少块、相机附近加载多大、战斗执行窗口多细。这四件事分散在不同配置里。

你想控制什么配置位置当前值改了会怎样
地图真实大小和基础格子assets/Maps/*.json
Boards[].WidthInTiles / HeightInTiles / GridCellSizeCm		250 x 250, 100cm决定 world cm 范围。当前公式得到 64km x 64km。
空间分区/加载基础块assets/Maps/*.json
Boards[].ChunkSizeCells		64 cells配合 1m cell 得到 64m chunk，影响 loaded chunks 和 graph projection。
MassNavigation 流送工作集assets/MassNavigationConfig.json
world.streamingChunkSizeCm / streamingRadiusCm		6400cm / 16000cm决定相机附近哪些块进入工作区。太小频繁切换，太大热数据变多。
Nav macro chunk 密度assets/MassNavigationConfig.json
bakeData.macroChunkColumns / macroChunkRows		256 x 256决定 64km 世界被切成多少个 runtime nav macro tile。越多越细，文件和查询管理也更多。
NavMesh agent / layer / areaassets/Configs/Navigation/navmesh.jsonGroundLight 等 profile决定半径、高度、坡度、区域代价。它不是 chunk 密度，但会影响能不能过窄口。
MassFlow cell / hashMassFlowSimulationState.cs100m field, 1m cell, 0.5m hard hash当前不是 Mod 配置。配置里的 solverWindow 必须匹配它，否则会直接报错。

07B / consequences

改密度不是“更大更好”，而是在精度、数量、更新成本之间换。

同样 64km 世界，macroChunkColumns 改一下，所有 tile 尺寸和数量都会变。你看到的 dirty 边框、NavMesh 覆盖范围、runtime bake 粒度也会跟着变。

配置每块多大全图块数结果
128 x 128500m16,384块少，索引和文件少；dirty bake 更粗，一画障碍可能重烘更大范围。
256 x 256250m65,536当前 U16 口径；大世界验收用这个证明 256 x 256 live NavMesh。
512 x 512125m262,144dirty 更细；tile 数量变 4 倍，bake 数据、索引、加载和诊断压力也上去。

计算公式

先由地图配置算 world，再由 macro rows/columns 切 runtime nav tile。不要拿 streaming chunk 尺寸去解释 nav macro tile。

worldWidthCm = WidthInTiles * 256 * GridCellSizeCm 当前 = 250 * 256 * 100 = 6,400,000cm navMacroTileWidthCm = worldWidthCm / macroChunkColumns 256 列 = 25,000cm = 250m
Mod 作者判断法：远距离组织可以用 128m-512m 级 macro；战术最后一公里不要靠 macro 精度解决，要交给 NavMesh / Flow / steering。

07C / defaults and failures

不配分三种：继承示例值、走代码默认值、直接启动失败。

所以答案不是简单“行”或“不行”。如果你的 Mod 就是复用 MassNavigation 示例地图，可以少配；如果是自己的地图和单位规模，就必须显式配，否则结果会和你的世界不匹配。

不配的是谁会怎样风险
不写自己的 override，只依赖 MassNavigationMod会继承当前示例配置：64km、1m grid、64m streaming、256 x 256 macro、100m MassFlow window。能跑 showcase；但你的 Mod 地图不是这个尺度时，overlay、bake、路径预算都会不贴合。
assets/Maps/*.json 里省略 Board 字段BoardConfig 有代码默认：64 x 64 tiles、100cm grid、64 cells chunk。会变成约 16.384km 世界，不是 64km；你以为没配，实际是在用默认小世界。
MassNavigationConfig.json 顶层缺 world / bakeData 等加载器会直接报错：Mass-nav config requires explicit ...这是好事，避免半套配置静默跑错。
world.streamingChunkSizeCm 或 bakeData.macroChunkColumns 是 0 / 缺失且没有继承值验证失败，启动或加载配置失败。不会悄悄猜一个值。
world.solverWindowWidthCm / HeightCm 不等于 10000当前会直接报错，因为 MassFlow SoA cache 现在固定 100m x 100m。MassFlow 窗口尺寸目前不是自由 Mod 配置。
navmesh.json profiles 为空NavMeshBakeConfig 加载失败。没有 agent profile，就不知道按什么半径、高度、坡度 bake。
一句话：做真实 Mod，不要“懒得配”。可以继承基础配置，但要明确知道自己继承了什么，并在 showcase 面板里显示这些最终值。

08 / nesting

大世界、导航块、加载块、战斗窗口，是套在一起的。

下面这张图是概念图，不是严格比例图。它只表达职责关系：外层管远距离，内层管当前附近，最内层管正在发生的战斗。

World: 64km x 64km
Nav macro: 250m
Streaming: 64m
MassFlow: 100m / 1m cells
  • World：整张地图，玩家可能在小地图上看到。
  • Nav macro：让远距离查询不用盯着每个 1m 小格。
  • Streaming：让相机附近的数据先热起来，远处不要全进热路径。
  • MassFlow window：让眼前这场战斗的 10k 单位共享执行方向。

09 / road graph

Road Graph 负责“走哪条大路”，不是负责每一步踩哪里。

它像地图软件里的高速公路网络：先告诉部队应该经过哪条路、桥、山口、入口，再把最后的局部细节交给 NavMesh 和 Flow。

  • Road edge：一段道路，带 cost、通行 profile、tag。
  • Portal：区域之间的入口，比如桥头、城门、山口。
  • Road chunk：按区域管理路网，方便远距离查询和流送。
  • 业务用法：小地图上显示完整战略路线，主视图只展开当前活跃段。

10 / navmesh

NavMesh 是一张“哪里可以走”的多边形网。

它适合解决建筑边缘、坡道、墙角、局部障碍这些细节。玩家不需要知道三角形，但 showcase 要能把 polygon、portal、blocked area 画出来。

术语人话解释看它干什么
Polygon一块可走区域看哪里能站人
Portal多边形之间的门看路径怎么穿过区域
Agent radius单位半径决定窄缝能不能过
Area cost区域代价让沼泽、坡、路有不同偏好

11 / recast

Recast 可以先理解成“NavMesh 烘焙器”。

它把 LogicHeightmap 和障碍数据采样成 cell，再生成可走多边形。Unity 和 Unreal 的 NavMesh 也有类似的 cell、voxel、tile、agent radius 概念。

概念0 基础解释调大/调小影响
Cell / voxel size烘焙时采样多细越小越精细，也越慢、越占内存
Tile sizeNavMesh 分块多大越小越适合局部更新，块太多管理成本更高
Agent radius单位要留多宽通道半径越大，能走的窄路越少
Agent slope最大可走坡度坡太陡就被标成不可走
Ludots 当前 GroundLight profile：radius 30cm、height 180cm、slope 45。当前 Recast cell size 由 agent 半径推导并夹在 1m 到 2m 范围内。

12 / runtime bake

Runtime bake 的人话解释：地图运行时变了，只重算被改脏的小块。

玩家或工具画了一个多边形障碍，正确结果不是全世界卡住重烘，而是找到被影响的 nav tile，局部 bake，替换数据，让新路径绕开障碍。

1

画障碍

多边形点位必须是 world cm，不是屏幕像素，也不是 baked local。

2

标 dirty tile

按 runtime nav tile 的世界范围找受影响的块。

3

局部 Recast bake

把世界坐标映射到 bake 空间，重烘受影响块。

4

替换 NavData

NavTileStore 更新，revision 增加，旧路径缓存失效。

showcase 应该让用户看见

障碍物、dirty tile 边框、新 NavMesh、旧路径失效、新路径绕行。颜色必须明确分开，不能和普通 NavMesh 线混在一起。

如果点了 Update NavData 画面没变化，0 基础用户会认为功能坏了。验收界面必须给出“baked 几块、changed 几块、revision 几号”。

13 / path cache

Path cache 是“同样的问题别重复算”，但地图变了必须失效。

如果很多单位去同一个目标，重复寻路要命中缓存。可是 runtime bake 后，旧路径可能已经穿过新障碍，所以 cache key 必须受 NavData revision 约束。

正确

  • 同起点/同目标/同 profile 的查询可以复用。
  • 并发路径查询不共享危险可变状态。
  • NavData revision 变化后旧结果失效。
  • showcase 显示 cache hit / miss。

错误

  • 画了障碍后还沿旧路穿过去。
  • 只用起终点做 key，不看 profile/layer/revision。
  • 远距离查询一多就卡死。
  • 失败时只说 no path，没有原因。
cache identity: start + goal + profile + layer + strategy + navDataRevision + normalized goal bucket

14 / spatial hash

空间 Hash 不负责找路，它负责快速找附近的人和障碍。

10k 单位互相避让时，不能每个单位都检查其他 9999 个单位。空间 Hash 把世界切成小格，每个单位只看自己附近几个格子。

Hash当前 cell解决什么
Separation hash1m找附近单位，做分离和排队
Hard resolve hash0.5m处理硬重叠、卡住、推开
Search radius附近几格不扫全场，只查局部邻居

16 / industry mapping

这些不是 Ludots 自己编的词，主流引擎也在解决同一类问题。

Unity 通常把 1 world unit 当 1m；Unreal 默认长度单位是 cm。它们都会用 agent、cell/voxel、tile、area cost、runtime rebuild 这类概念管理导航。

概念Unity / Unreal 常见语境Ludots 当前语境
世界单位Unity 常按米；Unreal 默认厘米runtime 使用 int cm
NavMesh可走区域、多边形、agent 配置.ntil tile + runtime query
Voxel / cell烘焙采样精度LogicHeightmap / Recast cell
Tile分块生成和动态重建nav macro tile、baked tile、dirty tile 要区分
Runtime update动态障碍或局部重建dirty chunk runtime bake + revision

17 / rts granularity

如果目标是 RA3 / SC2 类 RTS，战术层建议 0.5m 到 1m。

RTS 不需要 FPS 级别的厘米地形采样，但建筑缝、桥口、坡道、队形通过宽度不能太粗。宏观路线可以粗，最后一公里不能粗。

层推荐范围Ludots 当前结论
运行时坐标cm 或 m float 都可cm int足够细
地图语义 cell0.5m - 1m1m合理
NavMesh bake cell0.5m - 1m 常见约 1m - 2m普通 RTS 可用，窄口要关注
战术 tile32m - 128mbaked 64m合理
macro chunk128m - 512m250m适合远距离组织
局部硬碰撞0.25m - 0.5m0.5m合理
核心建议：250m macro 可以继续管大世界；最后一公里 NavMesh 和 MassFlow cell 要保持 0.5m - 1m 级有效精度。

18 / showcase ux

验收 showcase 要像教学工具，不像调试器倾倒内部变量。

0 基础用户打开后，应该先能完成普通操作，再逐层打开证据：路径、NavMesh、dirty tile、Flow、chunk、小地图、性能。

第一层：能玩

框选单位，左键/右键设置起终点，能看清路径和到达状态。

第二层：能看懂

颜色清楚区分：障碍、dirty、NavMesh、起点、终点、路径。

第三层：能验收

显示 baked / changed / revision / cache hit / query time / failure reason。

好的第一屏应该告诉用户：这是多大的世界、当前在哪个 chunk、你可以点哪里、按哪个按钮 bake、bake 后应该看见什么变化。

19 / visual language

路线、障碍、NavMesh、dirty tile 必须长得不一样。

0 基础用户不会读底层结构，只会读颜色和形状。验收画面如果线都一种颜色，就是把学习成本丢给用户。

图层建议视觉用户要读出的信息
Start绿色实心点路线从哪里开始
Goal紫色实心点或旗标目标在哪里
Path高亮紫色粗线单位实际会怎么走
NavMesh蓝色细线 / 半透明面哪里可走
Obstacle红色填充多边形哪里被挡住
Dirty tile橙色粗边框哪些块被重烘
Flow绿色箭头或热力群体朝哪移动
